# Архитектура и сопровождаемость

## Исследование

Продукт представляет собой локальный CLI над переносимым каталогом. Click передаёт управление `DatasetContext`; тот загружает конфигурацию и типы, сканирует исходные файлы, валидирует их, строит документы/записи/отношения и публикует производный индекс. Хранилища истории вынесены в адаптеры, модели — в `domain`, правила типов — в `typing_system`.

Это подходящая основа для source-native инструмента: пользовательские файлы доступны без сервиса, индекс можно восстановить, нет обязательной БД или сетевого процесса. Отдельный `atomic_write` обеспечивает замену содержимого одного файла через временный файл и `os.replace`. JSON-парсер отклоняет повторные ключи, невалидные константы и чрезмерную глубину. Эти механизмы следует сохранить при рефакторинге.

## Где архитектурные обещания расходятся с реализацией

`cli.py` содержит 2456 строк и не ограничивается разбором аргументов. В нём находятся чтение файлов, выборка секций, CSV-проекция, преобразование Markdown, экспорт и импорт директорий. Следовательно, описание «тонкого CLI» в `docs/state/02-architecture.md` — целевое правило, которому текущая реализация соответствует частично. Это объясняет различия проверки путей, бюджетов и ошибок между командами.

`DatasetContext.scan_and_validate`, `service.py:52–126`, соединяет валидацию с последующим повторным извлечением записей. Диагностика валидатора не является обязательным барьером для потребителя. Некорректный `relations[].target` доходит до `.get` и роняет команду: [CA-001](bugfixes/ca-001-malformed-relations.md). Аналогично файл с ошибкой кодировки получает диагностику, но может остаться документом со статусом `ok`, после чего поиск пытается прочитать его снова: [CA-002](bugfixes/ca-002-invalid-utf8.md).

Публикация индекса и запись данных имеют разные, неполные модели атомарности. Атомарная замена одного файла не обеспечивает create-only при гонке и не превращает удаление/переименование каталога индекса в транзакцию: [CA-005](bugfixes/ca-005-create-only-race.md), [CA-006](bugfixes/ca-006-index-publish.md).

## Предложения

Сначала закрепить общий слой чтения и записи: разрешение пути внутри корня, статус пригодности документа, проверка формы входа, план правки, согласованная публикация. Затем переносить содержательные обработчики из Click-функций в приложение. Простое разнесение `cli.py` по файлам без объединения этих механизмов оставит те же дефекты.

Разделить сущности «отсканирован», «успешно разобран», «допустим для поиска/запроса». Типизированный результат разбора должен переносить и данные, и ошибки; downstream-код не должен восстанавливать форму данных с помощью незащищённых `.get`.

Порты стоит добавлять для реальных границ: публикация снимка, конкурентная запись, история. Переход на SQLite или иной backend до фиксации контрактов не является необходимым условием исправлений. Тестируемый контракт важнее выбранного формата хранения.

## Ограничения вывода

Размер файла сам по себе не является багом и не доказывает необходимость переписывания проекта. Рекомендации основаны на конкретном повторении проверок и подтверждённых отказах. Полного анализа циклов импортов и сложности всех функций не проводилось.
