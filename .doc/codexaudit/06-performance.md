# Производительность и масштабирование

## Локальное измерение

Создан одноразовый датасет с 1000 короткими Markdown-файлами и одним общим поисковым термином. Каждый запуск — отдельный процесс `python3 -m todoc`, один и тот же Python 3.14.4 и WSL. Сетевых сервисов нет.

| Команда | Время | Результат |
|---|---:|---|
| `index rebuild` | 0.9525 с | exit 0 |
| Первый `docs search --query searchable --limit 5` после rebuild | 0.5604 с | exit 0 |
| Повтор того же поиска | 0.6107 с | exit 0 |

Это три отдельных наблюдения, не статистический бенчмарк, не p95 и не SLA. ОС-кэш, загрузка машины и время импорта Python включены. Первый rebuild не следует называть доказанным физически холодным чтением диска.

## Что объясняет стоимость

`ensure_index`, `service.py:190–212`, вызывает `scan()` перед решением о переиспользовании снимка. Даже на неизменном корпусе обход и stat остаются линейными по числу файлов. Хеш-кэш позволяет не перечитывать каждый файл для SHA, если совпали размер и mtime. Следовательно, фраза «каждая команда заново публикует индекс» неверна: снимок действительно переиспользуется, хотя обход сохраняется.

Поиск, `search.py:143–183`, читает текст каждого подходящего документа и разбирает Markdown. Для выданных результатов он ещё раз читает/разбирает Markdown, `search.py:197–202`, ради breadcrumb. `limit 5` ограничивает выдачу, но не сокращает просмотр всех кандидатов. Бюджет вывода не является бюджетом CPU или чтения диска.

`_snippet` ограничивает число окон-кандидатов 2000, что снижает стоимость выбора окна, но сначала собирает все позиции каждого термина. Для длинного документа с частым коротким термином массив позиций может быть большим. Стресс-тест такого файла здесь не проводился; это наблюдение сложности, а не подтверждённый аварийный отказ.

## Рекомендации по измерениям

Следующий воспроизводимый замер: 1k/10k/100k документов, короткие и длинные файлы, RU/EN, повторный поиск, изменение одного файла и большой JSON/CSV. Разделить время старта процесса, обхода, валидации, загрузки снимка и поиска. Измерить RSS, число read/stat, p50/p95 нескольких повторов и размер `.todoc`.

Сначала убрать повторный разбор результатов поиска и передавать структурные сведения из первого чтения. Затем оценивать reusable search representation или индекс по реальным измерениям. Решение о SQLite/FTS или другом backend нельзя обосновать только этим микрозамером.

## Надёжность кэша

Hash-cache доверяет паре mtime/size. Правка с сохранёнными размером и временем может не инвалидировать digest. Этот сценарий не воспроизводился; нельзя заявлять доказанную выдачу устаревших данных. Для операций, гарантирующих целостность перед записью, необходимо отдельно определить, когда требуется вычисление реального хеша, а не метаданные кэша.
