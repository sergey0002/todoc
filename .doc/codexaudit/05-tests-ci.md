# Тесты, CI и поставка

## Проверенные результаты

`PYTHONPATH=src python3 -m pytest` завершился с **1279 passed, 21 skipped за 95.75 с** на Python 3.14.4. Выполнен весь набор из настроенного `testpaths = tests`, а не выборочная папка. Причины каждого из 21 skip отдельно не исследовались; часть контрактных тестов явно пропускает сценарии, где команда завершилась успешно.

Wheel собран из временной копии `src`, pyproject, README и LICENSE командой pip с `--no-index --no-deps --no-build-isolation`. Сборка успешна, создан `todoc-0.1.0-py3-none-any.whl`, внутри есть `todoc/data/agent-skill/todoc/SKILL.md`. Установка собранного wheel в новое чистое окружение и проверка его CLI отдельно не выполнялись.

В `.github/workflows/tests.yml` настроены Python 3.11 и 3.12, pytest, branch coverage с `--fail-under=100`, linkcheck и валидация demo. Наличие этих шагов проверено локально по YAML; последний удалённый CI-run не запрашивался.

## Пробел контрактного инвентаря

`tests/cli/test_cli_contract.py:23–54` обходит только два уровня Click-команд и тем же способом считает ожидаемое число. В результате видит 62 позиции, включая группу `docs flow`, при фактических 63 листьях. Пропущены `docs flow render` и `docs flow walk`: [CA-007](bugfixes/ca-007-contract-leaves.md). Это относится к K47/K48; наличие других тестов flow не отрицается.

Тест, проверяющий размер инвентаря тем же алгоритмом, не обнаруживает структурную ошибку самого инвентаря. Здесь необходим рекурсивный обход и независимая проверка, что группы не попали в листья.

## Почему зелёный pytest пропускает найденные дефекты

Важны не дополнительные строки ради процента, а новые классы сценариев: некорректный target отношения, файл с невалидным UTF-8 в поиске, патч с неправильным типом line, нулевой limit, проигравший concurrent create и сбой rename после удаления предыдущего снимка. Сохранённый [воспроизводитель](evidence/reproduce.py) документирует эти сценарии без изменения runtime-кода.

Контрактные вызовы без обязательных аргументов в основном упражняют Click usage-ветки. Они не доказывают, что отказ после загрузки реальных данных тоже конвертируется в JSON. Нужны отрицательные интеграционные тесты с валидными аргументами и повреждёнными входами.

## Покрытие и окружение

`python3 -m coverage --version`, `.venv/bin/python -m coverage --version` и Windows `python -m coverage --version` сообщили об отсутствии модуля. Поэтому локальное покрытие неизвестно. Значение 100% не переносится из документации или CI-конфига в результат этого запуска. Сеть и установка пакетов для аудита не использовались.

В checkout есть `.venv/bin/python`, но нет `.venv/bin/todoc`; запуск с `PYTHONPATH=src` работает. Это соответствует ранее заведённым проблемам среды BUG-023/BUG-028, а не доказывает поломку wheel. Windows-падения из BUG-030…BUG-033 этим Linux-запуском не подтверждены и не опровергнуты.

## Предложения к CI

Сохранить branch coverage gate. Добавить содержательные отрицательные сценарии и fault injection. Проверять wheel в изолированном окружении и автоматически инвентаризировать package data. Добавить Windows в матрицу после выбора поддерживаемого runtime-контракта; версию 3.14 проверять явно, если требуется поддержка всего диапазона `>=3.11`.
