# Целостность данных и надёжность хранения

## Исследованные гарантии

Проверены планирование записи, применение хеша, создание документа/записи, точечная правка, публикация индекса и базовый путь change apply. Файлы данных остаются источником истины, производные данные находятся в `.todoc/index` и кэше. История отделена от индекса.

`atomic_write`, `scanner.py:37–53`, использует временный файл в том же каталоге, fsync и `os.replace`. Это полезная защита от частично записанного содержимого одного файла. Она не обеспечивает эксклюзивность создания, compare-and-swap или атомарную замену набора файлов.

## Потеря конкурентной записи

`apply_write_plan`, `write.py:118–132`, сначала проверяет `target.exists()` либо хеш, затем вызывает `atomic_write`. Воспроизводимый interleaving создаёт файл после проверки и до `os.replace`; функция успешно перезаписывает данные второго участника. Подробности: [CA-005](bugfixes/ca-005-create-only-race.md).

Это подтверждение конкретного окна гонки через подстановку в точке записи, а не измерение вероятности в реальной многопроцессной нагрузке. Для обычного одиночного агента последовательная проверка работает; для параллельных писателей обещание create-only недостаточно обеспечено. Аналогичный принцип требует проверки для optimistic locking правок.

## Снимок индекса не сохраняется при ошибке публикации

`RegistryStore.publish`, `registry.py:127–155`, использует общий `.tmp-current`, удаляет старый `current`, затем переименовывает staging. Инъекция ошибки на rename приводит к исчезновению рабочего `current`: [CA-006](bugfixes/ca-006-index-publish.md). Следующий rebuild способен восстановить индекс из исходников, поэтому утверждать потерю пользовательских документов нельзя.

Статический дополнительный риск: два publisher используют одно имя staging и способны удалить staging друг друга; читатель между удалением и rename видит отсутствие снимка. Эти параллельные варианты отдельно не воспроизводились и не выдаются за самостоятельные подтверждённые баги.

## Валидация перед записью

Создание записей проверяет тип, required_fields, schema и занятость идентификатора/пути. Создание документов проверяет структуру шаблона. Для редактирования нет аналогичного полноценного dry-run всех операций: [CA-003](bugfixes/ca-003-edit-preview-validation.md). Наличие preview-флага не заменяет общего планировщика.

Change apply считает новые тексты заранее и имеет откат при `OSError`, но это не даёт устойчивости к аварийному завершению процесса между записями. В этом аудите SIGKILL/crash-recovery и согласованность rollback с уже записанными событиями истории не проверялись; это отдельные сценарии приёмки, а не доказанная здесь потеря данных.

## Рекомендуемая модель

Для create — реальное эксклюзивное создание либо проверенная блокировка всего участка проверки/коммита. Для edit — проверка ожидаемого хеша внутри того же критического участка. Для индекса — отдельный immutable generation, атомарное переключение указателя и удаление старого поколения после успешной публикации. Читатель должен видеть целиком старую или целиком новую согласованную версию.
