# Контракт CLI для агента

## Что агент может считать стабильным

- Форма конверта: `schema_version`, `ok`, `data`, `diagnostics`, `next_actions`.
- Коды выхода: 0 успех, 1 операция, 2 использование, 3 валидация, 4 доступ, 5 конфликт, 6 неполнота.
- В stdout при `--output json` — ровно один JSON-текст.
- `next_actions[].argv` — готовые массивы аргументов для следующего шага.

## Что считать нестабильным

- `diag_*` идентификаторы: стабильны внутри одного запуска, не между процессами.
- Состав `data` у новых команд: читать через ключи, а не по позиции.

## Именование документов: русский заголовок — в метаданных, файл — на английском

Конвенция для любого документа датасета — и markdown, и JSON-записи:

1. **Заголовок — на русском, в стандартном поле метаданных.** Для md это поле
   `title` во front matter, для JSON-записи — поле `title` (обязательное во всех
   схемах сущностей). Отдельное поле `name` для заголовка **не вводится**:
   дублировать `title` — значит создать два источника истины для одного поля.
   Латинское машинное имя в системе уже есть — это слаг/`record_id`/имя файла
   (в формате Agent Skills ту же роль играет поле `name` = имени папки, а
   человекочитаемый текст живёт в `description`).
2. **Имя файла — на английском** (латиница, kebab-case, без кириллицы). Заголовок
   и имя файла независимы: русский заголовок не «переводится» в имя файла.
3. **Механика**: при кириллическом заголовке создавай документ с явным путём —
   `todoc docs new --path <dir>/<english-slug>.md` (слаг из заголовка сейчас
   наследует кириллицу — BUG-006; транслитерация уже реализована для изменений,
   `changes.py` `slugify`). JSON-записи именуются `record_id` латиницей — это
   enforce схемами (`^type:[a-z0-9-]+$`).
4. **Существующие кириллические имена** (4 плана в `plan/`, 6 баг-репортов в
   `bugs/` — 001–006; новые BUG-007+ именуются латинским kebab по конвенции
   ниже) — legacy: работают, но новые документы так не называть; переименование
   — отдельная миграция (ломает ссылки и `source_path` записей, делается скриптом
   с обновлением всех ссылок).

Все стартовые промпты типов (`todoc types prompt <тип> --op create`) несут
раздел «Именование файла» с этой конвенцией.

## Скилы: хранилище, диспетчер, мьют, импорт

Хранилище скилов — `demo/skills/` (открытый стандарт Agent Skills: папка со
SKILL.md = скил; опционально `references/` и `scripts/`). Подключение движка
к любому агенту — двумя взаимодополняющими способами: (а) нативно —
диспетчер-скил `todoc` одной папкой: `todoc skills attach --to <каталог скилов
платформы> --root demo`; для платформ с нативной поддержкой скилов больше
ничего не нужно; (б) строкой-правилом ниже в AGENTS.md — для платформ без
нативной поддержки. Витрина целиком в платформы НЕ монтируется — в контексте
платформы ровно один скил `todoc` (~100 токенов L1; описания под-скилов
тратят 0 токенов до выбора).

Правило (императив, с готовым argv):

```markdown
Перед любой нетривиальной задачей выполни:
  todoc skills tree --root demo
Выбери скилл по описанию (раздел = домен). Прочитай тело:
  todoc skills read --root demo --path <путь из дерева>
Действуй по инструкциям SKILL.md; references/ и scripts/ — по ходу.
Подходящего нет — работай без него; чужие скилы не модифицируй.
```

- **Мьют:** папка `!имя` исключена из дефолтного дерева и из `docs search`;
  `todoc skills tree --all` показывает с пометкой `[!]`. Содержимое не меняется.
- **Конфиги разделов:** папка (в т.ч. раздел vault) может описать себя файлом
  `.config.json` — русский `title`, `aliases` (через `|`), `description`,
  `order`; конфиг — не документ: вне индекса, поиска и счётчиков. Дерево
  малопонятно — прочитай `.config.json` раздела как обычный файл (отдельной
  команды нет), заголовки уже видны в `todoc skills tree` и `todoc docs tree`;
  «куда положить/где искать» — `todoc docs suggest --query "…"`.
- **Чужой скил — «просто закинул папку»:** скопируй папку скила в vault →
  одна команда `todoc validate --root demo --all` (live-скан подхватит сразу;
  целые пакеты — только папки со SKILL.md, обвязка hooks//manifests не
  переносится) — или одной командой:
  `todoc skills import --root demo --src <локальная папка или репо> --into <раздел>`.
  Перед использованием аудируй чужой скил (scripts/ — это код; скил
  `coding/review/security-review` — чеклист аудита).
- **После мьюта/импорта:** `todoc index rebuild --root demo`.

## Баг-репорты: поиск перед записью (анти-дубликат)

Каждый раз, наткнувшись на дефект, агент СНАЧАЛА ищет его в базе и только если
не находит — пишет новый репорт. Канон — шаг 1 create-промпта
(`todoc types prompt bug-report --op create`): два поиска (`--type bug-report`
по симптому и по компоненту, `--limit 10`); тот же дефект — не создавать,
сослаться на `BUG-NNN` и дополнить существующий репорт уточнением с датой;
созданный до проверки дубль — `status: duplicate` со ссылкой на основной
(репорты не удаляются); в новом репорте — строка-след поиска в «Заметки».
Пример связи-не-дубля: BUG-001 (явный doc_type без fm-правила) и BUG-002
(change open ставит doc_type note без правила) — один симптом, разные
механизмы и фиксы, перекрёстные ссылки в «Заметках».
