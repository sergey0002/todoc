# Идея: `.config.json` — самоописание папок

**Статус:** запланирована (2026-11-25) — исполняющий план
[folder-config-implementation](../plan/folder-config-implementation.md)
(doc:plan-folder-config): Задачи 1–5 = Фазы 1–2 и 3–5 (Фаза A скоринга);
Фаза 3b (стемминг+BM25) — вне скоупа плана с gate-условием (fixture-набор);
открытые вопросы закрыты в §4 плана. Продолжение линии «скилы как dir_type»
([skills-engine](skills-engine.md)) и общей модели типов todoc.

**Реализация:** выполнена (2026-11-26) — план [folder-config-implementation](../plan/folder-config-implementation.md)
(doc:plan-folder-config, 38/38) исполнен и закрыт (`done`); Фаза 3b (стемминг+BM25) — вне скоупа с gate-условием.

## Суть

Спец-файл **`.config.json`** в папке датасета: машиночитаемое самоописание —
заголовок, описание, порядок сортировки, иконка/цвет. CLI читает конфиги при
обходе и отдаёт человеку и агенту **описания папок прямо в выводе** — `docs tree`,
`skills tree`, `explain-path` перестают быть списком путей и становятся
сопроводительной картой: заголовок по-русски, описание, что здесь лежит и зачем.
Тот же конфиг — источник описаний для дерева скилов: сканер пробегает папки типа
`skill`, из `.config.json` берёт описание раздела, из SKILL.md — описание скила.

Кросс-ссылка: [теги документов](../plan/теги-документов-как-aliases-поиска--tags-updated-related-в-front-matter.md)
([[теги-документов-как-aliases-поиска--tags-updated-related-в-front-matter]]) — doc-уровень
той же весовой модели: теги папка+тип+тематика усиливают совпадения лексического поиска
и дают точный пост-фильтр `--tag`, дополняя папочную самоописание из `.config.json`.

## Проблема

1. **Папки молчат.** `dir_type` отвечает на вопрос «какой это тип», но не «что здесь».
   `docs tree` печатает пути без смысла; агент и человек угадывают назначение папки
   по имени (`notes/`? `inbox/`? что из них куда класть созвон?).
2. **Иерархия скилов без подписей.** В [skills-engine](skills-engine.md) разделы
   хранилища — обычные папки: `coding/`, `coding/git/` — но у них нет описаний,
   и дерево решений получается меню без пояснений к пунктам.
3. **Порядок отображения случаен.** Дерево сортируется алфавитом; важный раздел
   `process/` тонет между `misc/` и `tmp/`. Задать порядок нечем.
4. **Альтернативы хуже.** README в каждой папке шумит в `docs tree` и индексе
   (лишние документы), комментарии в коде не видны CLI, конфиг в `.todoc/` оторван
   от места (нельзя посмотреть, открыв папку, и не переносится вместе с ней при
   копировании подраздела).

## Принципы

1. **Данные, не код.** `.config.json` — декларативный JSON со `schema_version`,
   валидируется как остальная конфигурация todoc; ничего не исполняется (P3, P10).
2. **Служебный файл, не документ.** Файл исключается из индекса документов
   (как содержимое `.todoc/`): не попадает в `docs search`, не ломает счётчики,
   читается только сканером и CLI-выводом.
3. **Отсутствие — не ошибка.** Папка без `.config.json` валидна; файл — опциональное
   обогащение, а не обязательная плата (в отличие от `type.json` типов, где пустой
   описатель — ошибка конфигурации).
4. **Точка истины — файл рядом с данными.** Конфиг живёт в самой папке, переносится
   с ней (скопировал раздел скилов — перенёс и описания).
5. **Бонусом для скилов: каноническое место метаданных раздела.** description
   раздела скилов не надо выдумывать из SKILL.md первого попавшегося скила.

## Предложение

```json
{
  "schema_version": 1,
  "title": "Ремонт и стройка",
  "aliases": "стройка|ремонт|ванна|дизайн ванны|санузел|плитка",
  "description": "Идеи и скилы по ремонту и строительству.",
  "order": 10,
  "icon": "hammer",
  "lang": "ru",
  "tags": ["ремонт", "стройка"]
}
```

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `schema_version` | int | да | всегда 1 |
| `title` | string ≤ 80 | да | короткий заголовок для CLI-вывода; **без aliases участвует в поиске сам заголовок** — токенизируется и индексируется как основной поисковый текст папки |
| `aliases` | string ≤ 500 | нет | псевдонимы поиска через разделитель `|`: `стройка|ремонт|ванна|дизайн ванны`. Опциональное расширение поискового индекса: добавляет синонимы, которых нет в заголовке («Гит-скилы» не ловит «merge conflict» без них) |
| `description` | string ≤ 500 | нет | назначение папки; для разделов скилов — что внутри |
| `order` | int | нет | порядок в дереве (меньше — выше); без него — алфавит |
| `icon` | string | нет | имя иконки (UI-метаданные, не исполняется) |
| `lang` | string | нет | язык заголовка/описания |
| `tags` | list[string] | нет | ключевые слова; участвуют в `--query`-фильтрах наравне с aliases |

**Почему строкой через `|`, если псевдонимы есть.** Быстрее набирать, diff-friendly
(одна строка — одна правка), пустое/отсутствующее поле видно глазом. Нормализация:
пробелы по краям элемента обрезаются, пустые элементы отбрасываются, дубли —
`folder.config.duplicate_alias` (предупреждение, не ошибка). Папка без aliases
полноценно ищется по title (+description+tags); aliases — способ дописать синонимы
и жаргон предметной области, когда заголовка недостаточно.

Неизвестные поля — диагностика `folder.config.unknown_field` (та же философия, что
`config.unknown_field` у описателей типов: конфиг, молча принимающий лишнее, хуже
отказавшегося).

## Изменения CLI

| Команда | Что меняется |
|---|---|
| `docs tree` | рядом с путём — `title` (если есть) и обрезанное `description`; `--format json` добавляет `folder_meta` |
| `skills tree` (из [skills-engine](skills-engine.md)) | заголовки и описания **разделов** — из `.config.json`; описания скилов — из SKILL.md, как раньше |
| `explain-path` | доп. блок `folder_meta`: заголовок и описание папки назначения |
| `docs search` | `tags` из конфигов разделов участвуют в матчинге запроса (вес низкий) |
| `index rebuild` | конфиги читаются сканером, попадают в поколение индекса |

### Поиск по aliases и метрика релевантности

Механика встроена в CLI и используется тремя командами: `docs suggest` (из обсуждения
capture-workflows), `skills tree --query`, `docs tree --meta --match Q`.

**Фаза A — точный скоринг (как раньше, без зависимостей).** Тот же каркас, что у
существующего lexical-поиска (`application/search.py`: тот же `tokenize()` с кириллицей,
тот же детерминированный tie-break по id):

| Компонент | Вес | Правило |
|---|---|---|
| точный псевдоним | **+1.0 за элемент** | весь элемент `aliases` встречается в запросе подстрокой |
| пословное | **+0.3 за слово** | слова элемента найдены в запросе, порядок не важен |
| title/description/tags | **+0.2 за слово** | вспомогательный сигнал |
| бонус длины псевдонима | **×(1 + 0.1·(len−1))** | «дизайн ванны» > «ванна» при равных попаданиях |

Нормировка на максимум → 0..1; порог 0.25; ниже — в `discarded` (агент видит, почему
раздел не выбран). Пример «идея про дизайн ванны» → `ideas/repair 0.86 (alias: дизайн ванны)`.

**Фаза B — базовые формы слов (нормализация) + BM25-ранжирование.** Следующая ступень
точности, всё ещё офлайн и детерминированно.

#### Какие библиотеки брать (Python, минимальный набор)

| Задача | Выбор | Почему |
|---|---|---|
| Стеммер EN | **SnowballStemmer** из `nltk` или порт `snowballstemmer` (zero-dep, pure Python) | индустриальный стандарт Портера; `snowballstemmer` — один файл без данных, идеален для «не раздувать ядро» |
| Стеммер RU | тот же **Snowball russian** (обе библиотеки умеют) | единственный лёгкий вариант; полноценная морфология не нужна для aliases |
| Лёгкая RU-норма без nltk | усечение окончаний регэкспом (список суффиксов `ами|ями|иях|ах|ям|ой|ый|ая|ое|ые|у|ю|а|я|ы|и|е|ь`) | fallback, если зависимость нельзя; точность ниже, предсказуемость та же |
| BM25 | **`rank-bm25`** (одна функция, pure Python, ~200 строк) или **`bm25s`** (быстрее, numpy-опционально) | не тащим Whoosh/ tantivy: документация весит больше, чем наша задача |
| Русские стоп-слова | список на 100–200 слов прямо в коде (в, на, с, и, про, для…) | без библиотеки; стоп-слова вырезаются ДО стемминга |
| Чего НЕ брать | `pymorphy2/3` (морфология 5+ МБ словарей), `spaCy` (модели), `nltk` полный (корпуса) | избыточно для псевдонимов; может позже как opt-in |

Итог зависимостей фазы B: `snowballstemmer` + `rank-bm25` (или один `bm25s`) — суммарно
меньше 200 КБ, pure Python, офлайн. Всё за портами `E4 CandidateRetriever` /
`E5 Ranker` из AFTER-плана — ядро знает про интерфейс, не про библиотеки.

#### Нормализация (базовые формы)

Пайплайн одинаков для запроса, aliases, title, description, tags:

```
текст → lowercase → токенизация (существующий regex: буквы/цифры/_, кириллица)
     → вырезать стоп-слова (ru+en, список в коде)
     → стемминг Snowball (ru/en по алфавиту токена) → термы
```

Пример: «для дизайна ванны» → `дизайн`, `ванн` (stem), «Docker-контейнеры» → `docker`,
`контейнер`. Нормализованные формы индексируются рядом с исходными: **точное совпадение
даёт полный вес, стем-совпадение — 0.7** («ванной» поймает «ванна», но ниже точного).
Стеммы записей кэшируются в поколение индекса (как parse-кэш).

#### Индекс и BM25 по заголовкам + псевдонимам с весами

Что индексируется (мини-документ на папку/скил):

```
doc = title(×10) + aliases(×8) + tags(×4) + description(×2)
```

Поле повторяется N раз в индексном тексте → BM25-частота терма в «тяжёлом» поле выше.
Явные полевые веса проще и предсказуемее BM25-по-полям (BM25F), а результат тот же.

Формула — классический Okapi BM25 поверх стеммированных термов:

```
score(D, Q) = Σ_t  IDF(t) · (tf(t,D) · (k1+1)) / (tf(t,D) + k1·(1 − b + b·|D|/avgdl))
IDF(t) = ln(1 + (N − df + 0.5) / (df + 0.5))     # 0 < df ≤ N, без отрицательных IDF
k1 = 1.5, b = 0.75 (стандарт; настроечно через dataset.json позже)
```

где `tf` считает совместные вхождения исходных и стем-форм (стем с коэффициентом 0.7),
`N/df` — по папкам одного корня. Псевдоним-хиты дополнительно умножаются на 1.2
(alias-boost поверх BM25 — точное попадание в словарь сильнее частоты слова).

Слои ранжирования (детерминированно, сверху вниз):

```
1. Phase-A exact score (aliases подстрокой)      — главный сортировочный ключ
2. BM25 по стем-формам с полевыми весами        — второй ключ (ловит «ванной» через «ванн»)
3. tie-break: order → путь (лексикографически)   — как во всём todoc
```

Нормировка итогового списка: score/max → 0..1; порог 0.25; `reason` выводит, какой слой
сработал (`exact alias «дизайн ванны»`, `stem: ванной→ванн, поле aliases`). Всё это —
реализация порта `E5 Ranker`: `relevance_method` в конверте расширяется до
`lexical` / `lexical-stem` / `exact-alias`, обратная совместимость сохраняется.

**Сервис сохранения индекса.** Стем-индекс папок — производное: `index rebuild` пишет
`{поколение}/folder-index.json` (термы → папки, df-таблица) атомарно, как остальные
шарды; `docs suggest` читает его, отсутствие/устаревание (по `config_digest`) →
пересчёт на лету из конфигов (их мало, мгновенно). Никаких внешних хранилищ — тот же
принцип «файлы — истина, индекс — производное», P1/P2.

Пример запроса «нужно сохранить идею про ремонт ванной» после фазы B:

```
folder          score   reason
ideas/repair    0.91    exact alias «ремонт»; stem: ванной→ванн (aliases)
ideas/home      0.00    — (discarded)
```

**Честные ограничения метрики (прописаны в спеке):** стемминг ловит словоформы, но не
синонимию («ремонт» ≠ «отделка», пока не написано в aliases); Snowball иногда режет
короткие слова агрессивно — спорные пары проверяются fixture-запросами фазы 3; одинаковый
score у двух папок → обе в кандидатах, выбор за агентом/человеком. Никаких порогов
«уверенности» и молчаливых решений: CLI даёт ranked-список с числами и reason, выбор —
не его ответственность.

## Валидация (коды `folder.*`)

| Код | Когда |
|---|---|
| `folder.config.invalid_json` | синтаксическая ошибка JSON с локацией |
| `folder.config.unknown_field` | неизвестное поле |
| `folder.config.bad_type` | поле не того типа / длиннее лимита |
| `folder.config.bad_order` | `order` не int |
| `folder.config.bad_alias` | элемент псевдонима пустой/слишком длинный (>80) |
| `folder.config.duplicate_alias` | повтор псевдонима внутри одной папки (предупреждение) |
| `folder.config.alias_collision` | один и тот же псевдоним в двух папках (предупреждение: обе участвуют, агент видит обе с одинаковым score) |

Файлы `.config.json` в датасете «скилы»: правило поиска — сканер смотрит только на
верхний уровень каждой dir_type-папки (не рекурсивно в чужие типы).

## Роутинг агента (дополнение к skills-engine)

```markdown
3. Дерево малопонятно или пусто по описаниям — прочитай конфиг раздела:
   todoc docs read --root skills --path skills/coding/git/.config.json
```

(файл читается как обычный JSON через существующий CLI — отдельная команда не нужна).

### Текущий проект: хранится в движке, не в данных

Решение: контекст «в каком проекте работаем» — летучая переменная сессии,
поэтому живёт в **агентском стейте движка** `~/.local/state/todoc/state-<dataset_id>.json`
(переменная `context.current_project`), вне данных и вне Git. Формат стейта,
CLI (`state set/get/list/unset`), fallback-цепочка скоупа (явный `--within` →
стейт → весь корень) и фазы внедрения — в отдельной идее
[agent-state](agent-state.md). Команды `project use/show` — сахар над стейтом;
в v1 хранится только текущий проект.

## Сценарии (WHEN/THEN)

```markdown
#### Scenario: Дерево с описаниями
- **WHEN** в skills/coding/git/ лежит .config.json с title «Гит-скилы»
- **THEN** skills tree печатает «coding/git — Гит-скилы: Скилы работы с git…»
  без чтения человеком конфига вручную

#### Scenario: Папка без конфига
- **WHEN** .config.json отсутствует
- **THEN** папка выводится как раньше (путь), 0 диагностик

#### Scenario: Битый конфиг
- **WHEN** .config.json содержит неизвестное поле "color"
- **THEN** validate выдаёт folder.config.unknown_field с путём и JSON-локацией;
  дерево работает, поле игнорируется (fail-open на вывод, fail-closed на валидацию)

#### Scenario: Поиск по псевдонимам
- **WHEN** агент ищет «куда положить идею про дизайн ванны», а в
  ideas/repair/.config.json указан aliases "стройка|ремонт|ванна|дизайн ванны"
- **THEN** docs suggest возвращает ideas/repair с score ≈ 0.86 (точное вхождение
  многословного псевдонима) и reason «alias: дизайн ванны»; разделы без совпадений
  — в discarded

#### Scenario: Папка без псевдонимов
- **WHEN** .config.json написан без поля aliases (или пусто)
- **THEN** 0 диагностик: папка ищется по title/description/tags как обычно;
  aliases — опциональное расширение словаря, не требование

#### Scenario: Коллизия псевдонимов
- **WHEN** «ремонт» указан в двух папках
- **THEN** обе папки возвращаются с равным score и предупреждением
  folder.config.alias_collision; выбор — за агентом/человеком, CLI не решает
```

## План внедрения

- **Фаза 1 — парсер и валидация.** Чтение `.config.json` сканером, коды `folder.*`
  (aliases опционален, но валидируется при наличии). Приёмка: битые конфиги дают точные диагностики,
  отсутствующие/без aliases — 0 диагностик.
- **Фаза 2 — вывод.** `docs tree` и `explain-path` с `folder_meta`; JSON-конверт.
  Приёмка: демо-датасет с 3+ конфигами показывает заголовки.
- **Фаза 3 — скоринг и suggest (фаза A).** Токенизация, веса (1.0/0.3/0.2 + бонус длины),
  нормировка, порог 0.25, `discarded`; команда `docs suggest` (или флаг `--match`)
  по aliases+title+description+tags. Приёмка: сценарий «дизайн ванны» даёт
  ideas/repair сверху со score и reason; 5 fixture-запросов — ожидаемый порядок.
- **Фаза 3b — стемминг и BM25 (фаза B).** Зависимости `snowballstemmer` + `rank-bm25`
  (opt-in в pyproject extras `[search]`), стоп-лист в коде, нормализация пайплайном
  (токен → стоп-фильтр → стем), полевые веса title×10/aliases×8/tags×4/desc×2,
  alias-boost 1.2, стем-коэффициент 0.7, k1=1.5 b=0.75; `folder-index.json` в
  поколение индекса; `relevance_method: lexical-stem/exact-alias`. Приёмка: тот же
  fixture-набор, запрос «ремонт ванной» находит ideas/repair через стем-форму; gate:
  фаза B включается только если фаза A на нём хуже.
- **Фаза 4 — skills tree.** Описания разделов из конфигов; `skills tree --query`
  использует тот же скоринг. Приёмка: демо-хранилище печатает русские заголовки,
  query-фильтр возвращает релевантные разделы.
- **Фаза 5 — поиск.** `tags` в лексическом матчинге `docs search`. Приёмка: запрос
  по тегу находит документы раздела выше, чем до тегов.

## Открытые вопросы

- Наследование: раздел без описания наследует родительское? (рекомендация: нет —
  явность, иначе молчаливая семантика).
- Конфликт «description в конфиге vs первый параграф SKILL.md» для скил-папок:
  конфиг — для разделов, скил описывается своим SKILL.md (рекомендация).
- `.config.json` vs `.todoc/folder-configs.json` централизованно: выбрали рядом
  с папкой (переносимость + видимость); централизованный реестр может пригодиться
  для мульти-рутов — отложить.
- Регистронезависимость: только `.config.json` или также `config.json`?
  (рекомендация: только точное имя, конвенция одна).
- Граница фаз A/B: фаза A (точный скоринг) — сразу; фаза B (стемминг+BM25) — после
  fixture-набора запросов, доказывающего, что точного скоринга недостаточно (gate в
  духе search-embeddings-vector.after.md, только lexical-внутренний). Список
  fixture-запросов фиксируется до внедрения фазы B.
- Латинские и кириллические псевдонимы вперемешку («CI|гитхаб|github actions») —
  нормализация должна не ломать смешанные строки; токенизация по юникоду.
- Максимальное число псевдонимов на папку: лимит на длину строки (500) достаточен?
- Нужно ли `version`-поле для миграций формата (schema_version достаточно)?
