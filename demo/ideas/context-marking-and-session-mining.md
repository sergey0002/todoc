# Идея: независимая маркировка контекста и майнинг сессий (session-mining) для поиска тупиковых шагов агентов

**Статус:** зафиксирована (2026-11-28), идея — не план.

**Цель проекта (фиксируется здесь как корневая):** на основе парсинга
историй диалогов систематически выявлять тупиковые шаги и места, где агент
тратит лишние вызовы и токены, и **упрощать их** — в правилах, скилах,
промптах, справке CLI и документации. Улучшение измеряется теми же метриками
на следующей сессии того же класса задач, а не на глаз.

## Суть

Две половины одного контура, живущие в одной папке обычного Agent Skill
(`SKILL.md` + `references/` + `scripts/`), без хуков, плагинов и сети:

1. **Маркировка контекста.** В файле рулесов харнеса (`AGENTS.md`,
   `.cursor/rules/*.mdc`, `.claude/rules/*`) лежит системное правило со ссылкой
   на документ внутри скила, обязательный к чтению и исполнению. Агент выводит
   в чат маркеры-границы: `#session-<id>#` в начале сессии,
   `#skill-<имя>#` при вызове скила, `#/skill-<имя>#` в конце,
   `#rules-<путь>#` при обращении к рулесу. Только текст в ответе ассистента —
   поэтому одинаково работает в Kilo Code, Cursor, Claude Code, OpenCode,
   Codex и любом харнесе, который читает правила и хранит транскрипт.
2. **Майнинг сессий.** Python-скрипт в той же папке скила: драйверы находят
   сессии по вхождениям (ID бага, путь, фраза), читают их из хранилищ
   харнесов, нормализуют в древовидный JSON событий, считают токены и
   метрики, детектируют тупики, отдают `session.json` + `session.md` +
   компактный `feed.json` с бюджетом токенов для анализа ИИ.

## Проблема

1. **Сессия — чёрный ящик.** Лента диалога есть, но структуры нет: где
   начался скил, какие правила читались, какой вызов CLI был повтором
   предыдущего, сколько токенов ушло на неудачную ветку — вручную не
   восстановить на масштабе.
2. **Тупики видны только человеку.** Повторные `--help`, чтение одного файла
   по четыре раза, слепой ретрай после ошибки, брошенный на середине скил —
   каждый эпизод замечается чтением ленты, но не накапливается в метрику и
   не превращается в правку.
3. **Хуки привязаны к харнесу.** Готовые механизмы наблюдаемости
   (hooks, telemetry, OTel) работают только в своём харнесе и требуют
   установки; переносимого между Kilo/Cursor/OpenCode/Claude Code слоя нет.
4. **Обратная связь разорвана.** Правки правил и скилов делаются по
   ощущению; нет базовой линии «до» и замера «после» на том же классе задач,
   поэтому упрощение не доказуемо.
5. **Нет единиц для «сложности».** «Агенту было тяжело» — не метрика. Нужны
   `wasted_tokens`, `retry_rate`, `steps_to_first_success`,
   `abandoned_skills`, `orientation_calls` и т.п., считаемые из транскрипта.

## Принципы

1. **Zero-hook, zero-network.** Единственные механизмы — правило в файле и
   текст в ответе модели. Парсер читает файлы на диске. Ничего не надо
   устанавливать в харнес.
2. **Маркер — обычный текст ответа ассистента**, на отдельной строке, без
   обёрток и пересказа. Ни в кодовых блоках, ни в цитатах вывода CLI.
3. **Файлы — истина, производное пересобираемо** (P1): транскрипт харнеса —
   сырьё, `session.json`/`feed.json` — пересобираемые артефакты.
4. **Одна нормализованная модель событий — N драйверов.** Различия хранилищ
   харнесов изолированы в адаптерах; анализ не знает про Cursor/Kilo.
5. **Bounded output.** Компактный фид выбирается под бюджет токенов, а не
   «весь транскрипт целиком»; полный JSON остаётся на диске.
6. **Приватность по умолчанию.** Сессии содержат секреты: артефакты лежат
   локально, `out/` в `.gitignore`, фид проходит редактирование (ключи,
   токены, пути домашних каталогов).
7. **Метрика → гипотеза → правка → повторный замер.** Без повторного замера
   изменение не считается улучшением.
8. **Маркировка дешёвая.** ≤1 строка на событие, ~10–20 токенов; отсутствие
   маркера не ломает разбор, а становится метрикой `marker_compliance`.

## Предложение

### 1. Протокол маркировки — обязательный документ скила

Правило в рулесах (одна императивная строка + путь):

```markdown
Перед любой задачей прочитай и выполни
`skills/analysis/context-mining/references/marking-protocol.md`.
```

Сам протокол (`references/marking-protocol.md`) задаёт грамматику:

| Маркер | Когда | Закрывающий |
|---|---|---|
| `#session-<id>#` | первое сообщение ассистента в сессии; один раз | нет |
| `#skill-<имя>#` | перед выполнением скила; `<имя>` = `name` из его `SKILL.md` | да |
| `#/skill-<имя>#` | после Verification скила или при явном прерывании | — |
| `#rules-<путь>#` | при чтении/применении файла рулесов | нет (точечное событие) |

- `<id>` — длинный случайный идентификатор: `[0-9a-f]{32}` (UUID4 hex) или
  `YYYYMMDDTHHMMSSZ-<8hex>` для сортируемости. Генерирует
  `scripts/marker.py new-session`, модель выводит готовую строку; при
  отсутствии скрипта — UUID4, сгенерированный моделью.
- `<путь>` в `#rules-...` — путь от корня рабочей папки, без кавычек и
  пробелов (пробелы → `%20`).
- Маркеры на своей строке, с первого столбца, ровно один на строку, без
  окружающей пунктуации. Вложенность скилов разрешена: `#skill-a#` …
  `#skill-b#` … `#/skill-b#` … `#/skill-a#` — парсер собирает стек.
- `#rules-...` — точечное событие: последующие шаги приписываются к
  последнему маркеру правил до следующего такого маркера.
- Если маркер пришлось процитировать (документация, ответ пользователю),
  он экранируется: `\#session-...#`.
- Модель забыла маркер — парсер восстанавливает границы по вызовам
  инструментов и ставит `marker_compliance: false`; это дефект маркировки,
  а не потеря данных.

### 2. Раскладка скила

```
skills/analysis/context-mining/
├── SKILL.md
├── references/
│   ├── marking-protocol.md      ← обязателен к чтению, ссылка из рулесов
│   ├── event-model.md
│   └── dead-end-heuristics.md
├── scripts/
│   ├── marker.py                # new-session | validate
│   ├── mine.py                  # drivers | find | parse | report | feed
│   ├── drivers/                 # kilo.py cursor.py opencode.py claude.py file.py stdin.py
│   ├── tokens.py
│   └── schema/{session,feed,findings}.schema.json
└── out/                         # артефакты анализа (gitignore)
```

Скил ставится в любое хранилище `skills/` (vault todoc) или копируется в
нативную папку скилов платформы; правило-указатель добавляется в рулесы
каждого харнеса. Никакой генерации кода под конкретный харнес.

### 3. Драйверы сессий

```python
class SessionDriver(Protocol):
    name: str
    store_version: str
    def available(self) -> bool: ...
    def find_ids(self, needle: str, *, limit: int = 50) -> list[SessionRef]: ...
    def read(self, session_id: str) -> RawSession: ...
```

- `SessionRef = {driver, id, title, started_at, updated_at, cwd?, path}`.
- `find_ids` ищет вхождения строки (ID бага, путь файла, фразу) по
  заголовкам и телу сессий и возвращает id с датами — это входная точка
  «найди сессию, где обсуждался BUG-0NN».
- `read` отдаёт сырые сообщения и вызовы без нормализации.
- Драйверы: `kilo` (Kilo Code / VS Code storage), `cursor`, `opencode`,
  `claude` (Claude Code JSONL), `file` (любой JSONL/JSON/MD-транскрипт),
  `stdin` (вставка ленты вручную).
- Пути хранилищ — конфиг, не хардкод. Неизвестный формат — диагностика
  `driver.store_unknown` с путём и версией, а не пустой результат.
- `mine.py drivers` печатает таблицу: драйвер, доступен, версия хранилища,
  число сессий.

### 4. Нормализованная модель события

Одно событие:

```
{seq, ts, kind, session_id, skill_stack[], rules_ctx, tool, argv, cwd,
 exit_code, duration_ms, tokens:{in,out,counter}, bytes:{out,err},
 stdout_digest, files:{read[],written[]}, outcome: ok|error|unknown,
 retry_of, marker?}
```

`kind`: `marker.session|skill.open|skill.close|rules`, `message.user`,
`message.assistant`, `tool.cli`, `tool.shell`, `tool.script.temp`,
`tool.file.read|write|edit`, `tool.network`, `error`.

- `tool.cli` — вызов любой CLI (`todoc`, `git`, `npm`): argv, cwd, код
  выхода, длительность, дайджест вывода.
- `tool.shell` — bash/pwsh-команда с атрибутами и результатом.
- `tool.script.temp` — временный Python/JS/sh-скрипт: детектируется связка
  «создание (heredoc, `python - <<`, `cat > /tmp/x.py`, `Set-Content`) →
  запуск → результат» и склеивается в один логический шаг.
- Дерево: сессия → скилы (стек) → шаги. Выходы: `session.json` (вложенные
  `children`), `steps.jsonl` (плоско), `session.md` (для человека).

### 5. Компактный фид для ИИ

`feed.json`:

```
{session, budget_tokens, items:[{step_ref, kind, summary, why_included, tokens}],
 omitted:{count, tokens}, metrics}
```

Отбор: все маркеры, ошибки, ретраи, первый/последний шаг каждого скила и
аномалии; остальное — в `omitted` со счётчиком. Бюджет по умолчанию ~8k
токенов. Это то, что читает анализирующий ИИ вместо полного транскрипта;
полный JSON остаётся рядом для доказательств.

### 6. Метрики и детекторы тупиков

Метрики сессии: `steps`, `tool_calls`, `tokens_in/out`, `failed_steps`,
`retry_rate`, `wasted_tokens`, `orientation_calls`, `repeat_reads`,
`abandoned_skills`, `steps_to_first_success`, `marker_compliance`.

Детекторы (каждый даёт finding с ссылками на шаги-доказательства):

| Детектор | Условие | Сигнал |
|---|---|---|
| `flailing` | ≥3 варианта одной команды (Jaccard argv ≥0.6) без изменения состояния | перебор флагов |
| `blind_retry` | ошибка → идентичный вызов в следующих 2 шагах без правки файла | слепой ретрай |
| `orientation_loop` | `--help`/`types list`/`tree` больше 2 раз за сессию | потеря ориентации |
| `context_thrash` | один файл прочитан ≥4 раз | лишний контекст |
| `abandoned_skill` | `#skill-x#` без `#/skill-x#` или без успеха | брошенный скил |
| `token_overrun` | шаг дороже p95 сессии/класса | перерасход |
| `edit_revert` | запись файла, затем возврат к прежнему содержимому | откат |
| `dead_end` | ≥K шагов без успешного изменения состояния | тупик |

Выход `findings.json`: `{finding_id, type, severity, step_refs, evidence,
wasted_tokens, suggestion_hint}`.

### 7. Подсчёт токенов

`tokens.py` — подключаемый счётчик: `tiktoken` (`o200k_base`/`cl100k_base`),
`tokenizers` при наличии, fallback `ceil(chars/4)` с границами
`chars/3.2 … chars/4`. Ответ всегда несёт `{counter, in, out, estimate:
true|false}` — точность для Claude/Gemini не заявляется.

### 8. Замыкание цикла упрощения

`mine.py report` превращает findings в действие:

- `friction`/`token_overrun` → черновик `bug-report` (`todoc docs new
  --type bug-report`) с `agent_impact` и `tokens_extra_est`;
- повторяющийся тупик → правка правила/скила/справки CLI/документа;
- базовая линия: метрики сессий класса задач до правки; после правки —
  те же метрики на новых сессиях; улучшение = снижение
  `wasted_tokens`/`steps` при том же успехе.

### 9. Связка с движком todoc

- `ideas/action-logging.md` — CLI-лог даёт точные argv/exit codes; если
  движок начнёт писать `TODOC_SESSION_ID` из окружения, лог и транскрипт
  склеиваются по одному id.
- `ideas/agent-state.md` — `context.session_id` как точка стыковки.
- `bug-report` с `agent_impact` — штатный приёмник findings, фильтры
  `bugs-agent-friction.json` / `bugs-token-overrun.json` уже есть.

## План внедрения

- **Фаза 0 — протокол и правило.** `marking-protocol.md`, `marker.py`,
  указатели в `AGENTS.md`, `.cursor/rules`, `.claude/rules`.
  Приёмка: новая сессия содержит `#session-...#`, вызовы скилов дают
  парные маркеры; `marker.py validate` подтверждает грамматику.
- **Фаза 1 — драйверы `file`/`stdin` и модель событий.** `mine.py parse`,
  `session.json`/`session.md`/`steps.jsonl`, golden-тест на фикстуре.
  Приёмка: один и тот же транскрипт даёт побайтово стабильный JSON.
- **Фаза 2 — драйверы харнесов.** `kilo`, `cursor`, `opencode`, `claude` +
  `find_ids`. Приёмка: поиск ID бага находит правильные сессии и даты.
- **Фаза 3 — токены, метрики, детекторы, фид.** `findings.json`,
  `feed.json` с бюджетом. Приёмка: на 3 размеченных вручную сессиях
  precision детекторов ≥0.8, recall ≥0.6.
- **Фаза 4 — цикл упрощения.** Генерация черновиков `bug-report` и
  сравнение «до/после» на 5 классах задач. Приёмка: хотя бы один класс
  показывает снижение `wasted_tokens` без падения успеха.

## Открытые вопросы

- Надёжность эмиссии маркеров у разных моделей: часть моделей «нормализует»
  `#...#`; нужен ли второй, более устойчивый синтаксис (`⟦session:…⟧`) как
  опция протокола?
- Компакция контекста переписывает историю — маркеры ранних шагов могут
  исчезнуть; как восстанавливать границы по событиям компакции?
- Саб-агенты и параллельные сессии: как склеивать дерево по `parent_id`,
  если драйвер его не отдаёт?
- Форматы хранилищ меняются между версиями харнесов; политика: фиксировать
  `store_version` и падать явно или best-effort парсить?
- Приватность: где проходит граница редактирования (ключи, email, пути) и
  кто её задаёт — конфиг скила или локальный `.env`?
- Токены Claude/Gemini: принимать оценку по символам или тянуть
  провайдерский токенайзер, когда он есть?
- Нужен ли `#session-...#` закрывающий маркер для сессий без скилов, или
  конец сессии определяется по транскрипту?
- Как связывать сессию с репозиторием/классом задачи, если хранилище не
  хранит cwd, — по первому вызову CLI или по маркеру?
