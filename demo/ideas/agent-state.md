# Идея: агентский стейт — `state.json` в движке

**Статус:** идея, зафиксирован план. Продолжение линии «текущий проект»
([folder-config](folder-config.md), раздел «Текущий проект») и задач-записей
(entity_type `task`). В v1 хранится **только текущий проект**; карта остальных
значений — задел на будущее, не реализуется.

## Суть

Движок ведёт **персистентную память рабочего состояния** — один файл `state.json`
вне данных и вне Git (`~/.local/state/todoc/state-<dataset_id>.json`). Стейт —
«оперативка» между сессиями: где мы работаем, что в очереди, какие операции ждут
применения. Агент начинает любую сессию с чтения стейта и восстанавливает
контекст **одной командой**, не завися от переписки в чате: контекст чата конечен
и теряется, стейт — нет.

Граница (правило): данные — «диск» со знанием, стейт — указатели, курсоры и
короткие тексты **процесса**. Тест: удалили state.json → данные не пострадали,
сессия восстанавливает контекст из данных и заново выставляет переменные.

## Проблема

1. «Мы работаем в проекте X» приходится объяснять агенту в каждой сессии — чат
   не помнит; хранить это в данных нельзя (летучая переменная изменила бы
   corpus_digest и попала бы в счётчики/поиск, как обычный документ).
2. Незавершённые review-first операции (`--preview` без `--apply`) теряются между
   сессиями — негде держать «ждёт применения».
3. Курсоры интеграций (дофетчили Jira до задачи 1300 — с чего продолжать?) хранить
   негде: в данных — мусор, в чате — потеряется.
4. Служебные файлы движка уже есть (`<root>/.todoc/history/`, `<root>/.todoc/cache/`),
   но это данные-репозиторий: туда нельзя писать машинно-зависимое и сессионное —
   оно поедет в Git.

## Предложение

Один механизм вместо зоопарка файлов: **плоский именованный словарь переменных**
с секционными префиксами, файл keyed по dataset_id (два рута не конфликтуют),
запись только через CLI, атомарно. Поверх стейта — семантические команды
(`project use/show` из идеи 17 становятся сахаром над `state set/get`).

```
~/.local/state/todoc/state-<dataset_id>.json
{
  "schema_version": 1,
  "vars": { "context.current_project": "shop" },
  "updated_at": "2026-11-25T14:30:00Z"
}
```

- Ключи: `^[a-z][a-z0-9_.-]*$`, точка = секция (`context.current_project`).
- Значения: плоские скаляры (строка/число/bool); списки — нумерованные ключи
  (`next.1`, `next.2`).
- Лимиты: ≤200 ключей, значение ≤256 символов (кроме `session.last_summary` ≤200
  по определению), файл ≤64 КБ — стейт не свалка.
- Запись атомарная (в движке `atomic_write` уже есть), читает и пишет только CLI.

## Карта значений (полная, на будущее — в v1 НЕ реализуется)

| Секция | Ключи (примеры) | Что даёт новой сессии |
|---|---|---|
| `context` | `current_project`, `current_task`, `current_doc`, `current_goal`, `current_branch` | «мы в проекте shop, задача task:shop-0002 в работе» |
| `session` | `last_agent`, `last_at`, `last_summary`, `session_no` | чем закончили прошлый раз |
| `queue` | `next.1`, `next.2`… (указатели на record_id/doc_id), `note.*` | очередь дел на следующие сессии |
| `review` | `pending_op`, `pending_path`, `pending_hash`, `pending_since` | незавершённая review-first операция не теряется |
| `sync.*` | `jira.cursor`, `jira.last_fetch_at`, `gdrive.cursor`… | курсоры интеграций: продолжить с места остановки |
| `env` | `last_validate_at`, `last_validate_diag`, `last_index_gen`, `last_test_at`, `last_commit` | факты последней проверки среды (пишутся сами командами validate/index) |
| `prefs` | `language=ru`, `detail_level`… | пользовательские предпочтения сессий |
| `custom.*` | любые ключи пользователя | расширение без смены схемы |

Правило границы по секциям: указатели (`context.*`, `queue.*`, `review.*`) —
только ссылки на существующие записи/документы (валидация при set + `doctor`
на протухшие); курсоры (`sync.*`) и факты (`env.*`) — машинные; конвенции,
решения, постановки — **в данных** (`decision`, `idea`), стейт держит лишь ссылку.

## Объём v1: только проект

Единственная переменная v1 — `context.current_project` (строка). Остальные секции
карты — зафиксированный задел: реализация = добавить ключ в белый список и (для
указателей) валидатор, без изменения формата файла и CLI.

## План изменений (фазы)

1. **Хранилище стейта** (движок, без CLI):
   - `application/state.py`: load/save атомарно, путь `~/.local/state/todoc/state-<dataset_id>.json`
     (каталог создаётся при первом set; ошибка недоступного пути — внятная diagnostic).
   - Белый список ключей v1: `context.current_project`. Схема: schema_version, vars, updated_at.
   - Acceptance: unit-тесты load/save/атомарности/лимитов; данные демо не меняются.
2. **CLI `state`** (см. план CLI): set/get/list/unset; вывод JSON; коды ошибок.
   - Acceptance: `state set context.current_project demo` → `state get` возвращает;
     `state set foo.bar` → `state.unknown_key`; повторный set перезаписывает атомарно.
3. **Скоуп по умолчанию** (fallback-цепочка): явный `--within`/`--root` →
   `context.current_project` → весь корень. Первые команды-потребители:
   `docs search`, `records list` (при установленном проекте скоупятся на его папки).
   - Acceptance: с установленным проектом search не находит документы вне проекта;
     `--within` переопределяет; при пустом стейте поведение прежнее (0 диагностик).
4. **Сахар `project use/show`** (из идеи 17): `project use <name>` = `state set
   context.current_project <name>` + подтверждение; `project show` = переменная +
   сводка по проекту из данных (папка, счётчики задач по статусам, последние снимки).
   - Acceptance: use/show не пишут в данные; show работает при пустом стейте.
5. **Расширение секций + snapshot** (за gate): session/queue/review/env/sync;
   автообновление `env.*` командами validate/index; `state snapshot` — один JSON
   со всеми секциями для старта сессии; `state doctor` — проверка протухших указателей.
   - Gate: fixture-набор из ≥20 переменных — лимиты и скорость записи; snapshot
     читается агентом без второго вызова.

Порядок 1→2 обязательный; 3 и 4 можно менять местами; 5 — отдельным циклом после
стабильности v1.

## План CLI (одна новая группа `state`)

| Команда | Фаза | Поведение | Вывод (JSON) |
|---|---|---|---|
| `todoc state set <key> <value>` | 2 | атомарная запись; ключ только из белого списка v1; `--output json` | `{ok, key, value, updated_at}` |
| `todoc state get <key>` | 2 | чтение; отсутствующий ключ → ok=false | `{ok, key, value\|null}` |
| `todoc state list [--prefix <секция>]` | 2 | все переменные или секция | `{ok, vars: {...}}` |
| `todoc state unset <key>` | 2 | удалить ключ (idempotent) | `{ok, key, removed: bool}` |
| `todoc project use <name>` | 4 | сахар: set + проверка папки проекта в данных, если есть | `{ok, project, set_at}` |
| `todoc project show` | 4 | переменная + сводка из данных (счётчики, статусы задач) | `{ok, project, scope, stats}` |
| `todoc state snapshot` | 5 | все секции одним JSON — вход агента в сессию | `{ok, context, session, queue, review, env}` |

Коды ошибок: `state.unknown_key` (не в белом списке), `state.invalid_value`
(не скаляр, длина), `state.limit_exceeded` (>200 ключей), `state.pointer_missing`
(фаза 5: указатель на несуществующую запись), `state.file_unavailable`.

Валидация значения v1: `context.current_project` — строка `^[a-z0-9][a-z0-9_-]*$`;
существование проекта в данных проверяется с фазы 4 (`project use`), в фазе 2 —
просто строка (демо-хранилище ещё не имеет папок проектов).

## Сценарии (WHEN/THEN)

- WHEN агент начинает сессию THEN `state list` → «current_project: shop» → вся
  работа скоупится на проект без повторных объяснений пользователя.
- WHEN пользователь говорит «теперь работаем в проекте bakery» THEN
  `state set context.current_project bakery` → след одной командой, данные не тронуты.
- WHEN сессия на другой машине (стейт пуст) THEN агент восстанавливает контекст
  из данных (последние `origin.project` задач, решения) и выставляет переменную
  `set`-ом; стейт — подсказка, проверяемая по данным, не истина.
- WHEN агент делает `--preview` без `--apply` (фаза 5) THEN `review.pending_*`
  фиксирует незавершённую операцию; следующая сессия видит её в `snapshot`.
- WHEN попытка `state set session.last_agent…` в v1 THEN `state.unknown_key`
  (белый список = 1 ключ); расширение — правка списка, не формата.

## Миграция

- Раздел «Текущий проект» в [folder-config](folder-config.md) переписан на
  движковый стейт (эта идея); хранение контекста в данных (`current-project.json`)
  исключено.
- dataset.json не меняется (trusted_workflows не затронуты).
