# Идея: прямое редактирование файлов без дорогого `docs edit`, короткая команда финализации `todoc sync <path>` и замена правил/промптов

- Тип: `idea`
- Создан: 2026-11-27
- Идентификатор: `doc:ideas/direct-edit-and-git-sync.md`
- Статус: `captured` (базовый этап v1 зафиксирован; этап 2 с Git и авто-конвейером отложен на развитие)

## Суть

1. **Отказаться в правилах, скилах и стартовых промптах от дорогого по токенам редактирования через `todoc docs edit --patch-file`:** официально разрешить агенту и человеку **всегда редактировать любые исходные файлы в `DATA_ROOT` (`.md`, `.json`, `.csv`) напрямую** штатными инструментами (`Edit`/`Write`/IDE/Obsidian), оставив за CLI поиск, навигацию и создание каркасов по шаблонам (`docs new`, `records create`).
2. **Ввести одну короткую и дешёвую по выводу CLI-команду пост-финализации — `todoc sync --root <PATH> <path> [<path2>...]`** и прописать во всех правилах/скилах простое правило: *«Отредактировал файл напрямую — сразу апни его одной командой `todoc sync <path>`»*. Команда за один вызов бампит `updated:`, обновляет историю «до/после», чистит `parse_cache`/индекс, валидирует правку и возвращает компактный ответ с полем `guidance` (`P15`).
3. **Отложить обход коммитов Git на второй этап (с 100% переиспользованием кода `sync`):** сначала внедряется только пофайловая команда `todoc sync <path>` и обновление правил, а позже поверх этой же ядерной функции докручиваются проверка непроверенных коммитов `todoc sync --from-git` и пост-коммитные расширения (**авто-документирование**, **авто-код-ревью** и др.).

## Проблема

1. **Редактирование через CLI (`docs edit --patch-file`) критически дорого по токенам и выводам.**
   - Чтобы поправить план, идею, отчёт или JSON-запись через `todoc docs edit`, агенту приходится сначала вычитывать физические номера строк, затем генерировать отдельный JSON-файл патча `{"ops": [{"op": "replace|insert_after|delete", "line": N, ...}]}`, прогонять `--preview` (который печатает назад весь массив `ops` — [`BUG-014`](../bugs/bug-014-docs-edit-preview-ne-pokazyvaet-numeraciyu-rezultata.md)) и отдельно вызывать `--apply` ([`BUG-004`](../bugs/bug-004--docs-edit-не-умеет-вставку-и-удаление-строк.md)).
   - На больших документах это сжигает в `5–10` раз больше входных и выходных токенов и провоцирует промахи по номерам строк, тогда как нативный `Edit` агента делает ту же правку за один шаг.
   - При этом сейчас требование использовать `docs edit --patch-file` размножено во всех `32` промптах `.todoc/doc_types/*/prompts/edit.md`, `25` промптах `.todoc/entity_types/*/prompts/edit.md`, в `AGENTS.md`, `SKILL.md` и скилах `todoc-capture` / `todoc-plan` / `todoc-execute`.
2. **Но если просто править файлы напрямую без завершающего вызова CLI, выпадают 4 системных механизма `todoc`:**
   - не бампится автоматически поле `updated:` во front matter `.md`;
   - не пишется снимок «до/после» и диапазоны строк `ranges` в `.todoc/history/` (`observe_external_changes` фиксирует лишь слепой `before: null`);
   - не сбрасывается точечно парс-кэш документа (`invalidate_parse_cache`);
   - не проверяется конкурентная база (`--if-hash`) / дрейф автогенерируемых витрин `derived_from` и агент не получает блок подсказок `guidance` (`P15`) при случайной поломке секции, схемы или ссылки.

## Принципы

1. **Минимум токенов на правку и ответ.** Правка содержимого делается нативным инструментом напрямую, а CLI вызывается ровно один раз после правки с ультра-компактным ответом (`3–5` строк JSON при успехе, без перепечатки содержимого файла).
2. **CLI там, где он реально сильнее прямого доступа.** Поиск (`docs search`), оглавления (`docs tree`, `skills tree`, `docs suggest`), чтение секций (`docs read --section`), запросы к записям (`records list/query/aggregate`), создание по шаблону (`docs new`, `records create`) и перенос со ссылками (`docs move`, `folderize`) идут через CLI.
3. **Одно ядро синхронизации файла — и для ручного вызова сейчас, и для Git потом.** Вся логика финализации пишется в одной функции `sync_file(ctx, rel_path, ...)`, чтобы на следующем этапе обход коммитов Git просто вызывал её же без дублирования кода.

## Предложение

> **Этап 1 (делаем сейчас):** прямая правка любых файлов данных + одна короткая команда `todoc sync <path>` + обновление всех правил, скилов и промптов.

### 1. Спецификация короткой команды `todoc sync`

```bash
# Основной вызов сразу после прямой правки одного или нескольких файлов:
todoc sync --root KB <path> [<path2> ...]

# Вызов без аргументов (или с --dirty) — сам находит все локально изменённые файлы по mtime/hash из stats.json:
todoc sync --root KB [--dirty]

# Опциональная защита от гонок, если нужно сверить хеш файла до начала прямой правки:
todoc sync --root KB <path> --if-hash sha256:...
```

**Удобство аргументов для агента (нулевая фрикция):**
- `<path>` принимается **и как путь относительно `DATA_ROOT`** (`ideas/foo.md`), **и как путь от текущей рабочей директории** (`demo/ideas/foo.md`) — CLI сам приводит его к root-relative пути внутри `--root`, не падая с ложной ошибкой «файл не найден».
- Если агент поправил сразу 4 файла за один ход, он передаёт их списком в один вызов `todoc sync --root demo path1 path2 ...` (либо просто вызывает `todoc sync --root demo`).

**Что делает `todoc sync` внутри за один быстрый проход по каждому файлу:**
1. **Автобамп `updated:` во front matter:** если файл — `.md` с YAML front matter, содержащим `updated:`, и его содержательный хеш изменился (а не только строка `updated:`), атомарно выставляет `updated: <сегодняшняя UTC-дата>` прямо в файл.
2. **Запись «до/после» и `ranges` в историю:** достаёт предыдущее содержимое `before` (из последнего снимка журнала или `git show HEAD:./<path>` с учётом подпапки репозитория), считает построчные `changed_ranges(before, after)` и пишет полноценное событие истории (сохраняя работу `log --section`, `diff`, `blame`, `records undo-relation`).
3. **Сброс кэша и обновление индекса:** вызывает `invalidate_parse_cache(root, rel_path)` (при удалении файла — чистит сиротский кэш) и обновляет индекс, упоминания `mentions` и рёбра `relations`.
4. **Валидация и выдача `guidance` (`P15`):** проверяет JSON Schema записи, обязательные секции и `allowed_statuses` документа, локальные ссылки/якоря, а также не отредактирована ли вручную автогенерируемая витрина с `derived_from` (`docs.derived_edited_directly`) и не протухли ли якоря `stale`.

**Компактный контракт ответа (бережливый к токенам):**
```json
{
  "schema_version": 1,
  "ok": true,
  "data": {
    "dataset_id": "dataset-80c70868",
    "synced": [
      {"path": "ideas/foo.md", "hash": "sha256:...", "updated_bumped": true}
    ],
    "diagnostics_count": 0
  },
  "diagnostics": [],
  "next_actions": [],
  "guidance": null
}
```
При `ok: true` — никакого лишнего текста; при `ok: false` — точные `diagnostics` с локациями и развёрнутый блок `guidance` (`P15`) со ссылками на скил и документацию для исправления ошибки.

### 2. Как именно изменить правила, скилы и промпты (полная карта замен)

| Где меняем | Было сейчас | Станет в правилах v1 |
|---|---|---|
| **`AGENTS.md`** (правила 1 и 4 + шпаргалка) | Запрет прямой правки; правка существующих `.md` через `docs edit --preview` → `--apply` (с оговоркой-костылём только для пустого скелета `docs new`). | **Поиск/навигация и создание по шаблонам (`docs new`, `records create`) — через CLI. Редактирование любых файлов в `DATA_ROOT` — напрямую штатным `Edit`, после чего обязательно выполнить короткую команду `todoc sync --root demo <path>`.** Не править руками `created`/`updated` и автогенерируемые витрины `derived_from`; перенос файлов — через `docs move` / `folderize`. |
| **Корневой `SKILL.md` и `demo/skill/SKILL.md`** | Только `records create` и упоминание `docs edit --if-hash`, без правила прямой правки `.md`/`.json`. | Секция **Create via CLI templates, edit directly + `todoc sync`**: создавать новые файлы через `docs new` / `records create`, редактировать существующие напрямую и завершать правку вызовом `todoc sync --root <PATH> <path>`. |
| **`demo/notes/agent-contract.md`** | Нет канонического раздела о прямой правке и финализации. | Новый раздел **«Редактирование файлов данных: прямая правка + `todoc sync`»** с правилом экономии токенов и тремя границами (`derived_from`, даты front matter, перенос путей). |
| **Скилы процессов** (`todoc-capture`, `todoc-plan`, `todoc-execute`, `doc-flow-capture`, `doc-spec-write`) | Требуют готовить `patch-file` и вызывать `docs edit --patch-file ... --preview` → `--apply` даже для вписывания секций плана, `status: captured` и строк отклонений. | Заменяются на двухходовку: `docs new` (если новый файл) → прямое редактирование файла → `todoc sync --root KB <path>` (для точечной смены одного статуса по-прежнему удобен `docs status --set`). |
| **Стартовые промпты типов** (`.todoc/doc_types/*/prompts/{create,edit}.md` — `32` типа, `.todoc/entity_types/*/prompts/{create,edit}.md` — `25` типов, плюс шаблоны `init_dataset` в `src/todoc/config.py`) | Во всех `prompts/edit.md` прописана сборка `patch.json` / `patch.txt` и двойной вызов `docs edit --preview / --apply`. | Единый короткий шаблон правки: 1) при необходимости прочитай секцию/схему типа; 2) внеси правки напрямую в файл (не трогая `created`/`updated`); 3) запусти `todoc sync --root KB <path>` и убедись, что `ok: true` и `diagnostics: []`. |
| **Команда `todoc docs edit`** | Позиционировалась как основной способ редактирования. | Остаётся в CLI для обратной совместимости и внешних без-агентных скриптов, но снимается со всех обязательных правил; отпадает необходимость раздувать построчный патчер. |

## Вектор развития (Этап 2 — докрутка Git и пост-коммитной автоматики потом)

После того как базовая связка «прямая правка + `todoc sync <path>`» заработает в бою, поверх **той же самой функции `sync_file(...)`** без дублирования кода добавляются:

1. **Пакетная досинхронизация по непроверенным коммитам Git (`todoc sync --root KB --from-git`):**
   - хранит курсор последнего проверенного коммита `last_synced_head`;
   - находит все новые коммиты `last_synced_head..HEAD` (например, если человек поправил файлы в IDE/Obsidian и закоммитил забыв `todoc sync`, либо пришёл `git pull / merge`), достаёт список затронутых файлов и **прогоняет каждый через ту же команду `sync_file(...)`**;
   - сначала запускается руками, а позже при желании вешается на Git-хуки (`pre-commit` / `post-merge`) или авто-детект смены `.git/HEAD`.
2. **Пост-коммитный агентный конвейер поверх непроверенных коммитов (отдельные будущие идеи и `agent_flow`):**
   - **авто-документирование (`auto-docs`):** отслеживание коммитов в `src/`, изменивших CLI, схемы или бизнес-логику, с подготовкой черновиков обновлений для `state/` (`AS-IS`), `specs/`, `flow-doc`, `HOME.md` и `task-report` (в связке с [`documentation-system`](documentation-system.md));
   - **авто-код-ревью и секьюрити-аудит (`auto-review`):** прогон новых коммитов `last_reviewed_head..HEAD` через скилы `code-review` и `security-review` (соблюдение Конституции `P1–P15`, покрытие тестами, отсутствие секретов) с генерацией отчёта или баг-репортов;
   - **авто-сверка с активным планом (`plan-drift`) и извлечение уроков:** сопоставление закоммиченных правок с задачами активного плана `plan/<slug>/`, контроль счётчиков `README.md` (`BUG-003`), починка входящих ссылок после ручного `git mv` и кристаллизация фиксов `fix(...)` в базу инцидентов/правил.

## План внедрения (для Этапа 1)

1. **Фаза 1 — Ядро `sync_file` и CLI-команда `todoc sync`:**
   - Реализовать нормализацию путей (`DATA_ROOT`-relative и CWD-relative), режим `--dirty` по `stats.json`, автобамп `updated:`, запись `before/after + ranges` в историю, сброс `parse_cache`, обновление индекса, защиту `derived_from` и выдачу компактного конверта с `guidance` (`P15`).
   - *Acceptance:* `100%` branch coverage в `tests/`; прямая правка `.md` и `.json` + `todoc sync <path>` обновляет `updated:`, историю и индекс за один вызов и ловит любые ошибки схемы/секций/ссылок.
2. **Фаза 2 — Обновление правил, скилов и стартовых промптов всех типов:**
   - Обновить `AGENTS.md`, `SKILL.md`, `demo/skill/SKILL.md`, `demo/notes/agent-contract.md`, процессные скилы `demo/skills/process/*`, промпты `prompts/{create,edit}.md` в `demo/.todoc/` и дефолтные шаблоны в `src/todoc/config.py`.
   - *Acceptance:* `todoc validate --root demo --all` = `0` диагностик; `check-config` = `0`; ни один стартовый промпт больше не принуждает агента собирать `patch.json` для обычной правки.

## Решённые вопросы (закрыты при переходе в план)

- **Хранение служебного журнала локальных правок в Git (`BUG-012`):** решено спрятать служебную папку локальной истории `**/.todoc/history/` от Git через `.gitignore` (и снять `demo/.todoc/history/journal.jsonl` с индекса Git без удаления локального файла, плюс поддержать флаг `--no-history`), чтобы частый вызов `todoc sync` не засорял `git status`.
- **Поведение при случайной ручной правке автособираемых файлов-витрин (`export`, рендеры `flow-doc`):** решено помечать автогенерируемые типы флагом `"generated": true` в `type.json` (не путая их с авторскими планами, использующими `derived_from` для контроля свежести) и останавливать `todoc sync` с понятной ошибкой `docs.derived_edited_directly` и подсказкой в `guidance`, какой исходный файл нужно править вместо копии (аварийный обход — явно через `--allow-derived`).
