# Идея: сквозная система тегов (`todoc tags`, граф связей по тегам и фильтр `--tag-in` во всех выборках)

- Тип: `idea`
- Создан: 2026-11-26
- Идентификатор: `doc:ideas/unified-tags-and-tag-graph.md`
- Статус: `captured` (идея зафиксирована, не перешла в план)

## Суть

Развить базовые front-matter теги документов ([план тегов v1](../plan/теги-документов-как-aliases-поиска--tags-updated-related-в-front-matter.md)) в **единую сквозную систему тегирования и навигации для всех объектов датасета** — документов `.md`, JSON-записей `records`, папок `.config.json` и скилов `SKILL.md`:
1. закрепить единые правила и парсинг тегов с **автоматическим построением связей в графе** (`has_tag` / виртуальные узлы `tag:<name>`);
2. добавить группу CLI **`todoc tags`** с двухшаговым агентским протоколом разметки: **запрос 1** — вывести все существующие теги системы (`todoc tags list`), чтобы выбрать подходящие и не плодить синонимы; **запрос 2** — пометить любую сущность набором тегов (`todoc tags set`);
3. прокинуть мульти-фильтр **`--tag-in "tag1|tag2|tag3"`** во все команды выборки и поиска CLI (`docs search/tree`, `records list/query`, `skills tree`, `context`).

## Проблема

1. **Теги сейчас разорваны между носителями и недоступны для записей в CLI.** В первой волне ([`doc:plan-doc-tags`](../plan/теги-документов-как-aliases-поиска--tags-updated-related-в-front-matter.md)) теги появились только во front matter `.md`-документов и в `docs search --tag <один-тег>`. У JSON-записей царит разнобой (у `document` есть `tags`, у `task` — `labels`, у многих типов поля нет вообще), у папок теги лежат отдельно в `.config.json`, а единой команды чтения/записи тегов нет.
2. **Агент слепо придумывает новые теги, плодя дубли-синонимы.** В CLI нет команды «покажи все уже существующие теги в базе». Поэтому при создании документа или задачи модель каждый раз изобретает написание с нуля (`auth` / `authn` / `авторизация`, `bug` / `bugs`, `temporal` / `bitemporal`), размывая навигацию.
3. **По тегам не строятся связи между документами и сущностями.** Документ идеи, план, JSON-задача и папка раздела могут быть помечены одним предметным тегом (например, `todocignore`), но в графе связей (`relations graph/tree`) между ними нет моста, пока кто-то вручную не пропишет десятки перекрёстных ссылок.
4. **Нет выборки по набору тегов (`OR` / пересечение) во всех CLI-командах.** В `docs search` сейчас обязателен текстовый `--query` и поддерживается только один `--tag`, а `records list`, `records query`, `docs tree` и `skills tree` вообще не умеют отбирать объекты по маске вида `tagin=x|y|z`.

## Принципы

1. **Единый носитель `tags` и единые правила гигиены для всего корпуса.** У `.md` и `SKILL.md` — `tags: [...]` во front matter; у всех JSON-записей `records` — верхнеуровневое поле `"tags": [...]` (с унификацией legacy-поля `labels` у `task` в `tags`); у папок — `"tags": [...]` в `.config.json`.
2. **Сначала посмотри словарь — потом назначай (протокол 2 запросов).** Никакого отдельного ручного файла-реестра, который рассинхронизируется с данными: живой словарь собирается из индекса командой `todoc tags list`. Модель видит существующие теги с их частотами, переиспользует каноничные и вводит новый тег только тогда, когда существующие не подходят.
3. **Тег — узел навигационного графа (`tag:<name>`), а не просто строка.** При сборке индекса теги образуют производные связи `has_tag` (по аналогии с `mentions`), связывая воедино разнородные объекты (`.md` + `.json` + папки) без ручной правки каждого соседа.
4. **Прогрессивное масштабирование словаря (порог `200` тегов — зафиксированный задел).** Пока уникальных тегов в системе `≤ 200`, первый запрос (`todoc tags list`) отдаёт весь список целиком — это детерминированно, занимает пару килобайт и даёт модели 100% обзор. На вырост (когда уникальных тегов станет `> 200`) фиксируется переход ко второй фазе: ранжированная подсказка топ-`K` наиболее близких/связанных тегов под конкретную сущность с отсечением хвоста (`truncated: true`).
5. **Не конфликтовать с `todoc tag` истории ревизий.** Команда в единственном числе `todoc tag` уже занята релизными метками на журнале истории (`journal.jsonl`), поэтому таксономические теги живут в группе множественного числа **`todoc tags`**.

## Предложение

### 1. Правила именования и валидации тегов

- **Формат одного тега:** строчная латиница, кириллица и цифры в `kebab-case`, длина `2..32` символа: `^[a-z0-9Ѐ-ӿ]+(-[a-z0-9Ѐ-ӿ]+)*$`.
- **Лимит на объект:** от `1` до `10` уникальных тегов на документ, запись или папку; дубли внутри одного объекта автоматически схлопываются при `tags set`, а при ручной правке репортуются валидатором (`tags.duplicate`, `tags.invalid_format`).
- **Семантическое правило анти-дублей (в промптах типов и скиле захвата):** использовать базовую форму понятия (единственное число для предметных концептов: `flow`, `rule`, `incident`, `timeout`), не дублировать тегом то, что уже выражено полем `status` (`done`, `open`).

### 2. Индексация тегов и построение связей в графе (`has_tag`)

При `scan_and_validate` / публикации снапшота индекса (`service.py` + `registry.py`) строится производная секция `tag_index`:
- для каждого тега `T` хранится список владельцев `{id, kind: "document"|"record"|"folder", path}`;
- в графовый движок (`query.py`: `graph_neighbors`, `build_tree`) добавляются производные рёбра типа **`has_tag`** (`via: "tag"`):
  - `todoc relations graph --root KB --from tag:bitemporal` — мгновенно возвращает все документы, планы, задачи и папки с тегом `bitemporal`;
  - `todoc relations graph --root KB --from doc:ideas/todocignore.md --via-tags` (или `todoc tags related --id ...`) — находит связанные документы и записи по пересечению тегов, ранжируя соседей по редкости общих тегов (IDF-вес: редкий предметный тег `pathspec` весит кратно больше общего тега `idea`).

### 3. Двухшаговый workflow разметки в CLI (`todoc tags`)

**Шаг 1 — Вывести все теги системы (`todoc tags list`):**

```bash
todoc tags list --root KB [--within <dir>] [--kind document|record|folder]
```

Возвращает отсортированный каталог всех тегов датасета (по убыванию частоты или алфавиту):

```json
{
  "schema_version": 1,
  "ok": true,
  "data": {
    "dataset_id": "dataset-80c70868",
    "total_tags": 84,
    "truncated": false,
    "items": [
      { "tag": "cli", "count": 19, "docs": 14, "records": 4, "folders": 1 },
      { "tag": "bitemporal", "count": 3, "docs": 2, "records": 1, "folders": 0 }
    ]
  },
  "diagnostics": [],
  "next_actions": [
    {
      "argv": ["todoc", "--root", "demo", "tags", "set", "--id", "<target_id>", "--tags", "tag1|tag2", "--apply"],
      "purpose": "Назначить выбранные теги целевой сущности"
    }
  ]
}
```

> **Зафиксированное правило масштабирования (на будущее, Фаза 2):** пока `total_tags <= 200`, `todoc tags list` всегда возвращает полный список без обрезки — модель сама выбирает релевантные теги и при необходимости добавляет новый. Когда база перешагнёт порог **`> 200` уникальных тегов**, в `todoc tags list --for <id|path>` (или `todoc tags suggest --id <id> --limit 30`) включается предварительное ранжирование всех тегов по лексическому совпадению с заголовком/текстом сущности и ко-встречаемости у соседей графа: CLI отдаёт первые `X` наиболее вероятных кандидатов, а остальные отрезает (`truncated: true`). На первом этапе реализуется полный вывод всех тегов.

**Шаг 2 — Назначить теги любой сущности (`todoc tags set`):**

```bash
# Замена или дополнение набора тегов у документа, JSON-записи или папки:
todoc tags set --root KB --id doc:ideas/todocignore.md --tags "ideas|todocignore|pathspec|scanner" --apply
todoc tags set --root KB --id task:shop-0002 --tags "checkout|payment" --mode add --apply
todoc tags set --root KB --id folder:ideas --tags "backlog|roadmap" --mode add --apply
```

- Принимает `--id` любого типа (`doc:...`, `task:...` / любой `record_id`, `folder:<rel_path>`) либо `--path <rel_path>`.
- Режимы `--mode`: `replace` (по умолчанию — установить точный набор), `add` (дописать недостающие), `remove` (снять перечисленные).
- Поддерживает канон `--preview` / `--apply` и `--if-hash`, атомарно пишет в нужный носитель (YAML front matter `.md` с бампом `updated`, JSON-объект записи или `<folder>/.config.json`), пересобирает индекс и проверяет валидность тегов за один вызов.

### 4. Сквозной фильтр по набору тегов во всех выборках CLI (`--tag-in`)

Во все поисковые и списочные команды добавляется единый фильтр по набору тегов через разделитель `|` — **`--tag-in "x|y|z"`** (и опциональный строгий `--tag-all "x|y"` для пересечения `AND`):

| Команда CLI | Поведение с `--tag-in "tag1\|tag2\|tag3"` |
|---|---|
| `todoc docs search` | `--query` становится **необязательным**, если передан `--tag-in` / `--tag`! При `--tag-in "cli\|scanner"` без `--query` возвращаются все подходящие документы, отранжированные по числу совпавших тегов из списка; с `--query` работает и фильтр, и лексическое ранжирование. |
| `todoc docs tree` | Отфильтровывает дерево папок и документов, оставляя только узлы с хотя бы одним тегом из списка (и их родительские пути). |
| `todoc records list` | Отбирает JSON-записи любого (или заданного `--type`) типа, у которых `tags` пересекается со списком `--tag-in`. |
| `todoc records query` | Поддерживает как CLI-флаг `--tag-in "a\|b"`, так и декларативный оператор в `QuerySpec`: `"tag_in": ["a", "b"]` (или `"a\|b"`). |
| `todoc skills tree` | Фильтрует дерево скилов по тегам во front matter `SKILL.md` и `.config.json` разделов. |
| `todoc context` | Собирает пакет контекста (документы + записи + соседи) по набору тегов `--tag-in` в пределах байтового `--budget`. |

## План внедрения

1. **Фаза 1 — Унификация поля `tags` у записей и индекс тегов + связи `has_tag`:**
   - Поддержать и валидировать `tags` у всех JSON-записей в `validator.py` (мигрировать `labels` → `tags` у `task` с обратной совместимостью при чтении).
   - Собрать сводный `tag_index` в снапшоте индекса и подключить виртуальные узлы `tag:<name>` и рёбра `has_tag` в `relations graph/tree`.
   - *Acceptance:* `relations graph --from tag:<name>` возвращает и `.md`, и `.json`, и `folder:*` владельцев тега; `validate --all` ловит битый формат тега в JSON так же, как в Markdown.
2. **Фаза 2 — Группа CLI `todoc tags` (`list`, `set`, `show`) — протокол 2 запросов:**
   - Реализовать `todoc tags list` (полная выдача при `≤ 200` тегов) и атомарный `todoc tags set` (`replace|add|remove`, `--preview`/`--apply`) для документов, записей и `.config.json` папок.
   - *Acceptance:* разметка документа, записи и папки за 2 вызова (`tags list` → `tags set --apply`); `updated` бампается у `.md`; история фиксирует правку.
3. **Фаза 3 — Мульти-фильтр `--tag-in` во всех выборках CLI:**
   - Добавить `--tag-in` (и опциональность `--query` при наличии тег-фильтра в `docs search`) в `docs search`, `docs tree`, `records list`, `records query` (`QuerySpec`), `skills tree` и `context`.
   - *Acceptance:* выборки по `--tag-in "a|b|c"` ранжируют объекты с большим числом совпавших тегов выше; `100%` branch coverage; `todoc validate --root demo --all` = `0`.
4. **Фаза 4 (отложенная, за порогом `> 200` уникальных тегов) — Ранжированный `tags suggest`:**
   - Автоподбор и ранжирование топ-`X` подходящих тегов под целевую сущность с обрезкой хвоста (`truncated: true`), чтобы не передавать сотни тегов в окно модели.

## Открытые вопросы

- **Наследование тегов папки дочерними документами и записями при фильтрации `--tag-in`:** если папка домена (например, `ideas/todocignore/.config.json`, см. [`todoc folderize`](entity-to-folder.md)) помечена тегом `scanner`, должен ли запрос `--tag-in "scanner"` находить вложенные в эту папку задачи автоматически (с пометкой `inherited_tag: true`), или `--tag-in` проверяет только собственные теги объекта, а папочные теги дают лишь буст ранжирования?
- **Судьба поля `labels` в типе записи `task`:** сделать полную миграцию `labels` → `tags` в схеме `task`, или временно оставить `labels` алиасом при чтении? Полная унификация в `tags` чище (одно имя поля везде).
