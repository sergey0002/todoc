# Идея: справочник сущностей системы (entity catalog) и генерируемые витрины

> Источник: обсуждение 2026-11-26 (пользователь) + ресёрч
> [decision-tree-formats](../.research/decision-tree-formats.md) (doc:decision-tree-formats)
> и план [документирование-софта](../plan/документирование-софта--типовой-профиль---типы--стартовые-промпты--скилы.md)
> (doc:plan-softdoc-profile). Идея — кандидат в план после softdoc.

## Суть

Три сдвига одной архитектуры, все на существующих механиках движка
(JSON Schema для записей, relation_types, `derived_from`/`stale`, `--output`):

1. **Истина переезжает в записи.** Флоу = записи `flow`/`rule` (entity-типы
   из Задачи 2 softdoc) со структурированным деревом решений (nodes/edges,
   props развилок `mode: ask-user|auto` — см. ресёрч §4). Markdown-флоу-док
   — **не истина, а витрина**: CLI генерирует её на лету (`docs flow render`)
   и отдаёт агенту в выводе; для Obsidian её можно материализовать в файл,
   который объявляет fm `derived_from` на записи — дрейф ловит существующий
   `todoc stale` (staleness.py поддерживает fm-зависимости и якоря фрагментов).
2. **Глоссарий становится справочником сущностей.** Новый entity_type `term`
   (JSON-записи): не только смысл (definition), но и **данные** —
   `term_type` (actor/role/system/component/event/rule/field/external),
   `aliases[]`, `responsible`, `artifacts[]` ({path, role} — указатели на файлы
   **полями, не рёбрами**: файлы не имеют record_id, ребро на них повиснет —
   `relation.dangling_target`). md-запись глоссария (1 термин = 1 файл, как
   сейчас) — человеческая витрина термина, указатель на неё — поле `source_path`.
3. **Связи сущностей — через граф записей.** Новые relation_types (данные,
   без правок движка): `uses_term` (source: flow/rule/incident/release/change;
   target: term — ребро хранит **потребитель**, не термин), `part_of`
   (term→term — иерархия справочника). Граф двунаправленный
   (`relations graph --from term:operator` покажет все флоу/правила, где
   термин используется).

## Проблема

1. Истина флоу размазана: таблица решений в md, examples в записях правил —
   два носителя, ручная синхронизация; агент не может «пройти» дерево.
2. Глоссарий — словарь (только смысл): ни данных об акторах/системах, ни
   машинных связей; флоу не может сослаться на термин ребром (записей нет).
3. Связи уровня «раздел md ↔ сущность» недостижимы: рёбра целятся в
   record_id, а не в файлы/разделы; спец-разметка в md не валидируется
   движком и создаст ложное чувство машинности.

## Предложение

### 1. entity_type `term`

```json
{
  "record_id": "term:operator",
  "entity_type": "term",
  "title": "Оператор",
  "term_type": "role",
  "definition": "Сотрудник поддержки, обрабатывающий заказы вручную",
  "aliases": ["кассир", "оператор КЦ"],
  "responsible": "команда поддержки",
  "source_path": "glossary/operator.md",
  "artifacts": [{"path": "src/orders/handoff.py", "role": "код эскалации к оператору"}],
  "relations": [{"type_id": "part_of", "target": {"kind": "record", "id": "term:support"}}]
}
```

Схема: `record_id ^term:[a-z0-9][a-z0-9-]*$`, required title/term_type/definition,
enum term_type, `artifacts` — array of {path, role} (path — строка, не проверяется
на существование: репо кода вне KB, P1 «файлы — истина» соблюдён: KB ссылается,
не копирует). Валидация — существующий `record.schema_violation` сегодня.

### 2. relation_types `uses_term` и `part_of`

- `uses_term`: source [flow, rule, incident, release, change, api-endpoint,
  domain-event], target [term]. Ребро пишет потребитель (флоу/правило),
  термин не редактируется при каждом новом использовании.
- `part_of`: term→term (иерархия: `term:operator` ∈ `term:support`).
- Существующие `references`/`describes` остаются для документных связей;
  между терминами и документами — поле `source_path` + (опционально, при
  закрытии долга самоописания) ребро на document-запись.

### 3. Генерируемые витрины (flow-doc, glossary-entries)

- `docs flow render --id flow:X` → в выводе: state machine, таблица решений
  (с колонкой «Режим»), mermaid flowchart, lineage, ссылки на термины
  (`uses_term`) — агент получает витрину одним вызовом без файла.
- `--write flows/order-placement.md` — материализация для Obsidian: файл
  помечается заголовком «сгенерировано, не править руками» и fm
  `derived_from: [flow:order-placement]`; `todoc stale` показывает дрейф,
  `docs flow render --write` обновляет. До появления команды рендера в коде
  движка (эта идея — первый кандидат) витрину пишет агент по промпту типа,
  честно помечая её снапшотом.
- md-записи глоссария аналогично: термины-записи — истина, md — витрина
  (генерация позже той же командой, семейство `--render`).

### 4. Связь «раздел md ↔ термин» — без спец-разметки

Решение: **разметку не вводим**. Вместо неё:
- глоссарий уже 1 термин = 1 файл → связь файл↔сущность это поле
  `source_path` записи термина (адресация целым документом достаточна);
- для разделов больших md: в **генерируемых** витринах ссылки на термины
  ставит рендерер (данные уже в записях — в md ничего размечать не нужно);
- в рукописных md: fm `related` + `[[term:*]]`-wikilinks остаются
  человеческим слоем (Obsidian), движок их не валидирует — и честно
  не обещает (отличие от фиктивной «спец-разметки»).

### 5. Единый формат ссылок между носителями (u-graph)

Три адресуемых носителя: md-файлы (и их разделы), JSON-записи (и их фрагменты).
Один формат ссылки — hash-фрагмент; семантика типа связи остаётся на рёбрах
записей, все md-ссылки — mentions («здесь упомянут X в фрагменте Y»):

| Вид связи | md-синтаксис | из JSON-записи | Адресат |
|---|---|---|---|
| файл → файл | `[[x]]`, `[..](x.md)` | `source_path` | целый файл |
| файл → раздел md | `[[x#раздел]]`, `[..](x.md#якорь)` | — | заголовок (якорь = slug заголовка; парсер генерирует их уже сегодня, markdown.py) |
| файл → запись | `[[term:operator]]` | — | record_id |
| файл → фрагмент записи | `[[term:operator#/artifacts/0]]` | — | JSON Pointer RFC 6901 (resolve_pointer в движке уже есть: jsonfmt.py:248, `docs read --pointer`) |
| запись → файл/раздел md | — | `references` → запись-документ (`source_path`) — уже работает; фрагмент: `source_anchor`-поле (этап 2) | раздел/файл md |
| запись → запись | `relations[]` | — | record_id |
| абзац ↔ что угодно | `^block-id` | — | block-ref (этап 3) |

**Этапность:** этап 1 — якоря-разделы + entity-ссылки + pointer-фрагменты +
edge-undo (ядро); этап 2 — запись → фрагмент md (`source_anchor`, новый kind
target'а в валидаторе); этап 3 — block-refs `^block-id` (парсер + уникальность
id + индекс), когда единицы «раздел» перестанет хватать.

### 6. Edge undo: ревизии рёбер и точечный откат

Ребро — часть файла-записи, и движок уже пишет before/after-снапшоты каждой
правки: каждое ребро неявно имеет ревизии. Edge undo — интерфейс над этим,
без второй базы истории:

- `todoc records undo-relation --id flow:X --pointer /relations/2` — план:
  запись, указатель, как выглядело ребро до последней изменившей его ревизии
  (данные уже дают `log --path` + `diff REV_A REV_B`; команда собирает их в
  один ответ);
- `--apply --expected-hash` — применяет обратный дифф массива `relations`
  обычной записью: review-first сохраняется (undo — тоже правка, со своей
  ревизией и журналом);
- отказ-кейс: нужная ревизия не найдена в снапшотах (журнал чистился) →
  `history.revision_missing` + подсказка ручного edit.

### 7. Разбор, кеш и вывод (контракт для будущего плана)

- **Парсинг**: wikilink-цель = `target[#fragment]`; фрагмент — либо
  `#якорь-раздела` (md), либо `#/json/pointer` (запись). Индекс ссылок
  расширяется: `{source_file, source_line, source_fragment, target,
  target_kind: doc|record|fragment}`; в JSON самих записей менять ничего
  не нужно — md-ссылки живут в md.
- **Валидация** (новые коды, старые `markdown.link.*` не переименуются):
  `markdown.anchor_not_found` (фрагмент не совпал со slug'ами заголовков
  цели), `markdown.record_not_found` (record_id-цель вне реестра),
  `markdown.pointer_invalid` (pointer не резолвится в записи).
- **Кеш**: entity-mentions и фрагментные ссылки — часть derived-индекса
  (rebuildable, как backlinks сегодня); `index rebuild` пересобирает.
  **Записи не кешируются**: истина всегда файл записи (история — снапшоты
  журнала), индекс хранит только адреса.
- **Вывод CLI**: `docs read --id doc:x#раздел` — фрагмент в id-адресации;
  `records read --id term:operator` дополняется `mentioned_in`
  ({file, section, line} из индекса — кто и где упомянул запись; цели
  исходящих рёбер и так в `relations`); `relations graph` включает
  mention-вершины (md-файлы/фрагменты) отдельным типом узла — граф цельный.
  Фрагменты адресуются парами `{id, fragment}`, не строками-суррогатами;
  конверт — только существующие ключи.

### 8. JSON ← md: словарь на записях, адресация обратно

Записи `term` — машинная истина словаря; md-страница термина — витрина
(`source_path`). Обратный адрес записи → md-раздел: поле `source_anchor`
(якорь раздела витрины) для больших страниц; для генерируемых витрин
якоря ставит рендерер — записи не правятся руками. Сегодняшний обходной
путь (без этапа 2): запись → `references` → запись-документ (`source_path`) —
файл уже адресуем транзитивно, фрагмент добавит этап 2.

### 9. Реестр новых инструментов (что появится, по этапам)

Правило: команда добавляется, только если её нельзя собрать из существующих;
всё — review-first, без новых зависимостей, конверт `--output` сохраняется.

**Новые команды (3):**

| # | Команда | Этап | Что делает | Зависит от |
|---|---|---|---|---|
| T1 | `docs flow render --id flow:X [--write PATH] [--section table\|mermaid\|lineage\|terms]` | 1 | витрина флоу в выводе: state machine, таблица решений (с колонкой «Режим»), mermaid, lineage, термины по `uses_term`; `--write` — материализация md с fm `derived_from` (дрейф ловит существующий `stale`) | записи flow/rule + дерево (этап 0) |
| T2 | `docs flow walk --id flow:X [--at node:ID]` | 1 | навигатор дерева решений: узел = вопрос/условие, ветви с приоритетом, props развилки (`mode: ask-user\|auto`, default), пути до терминалов; без `--at` — корень | дерево в записи flow |
| T3 | `records undo-relation --id X --pointer /relations/N [--apply] [--expected-hash]` | 1 | точечный откат ребра: план из ревизий журнала (log+diff собраны в один ответ), apply — обратный дифф массива обычной записью (undo тоже ревизия) | before/after-снапшоты журнала (есть) |

**Расширения существующих команд (3):**

| # | Команда | Этап | Что добавляется |
|---|---|---|---|
| T4 | `records read --id term:X` | 1 | блок `mentioned_in`: {file, section, line} из mention-индекса — где запись упомянута в md |
| T5 | `docs read --id doc:x#раздел` | 1 | fragment в id-адресации (синоним `--section`, парсится из id) |
| T6 | `relations graph` | 1–2 | mention-вершины (md-файлы/фрагменты) отдельным типом узла — граф цельный |

**Валидатор и derived-индекс (не команды):**

| # | Инструмент | Этап |
|---|---|---|
| T7 | диагностики `markdown.anchor_not_found` / `markdown.record_not_found` / `markdown.pointer_invalid` | 1 |
| T8 | mention-индекс {source_file, line, fragment, target, target_kind} — rebuildable, пересобирается `index rebuild` | 1 |
| T9 | резолв `source_anchor` записи → раздел витрины; kind `fragment` у target'ов рёбер | 2 |
| T10 | block-ref парсер `^block-id` + уникальность id + индекс | 3 |

**Данные (без кода, этап 0):** entity_type `term`; relation_types `uses_term`,
`part_of`; расширение схемы `flow` полем `tree` (nodes/edges, props развилок
`mode`/`default_branch`/`timeout`); поле `source_anchor` (этап 2).

**Существующие механики, которые НЕ дублируются:** `stale`/`derived_from`
(дрейф витрин), `log`/`diff`/`blame` (история), CAS-хэши, JSON Pointer
resolver, slug-якоря заголовков, backlink-билдер, журнал снапшотов,
конвенция `--output`.

**Оценки объёма:** T1/T2/T10 — M (средние); T3–T9 — S (малые, по духу
BUG-005). Порядок внедрения: этап 0 (данные) → T7/T8 → T4/T5 → T3 →
T1 → T2 → T9/T6 → T10.

## Альтернативы (рассмотрены и отклонены)

- **Всё в fm md**: связи и данные термина в front matter — нет графа,
  нет JSON Schema, fm распухает.
- **Обойтись document-записями**: семантика «документ», не «сущность»;
  artifacts/term_type/aliases некуда класть без углубления схемы document.
- **Одна mega-сущность**: term/flow/file в одном типе с дискриминатором —
  схемы теряют точность, endpoints связей размываются.
- **Спец-разметка разделов в md** (`<!-- term: operator -->`): парсится
  будущим кодом, не валидируется движком сегодня — ложная машинность;
  заменено source_path + генерируемыми витринами.
- **Тип связи в тексте md** (`[[term:operator|uses_term]]`): алиас
  невалидируем, дублирует ребро записи — семантика только в записях,
  md-слой безтиповых mentions.
- **Обратная запись md-mentions в JSON-записи** («зеркалить» mentions
  рёбрами): двойная истина; mentions живут только в derived-индексе.
- **Ссылки «по индексам массива»** (`[[x.json#/0/2]]`): хрупко при
  реордеринге; разрешены только осмысленные pointer'ы по ключам,
  порядок массива не считается адресом.

## Критерии приёмки (для будущего плана)

1. `term` зарегистрирован; 10 существующих терминов глоссария перенесены в
   записи (md остаются витринами); validate = 0.
2. `uses_term`/`part_of` в реестре; пилотный флоу (softdoc З5) ссылается
   `uses_term` на `term:operator`; `relations graph --from term:operator`
   показывает флоу и правила.
3. `docs flow render` выдаёт таблицу+mermaid+Режим+термины; `--write`
   материализует с `derived_from`; `stale` ловит дрейф после правки записи.
4. Справочник читается агентом: `records list --type term`, `records read
   --id term:X`, граф — без новых команд.
5. Этап 1: `[[term:operator]]` и `[[term:operator#/artifacts/0]]`
   валидируются (битые дают record_not_found/pointer_invalid);
   `[[x#раздел]]` валидируется по slug'ам заголовков (anchor_not_found);
   `records undo-relation` показывает прежнее ребро из ревизий, `--apply`
   восстанавливает (validate = 0, новая ревизия в журнале);
   `records read` отдаёт `mentioned_in`.
6. Этап 2: `source_anchor` у записи резолвится в раздел витрины,
   `relations graph` показывает mention-вершины фрагментов.
7. Инструменты реестра §9: T1 `docs flow render` выдаёт все 4 артефакта
   и колонку «Режим» пилотного флоу, `--write` материализует и `stale`
   ловит дрейф после правки записи; T2 `flow walk` проходит каждый путь
   пилота до терминала; T3 `undo-relation` восстанавливает ребро из
   ревизии (validate = 0, новая ревизия в журнале); T4 `mentioned_in`
   показывает упоминания в витринах и планах.

## Вне скоупа

- Автолинкинг терминов в произвольных текстах (NLP-задача).
- Рендер графов в изображения (mermaid-текст достаточен).
- Правки валидатора под artifacts-пути (репо кода вне KB).
