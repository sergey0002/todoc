# Идея: `todoc docs move` — транзакционный перенос и переименование документа

- Тип: `idea`
- Создан: 2026-11-26
- Идентификатор: `doc:ideas/docs-move.md`
- Статус: `captured` (идея зафиксирована, не перешла в план)

## Суть

Добавить CLI-команду **`todoc docs move`** (и алиас `mv`), которая **одной транзакционной операцией** переносит или переименовывает документ внутри `DATA_ROOT`, автоматически пересчитывает все входящие и исходящие ссылки, wikilinks, типизированные связи JSON-записей, якоря `derived_from`, путевые поля и метаданные, пересобирает индекс и прогоняет валидацию. В ответ команда выдаёт компактный стандартный JSON-конверт (`ok: true` со счётчиками правок либо `ok: false` с детальными `diagnostics[]` и полным откатом без следов на диске), экономя контекст агента в десятки раз.

## Проблема

1. **В CLI нет механизма переноса и переименования.** Сейчас в группе `todoc docs` есть только `new`, `read`, `edit`, `status`, `search`, `tree`, `suggest`, `links`, `flow` (create-only + построчные патчи). Единственное физическое перемещение в коде — узкий `source.rename(target)` в `changes.py` при архивации change-папки, не трогающий граф ссылок датасета.
2. **Огромный перерасход токенов и вызовов при ручном переносе.** Чтобы перенести заметку из `inbox/` в профильную папку (сценарий разбора входящих) или переименовать legacy-файл с кириллическим именем ([BUG-006](../bugs/bug-006--docs-new-создаёт-кириллические-имена-файлов-из-кириллического-заголовка.md)) в английский `kebab-case`, агенту приходится вручную искать все упоминания, пересчитывать относительные пути `../`, готовить десятки JSON-патчей `docs edit` для `HOME.md`, планов, карточек записей `records/documents/*.json` и `derived_from`, пересобирать индекс и запускать `validate --all`.
3. **Хрупкость многослойных связей `todoc`.** Документ в `todoc` связан с остальной базой не одной Markdown-ссылкой, а сразу восемью контурами: исходящие `[text](../path#anchor)` внутри него самого, входящие относительные ссылки из других `.md`, wikilinks `[[stem]]` и `related` во front matter, `document_id` вида `doc:<path>`, рёбра `relations[].target.id` и поля `source_path` в JSON-записях, якоря `derived_from` (`path#fragment@sha256:…`), папочные правила `dir_rules` / теги и журнал истории. Пропуск хотя бы одного контура ломает `validate --all` или оставляет скрытый дрейф ([BUG-011](../bugs/bug-011-dreyf-derived-from-pri-smene-statusa-tela-ishodnika-trebuet-ruchnogo-re-ankoringa.md)).
4. **Риск полуперенесённого состояния.** При ручной серии правок сбой на 5-м файле из 10 оставляет датасет в битом состоянии с разорванными ссылками.

## Принципы

1. **Атомарность «всё или ничего» (All-or-Nothing).** Все новые версии затрагиваемых файлов собираются и валидируются до коммита на диск. Если целевое состояние порождает хотя бы одну ошибку схемы, типа, ссылки или конфликта хеша — на диске не меняется ни один байт, возвращается `ok: false` с диагностиками.
2. **Review-first по канону CLI (`--preview` → `--apply`).** Без `--apply` команда работает как сухой прогон: возвращает компактную сводку всех предстоящих переписываний и результат предвалидации без модификации файлов и истории.
3. **Экономия контекста агента (Bounded Envelope).** Никаких многокилобайтных диффов всех затронутых файлов в дефолтном ответе: стандартный JSON-конверт `schema_version: 1` возвращает короткие счётчики и список затронутых путей (полный построчный дифф отдаётся только по явному `--verbose` / в `--preview`).
4. **Правка ссылок строго по AST/прозе, а не слепым `replace`.** Ссылки внутри fenced-блоков кода (```` ``` ```` / `~~~`) и inline-кода (`` `...` ``) никогда не переписываются (согласовано с парсером `markdown.py` и [BUG-007](../bugs/bug-007--linkcheck-command-missing.md)).
5. **Стабильность явной идентичности ([Конституция, FR-1](../plan/constitution.md)).** Если у документа задан собственный смысловой `id` во front matter (`id: doc:home`, `id: doc:constitution`), он не меняется при переезде файла. Если же `id` имел автогенерированную путевую форму `doc:<old_rel_path>`, он синхронно переназначается вместе со всеми ссылающимися `relations`.
6. **Единое событие в истории.** Вся пачка правок (перенос файла + обновление ссылок в `N` документах и `K` записях) записывается в `history/journal.jsonl` под одним `change_id` (`kind: "move"`), чтобы `todoc revert` мог откатить перенос целиком.

## Предложение

### 1. Контракт команды CLI

```bash
# Предпросмотр переноса по id или текущему пути (по умолчанию --preview):
todoc docs move --root KB --id doc:inbox/draft.md --to notes/caching-strategy.md

# Перенос в существующую папку с сохранением имени файла (notes/draft.md):
todoc docs move --root KB --from inbox/draft.md --to notes/ --apply --if-hash sha256:...
```

- Вход: `(--id <doc_id> | --from <rel_path>)` + `--to <rel_path_or_dir>`.
- Опции: `--preview` (дефолт) / `--apply`, `--if-hash <sha256>` (оптимистическая блокировка исходника), `--keep-id` (оставить старый `id` во front matter даже для путевого `doc:<old_path>`), `--pin-type` (зафиксировать текущий `doc_type` во front matter, если он выводился из правила старой папки), `--output json|table|markdown`.
- Коды возврата по стандарту CLI `todoc`: `0` (`ok: true`), `2` (`EXIT_USAGE`), `3` (`EXIT_VALIDATION` — нарушение схемы/типа/ссылок после симуляции переноса), `4` (`EXIT_CONFLICT` — цель уже существует или `hash_mismatch`).

### 2. Полная матрица автокоррекции («всех связей внутри всех и всего»)

| Контур | Что проверяется и переписывается автоматически |
|---|---|
| **1. Исходящие ссылки внутри переносимого `.md`** | Все локальные `[text](rel/target.md#anchor)` и изображения `![alt](../assets/img.png)` вне код-блоков пересчитываются через `relpath` относительно новой папки назначения с сохранением `#anchor` и title-атрибута. |
| **2. Входящие относительные ссылки во всех `.md` датасета** | Во всех документах корпуса (`HOME.md`, MOC, планы, отчёты, гайды, `SKILL.md`) ссылки, резолвящиеся в `old_path`, переписываются на новый относительный путь от папки каждого документа-источника с сохранением `#anchor`. |
| **3. Wikilinks `[[...]]` и поле `related` во front matter** | При смене имени файла (`old-stem` → `new-stem`) обновляются `[[old-stem]]`, `[[old-stem#anchor]]`, `[[old-stem\|alias]]` в тексте и элементы `related: ["[[old-stem]]"]` во front matter. Если имя сохранилось, но в другой папке уже есть тёзка, wikilinks квалифицируются путём (`[[new-dir/stem]]`), предотвращая `markdown.link.ambiguous`. |
| **4. `document_id` и рёбра `relations` в JSON-записях** | Смысловой `id` (`doc:home`) не трогается. Путевой `id: doc:<old_path>` (по умолчанию без `--keep-id`) заменяется на `doc:<new_path>` во front matter и синхронно переписывается во всех `relations[].target.id` и `source_id` в `records/**/*.json`. |
| **5. Путевые поля JSON-записей (`source_path` и др.)** | В записях карточек документов (`records/documents/*.json`, поле `source_path`) и любых типизированных записях со строковыми полями пути к документу старый `rel_path` заменяется на новый. |
| **6. Якоря свежести `derived_from` (`staleness.py`)** | Во front matter зависимых `.md` и в JSON-записях якоря `old/path.md[#fragment]@sha256:…` переводятся на `new/path.md[#fragment]@sha256:…`. Если хеш самого переносимого файла изменился **только** из-за пересчёта его собственных исходящих ссылок (семантический текст секций не менялся), whole-file хеш `@sha256:…` автоматически ре-анкорится без ложной тревоги `todoc stale`. |
| **7. Правила целевой папки, `doc_type`, `tags`, `updated`** | Проверяется `resolve_type` для нового пути по `directory-rules.json` / `document-rules.json`. Если в новой папке документ обязан соответствовать типу (например, перенос в `ideas/` требует секций `Суть`/`Проблема`/`Предложение`), структура проверяется до записи. Папочный тег в `tags` (конвенция `папка + тип + тематика`) заменяется со старой папки на новую; `updated` бампается у перенесённого файла. |
| **8. Конфиги, `.todocignore`, стейт, индекс и гейт целостности** | Проверяется, что цель внутри `DATA_ROOT`, не попадает в `.todoc/` и не скрыта правилами [`.todocignore`](todocignore.md) (`move.target_ignored`). Обновляются пути в открытых `changes/*/change.json` и указателях `state.json` (при наличии). После атомарной записи пересобирается индекс (`ensure_index` / `publish` с пересчётом `mentions`) и запускается встроенная проверка `validate` + `links` на весь датасет. |

## План внедрения

1. **Фаза 1 — Планировщик графа переноса (`src/todoc/application/move.py`, in-memory):**
   - Построение `MovePlan` без записи на диск: расчёт нового пути, проверка containment / коллизий / `.todocignore`, AST-переписывание исходящих и входящих Markdown-ссылок и wikilinks вне код-блоков, пересчёт `id`, `records`, `derived_from` и `tags`.
   - Предвалидация виртуального состояния через `validate_dataset` + `validate_relations` в памяти.
   - *Acceptance:* unit-тесты на перенос вверх/вниз по глубине папок, переименование файла, сохранение `#anchor`, неприкосновенность ссылок внутри ```` ``` ```` и `` `...` ``, отказ без записи при нарушении `required_sections` целевой папки.
2. **Фаза 2 — Атомарный коммиттер и интеграция с `history` + индексом:**
   - Многофайловая атомарная запись (`temp` + `os.replace` с rollback-журналом на случай ошибки ФС посередине), удаление старого пути после успешной записи нового, единая запись `kind: "move"` в `history` и немедленная публикация нового снапшота индекса.
   - *Acceptance:* инъекция `OSError` на середине коммита откатывает все уже записанные файлы к исходным байтам; `todoc revert` по ревизии возвращает файл и все ссылки обратно; `100%` branch coverage.
3. **Фаза 3 — CLI `todoc docs move` (`--preview` / `--apply`) и проверка на реальном датасете:**
   - Подключение команды в `src/todoc/cli.py` с JSON/table/markdown выводом.
   - Полевое испытание: переименование кириллического файла из [BUG-006](../bugs/bug-006--docs-new-создаёт-кириллические-имена-файлов-из-кириллического-заголовка.md) одной командой с `0` диагностик `validate --all` и `0` битых ссылок `docs links`.

## Открытые вопросы

- **Перенос целой папки (`todoc docs move --dir <old_dir> --to <new_dir>`):** включать ли пакетный перенос поддерева папок сразу в v1 (как групповой `MovePlan` над всеми файлами внутри папки + `.config.json` + `.todocignore`), или вынести во вторую итерацию после одиночного файла?
- **Сопутствующие локальные ассеты (картинки/схемы рядом с документом):** если документ ссылается на уникальное локальное вложение `./diagram.png` в той же папке, предлагать ли флаг `--with-assets` или ограничиться корректным пересчётом относительной ссылки `../old-dir/diagram.png`?
- **Поведение для путевого `id: doc:<old_path>` по умолчанию:** переназначать `id` в `doc:<new_path>` (с автоправкой всех `relations` в `records/`), чтобы `id` не врал о текущем пути, или наоборот делать `--keep-id` дефолтом ради внешней неизменности ID?
- **Нужен ли симметричный `todoc records move`** для физического переноса JSON-записей (например, при реорганизации подпапок `records/`), учитывая, что на записи ссылаются по `record_id`, но `derived_from` может указывать на путь `.json`?
