# Создание: `bug-report`

Баг-репорт — отчёт о дефекте или недочёте, найденном при эксплуатации системы
(движок, CLI, демо-датасет, типы, документация). Один документ = один баг.
Репорт пишется для исполнителя без контекста сессии: тот должен суметь
воспроизвести, понять ожидание и проверить фикс, не спрашивая никого.

## Когда создавать

- Команда CLI дала результат, противоречащий документации, контракту или ожиданию.
- Данные/типы/правила датасета ведут себя не так, как описано.
- Недочёт: работает, но удивляет — молчаливое усечение, счётчики врут,
  флаг принимается и игнорируется, обходной путь заставляет выйти из CLI.
- **Фрикция агента — тоже баг**: задача потребовала повторных вызовов,
  перечитываний, обходного пути или вышла дороже по токенам, чем прямое
  взаимодействие с файлами без CLI. Система обязана быть дешевле прямого
  доступа; каждый такой эпизод фиксируется, чтобы анализировать и улучшать
  систему (что фильтруется по `agent_impact`).

## Как создавать

1. **Дедуп — поиск ПЕРЕД записью, всегда.** Два запроса:

   ```bash
   todoc docs search --root KB --type bug-report --query "<симптом>" --limit 10
   todoc docs search --root KB --type bug-report --query "<компонент>" --limit 10
   ```

   Найден тот же дефект (компонент + корневая причина совпадают) — **не создавай
   новый**: сослайся на существующий `BUG-NNN` в своей работе; новые
   доказательства — уточнением в его «Заметки» с датой (задним числом нельзя).
   Если новый репорт уже создан до проверки — не удаляй (репорты не удаляются):
   поставь `status: duplicate` и в «Заметки» укажи основной репорт.
   Не создал — в «Заметки» нового репорта первой строкой зафиксируй поиск:
   `Поиск перед созданием (YYYY-MM-DD): --type bug-report --query "…" — совпадений нет.`
2. Номер: продолжи нумерацию папки `bugs/` (BUG-001, BUG-002, …).
3. Скелет:

   ```bash
   todoc docs new --apply --root KB --type bug-report --title "BUG-NNN: <суть>" --dir bugs
   ```

4. Заполни все секции шаблона; `status` и `severity` — во front matter.
5. Проверка: `todoc docs read --root KB --id doc:bugs/<файл> --section "Сводка"`,
   затем `todoc validate --root KB --all` — 0 диагностик.

## Правила качества (лучшие традиции баг-репортов)

- **Воспроизводимость**: шаги с точными командами и ключевым выводом каждой.
  Не воспроизводится — зафиксируй условия и частоту честно.
- **Ожидание со ссылкой**: на что опираешься — README, docs/state, конституция,
  код `файл:строка`. «Должно работать правильно» — не ожидание.
- **Evidence, не воспоминания**: выводы CLI, ссылки на файлы и документы;
  ничего «из головы».
- **Один баг = один репорт**: группа связанных — отдельные репорты + «Заметки»
  со ссылками друг на друга.
- **Заголовок**: `BUG-NNN: <суть>` — суть в одной строке, без «проблема с…».
- **Severity честно**: critical — данные/безопасность; major — неверные
  результаты или обход системы; minor — неудобство; docs — только документация.

## Классификация влияния на агента (`agent_impact`)

Заполняется всегда, у функционального дефекта без агентских последствий —
`none`:

| Значение | Когда ставить |
|---|---|
| `friction` | эпизод потребовал повторных вызовов CLI, перечитываний, обращения к коду/документации «в сторону» или обходного пути |
| `token_overrun` | эпизод стоил агенту заметно больше токенов, чем прямое взаимодействие с файлами без CLI (серия вызовов + перечитывания против одного read/write) |

Значения можно комбинировать списком: `agent_impact: [friction, token_overrun]`.
При `token_overrun` добавь `tokens_extra_est` (приблизительное число токенов
перерасхода за один эпизод) и разложи цену в «Воздействии»: сколько вызовов,
что перечитывалось, чем был прямой путь. Эти поля — данные для последующего
анализа экономики системы, а не формальность.

## Фильтрация репортов

```bash
# Вся фрикция агента
todoc docs search --root KB --type bug-report --query "agent_impact friction" --limit 20
# Перерасход токенов
todoc docs search --root KB --type bug-report --query "agent_impact token_overrun" --limit 20
# Всё по компоненту
todoc docs search --root KB --type bug-report --query "component engine" --limit 20
```

Поиск матчит полный текст файла, включая front matter, — значение атрибута
в шапке попадает в выдачу. Для программного анализа — `--output json`.

## Запрещённые заглушки

- «Иногда падает» без условий и шагов.
- «Работает неправильно» без ожидания и факта.
- Пустые секции, «смотри выше», evidence без команды и вывода.
- Предложение по исправлению вида «починить баг» без места и способа проверки.

## Жизненный цикл

- `status: open → triaged → in_progress → fixed | wontfix | duplicate`;
  `fixed/wontfix` — только после явного подтверждения, с датой и коммитом
  в «Заметках». Репорт не удаляется и не переписывается задним числом.
- Набор статусов — конвенция; полевая валидация придёт с allowed_statuses
  (план жизненного цикла).

## Самопроверка перед сохранением

1. Пройди по своим шагам воспроизведения заново — команды дают заявленный вывод?
2. Каждое утверждение имеет доказательство в «Доказательствах»?
3. Убрал все заглушки? Секции не ссылаются друг на друга вместо содержания?

Формат собран из практик качественных репортов: воспроизводимость и минимальный
пример (как в отчётах дефектов популярных проектов), разделение ожидание/факт,
evidence-first и честный severity — см. `docs/state/06-validation-and-diagnostics.md`
(философия точных локаций) и шаблон `template.md`.

## Именование файла

Заголовок документа — на русском и живёт в метаданных: поле `title` во front
matter (md) или поле `title` записи (json). Имя файла — на английском
(латиница, kebab-case); заголовок и имя файла независимы. При кириллическом
заголовке создавай документ с явным путём:
`todoc docs new --apply --path <dir>/<english-slug>.md` (слаг из заголовка наследует
кириллицу — BUG-006). Поле `name` для заголовка не вводится: `title` — уже
стандарт, дубль = два источника истины. Существующие кириллические имена —
legacy, не размножать. Подробно: `notes/agent-contract.md` → «Именование
документов».

> **Метаданные:** `created` и `updated` во front matter ставит движок (`docs new`) — руками не заполнять. Заполни `tags` (2–8 kebab-тегов: папка + тип + тематические) и, если есть явные связи, `related`-wikilinks (`[[имя-без-.md]]`).
