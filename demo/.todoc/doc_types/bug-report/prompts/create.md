# Создание: `bug-report`

Баг-репорт — отчёт о дефекте или недочёте, найденном при эксплуатации системы
(движок, CLI, демо-датасет, типы, документация). Один документ = один баг.
Репорт пишется для исполнителя без контекста сессии: тот должен суметь
воспроизвести, понять ожидание и проверить фикс, не спрашивая никого.

## Когда создавать

- Команда CLI дала результат, противоречащий документации, контракту или ожиданию.
- Данные/типы/правила датасета ведут себя не так, как описано.
- Недочёт: работает, но удивляет — молчаливое усечение, счётчики врут,
  флаг принимается и игнорируется, обходной путь заставляет выйти из CLI.

## Как создавать

1. Дедуп: `todoc docs search --root KB --query "<ключевые слова бага>" --limit 5`
   — нет ли уже репорта; есть — дополни его `docs edit`, не плоди дубль.
2. Номер: продолжи нумерацию папки `bugs/` (BUG-001, BUG-002, …).
3. Скелет:

   ```bash
   todoc docs new --root KB --type bug-report --title "BUG-NNN: <суть>" --dir bugs
   ```

4. Заполни все секции шаблона; `status` и `severity` — во front matter.
5. Проверка: `todoc docs read --root KB --id doc:bugs/<файл> --section "Сводка"`,
   затем `todoc validate --root KB --all` — 0 диагностик.

## Правила качества (лучшие традиции баг-репортов)

- **Воспроизводимость**: шаги с точными командами и ключевым выводом каждой.
  Не воспроизводится — зафиксируй условия и частоту честно.
- **Ожидание со ссылкой**: на что опираешься — README, docs/state, конституция,
  код `файл:строка`. «Должно работать правильно» — не ожидание.
- **Evidence, не воспоминания**: выводы CLI, ссылки на файлы и документы;
  ничего «из головы».
- **Один баг = один репорт**: группа связанных — отдельные репорты + «Заметки»
  со ссылками друг на друга.
- **Заголовок**: `BUG-NNN: <суть>` — суть в одной строке, без «проблема с…».
- **Severity честно**: critical — данные/безопасность; major — неверные
  результаты или обход системы; minor — неудобство; docs — только документация.

## Запрещённые заглушки

- «Иногда падает» без условий и шагов.
- «Работает неправильно» без ожидания и факта.
- Пустые секции, «смотри выше», evidence без команды и вывода.
- Предложение по исправлению вида «починить баг» без места и способа проверки.

## Жизненный цикл

- `status: open → triaged → in_progress → fixed | wontfix | duplicate`;
  `fixed/wontfix` — только после явного подтверждения, с датой и коммитом
  в «Заметках». Репорт не удаляется и не переписывается задним числом.
- Набор статусов — конвенция; полевая валидация придёт с allowed_statuses
  (план жизненного цикла).

## Самопроверка перед сохранением

1. Пройди по своим шагам воспроизведения заново — команды дают заявленный вывод?
2. Каждое утверждение имеет доказательство в «Доказательствах»?
3. Убрал все заглушки? Секции не ссылаются друг на друга вместо содержания?

Формат собран из практик качественных репортов: воспроизводимость и минимальный
пример (как в отчётах дефектов популярных проектов), разделение ожидание/факт,
evidence-first и честный severity — см. `docs/state/06-validation-and-diagnostics.md`
(философия точных локаций) и шаблон `template.md`.
