# Документирование софта: типовой профиль — типы, стартовые промпты, скилы — план реализации

> **Исполнителю (агенту):** план самодостаточен — читай его, а не историю сессии.
> Работай по задачам сверху вниз; шаги отмечаются чекбоксами (`- [ ]`) в том же
> коммите, который делает шаг. Начинай всегда с первого неотмеченного.

**Цель:** ввести в демо-датасет типовой профиль документирования софта (Фаза 1 идеи
[documentation-system](../ideas/documentation-system.md)) **двумя волнами**:
волна 1 — 4 dir_types, 4 doc_types с шаблонами и CRUD-промптами, 6 entity_types
со JSON Schema, 4 relation_types, 5 скилов документирования и приёмочный
флоу-документ «оформление заказа»; волна 2 (задачи 8–10, из веб-ресерча
25.11.2026) — контракты и операции: `api-contract`, `runbook`, `postmortem` +
сущности `api-endpoint`, `domain-event`, `bounded-context`, `slo`, `dependency`
и связь `depends_on`. Всё проверяется существующим валидатором без единой правки
кода движка.
**Спека:** [ideas/documentation-system.md](../ideas/documentation-system.md)
(разделы «Какие типы добавить», «Флоу-документ: эталон», «Task report», «Практики
оформления спек») + [ideas/skills-engine.md](../ideas/skills-engine.md) (формат
Agent Skills, SKILL.md) + решения по совместимости с движком из раздела 4 +
веб-ресерч 25.11.2026 по типам инженерной документации и агентным практикам
(раздел 4, таблица «Источники веб-ресерча»).
**Стек:** только JSON-дескрипторы, JSON Schema 2020-12, Markdown; click-CLI движка
как исполнитель; без новых зависимостей, без изменений `src/`.

## 2. Вне скоупа

- Фазы 2–7 идеи documentation-system: collector по git, Jira-фетчер, fixture-тесты
  правил, релизный цикл, task-report-генерация, импорт/экспорт OpenSpec.
- Код движка `src/`: `skills tree`, `docs suggest`, проверка `allowed_statuses`,
  проверка endpoints у связей, `folder.config` — всё это отдельные планы
  (skills-engine, folder-config, скилы-взаимодействия).
- Ребро `implements` и статусы md-документов (`allowed_statuses`) — вводит план
  «скилы-взаимодействия»; здесь не дублируются.
- Записи-документы для прочих 19 документов демо без записей — известный долг
  самоописания (`references/state/16-leftovers-report.md`), закрывается отдельно.
- Сохранённые запросы `.todoc/queries/` под новые типы — после первого реального
  использования, не в этом плане.
- **Рассмотрено в ресерче и отклонено** (сущности/типы из веб-обзоров инженерной
  документации): `troubleshooting` (структура symptom-to-fix покрывается
  runbook + rule.examples), onboarding-гайд (покрывается существующим doc_type
  `guide`), changelog (покрывается `release-note`), RFC/design-doc (покрывается
  связкой `change` + `spec-doc` + `adr`), test-plan/SRS (вне ядра базы знаний,
  живут в репо кода), feature-flags и environments-register (эксплуатационное
  состояние, не знание; против P1 «файлы — истина»: состояние флага живёт в
  конфиге сервиса, не в KB), RFC 2119-словарь как отдельный тип (нотация SHALL
  уже в spec-doc).

## 3. Глобальные ограничения

- **Только данные датасета**: `demo/.todoc/**`, папки и записи демо. Файлы `src/`
  и тесты не трогаются ни в одной задаче.
- **Формат дескрипторов строгий**: только поля, разрешённые движку
  (`src/todoc/typing_system/descriptors.py`); неизвестное поле =
  `config.unknown_field` и валидно не проходит. Не добавлять `allowed_statuses`
  в doc_types, пока валидатор их не читает (ждёт план жизненного цикла).
- **Review-first**: JSON-записи — только `records create --preview` → `--apply`
  (create-only); правки существующих md — `docs edit --preview/--apply`;
  создание md — `docs new`, наполнение тела — в файл (движок умеет только
  замену строк 1:1 без вставки — ограничение `apply_edit_ops`), после чего
  обязательное чтение назад через `docs read`.
- **Версии правил append-only**: изменилось правило — новая запись
  `rule:<имя>-v<N+1>` с ребром `supersedes`; старая не редактируется.
- **Связки, не копии**: задачи Jira — снимки (`task-snapshot`), живая истина —
  в Jira; `origin.task` — поле, не ребро.
- Каждый шаг каждой задачи проверяется командой с ожидаемым выводом; после
  каждой задачи — `todoc validate --root demo --all` = 0 диагностик и коммит.

## 4. Архитектура и файловая карта

Подход: профиль — это **данные** (дескрипторы + шаблоны + промпты) поверх
существующего резолвера типов; семантика работы — **скилы** (формат Agent Skills,
папки в `demo/skill/`), которые вызывают **типовые промпты** (`todoc types prompt`)
и команды CLI. Двухслойная модель отвечает на gap конкурентного анализа (§10.1,
C20): «type-directed capture через Skill» — скил ведёт процесс, тип и схема
принуждают структуру, валидатор замыкает контур.

**Решения (приняты по результатам ресерча 25.11.2026, не открытые вопросы):**

- **D1. `change` — движок-совместимый.** У движка уже есть жизненный цикл
  изменений (`application/changes.py`): запись `changes/<slug>/change.json`
  со статусами `STATUS_FLOW = (proposed, in_progress, blocked, applied,
  archived, reverted)`, полями `created_at/applied_at/artifacts/baseline` и
  ребром `blocked_by`. Схема `change` в демо = надмножество этого контракта
  (enum статусов движка, те же поля, плюс опциональный `requirements_delta`
  из идеи — списки SHALL `added/modified/removed` для OpenSpec-интеропа).
  Пилот создаётся командой `todoc change open`, а не `records create` — это
  доказывает совместимость.
- **D2. Статусы md-типов — отложены.** `allowed_statuses` в `type.json`
  сейчас дал бы `config.unknown_field`, а валидатор это поле ещё не проверяет.
  В схемах entity_types статусы легальны сразу (enum в JSON Schema проверяется
  движком сегодня: `record.schema_violation`).
- **D3. Папка движка `changes/` — типизирована.** `change open` создаёт рядом с
  `change.json` файлы `proposal.md`/`tasks.md` с `doc_type: note`; без правила
  они получают `doc_type: unknown` (открытый дефект P1-14). Добавляются:
  dir_type `changes`, правило каталога и fm-правило для `note`.
- **D4. Endpoints у связей декларируются честно.** Валидатор проверяет
  `relation.unknown_type` и `relation.dangling_target`, но не endpoints;
  в описаниях связей пишем «смысловой контракт», не «enforced».
- **D5. `release-note` — по front matter.** Отдельной папки в идее нет; живёт в
  `reports/`, назначается fm-правилом приоритета 200 (побеждает glob папки).
- **D6. Скилы — в `demo/skill/<имя>/SKILL.md`**, по конвенции плана
  «скилы-взаимодействия» (не `skills/`-хранилище из идеи skills-engine — оно
  появится с CLI-командой). Front matter несёт `name` (= имени папки, lowercase-
  дефисы, ≤64) и `description` ≤1024 «что + когда» — стандарт Agent Skills.
- **D7. Счётчики — от факта.** `demo/README.md` уже врёт (15 dir_types при 17);
  критерии считают приращения, финальные числа берутся из `types list`.
- **D8. Контракты — связками, не копиями.** OpenAPI/AsyncAPI-файлы остаются в
  репо сервиса (docs-as-code: правка контракта в том же PR, что и код, lint в
  CI); в KB живёт doc `api-contract` с человекочитаемыми разделами и полями
  `spec_url`/`spec_format` (openapi|asyncapi) + записи `api-endpoint` для
  запросимой карты операций. Машинный YAML/JSON-файл в датасет не кладём:
  JSON без `record_id` индексируется документом с `doc_type: unknown`
  (следствие открытых P1-9/P1-14), а копия протухла бы. Полные машинные схемы
  агенты читают по `spec_url` из источника.
- **D9. Свежесть runbook — обязательным полем.** SRE-практика «runbook,
  который никто не проверял, — черновик»: template и required-поле front matter
  `last_verified` (дата) + секция «Проверка» с точной командой и ожидаемым
  выводом; движковая механика `stale`/`derived_from` подключается позже
  (задача вне этого плана), пока поле — конвенция и данные для неё.
- **D10. Postmortem без виноватых, инцидент — запись.** Блеймлесс-шаблон
  (Summary/Impact/Timeline UTC/Contributing factors — системные, не персональные/
  What went well/Action items owner+due); root cause в файле `postmortem`,
  машиночитаемый итог — запись `incident` (уже в волне 1) с ребром `fixes`
  от release. Документ — «почему», запись — «что», связка `references`.

**Волна 2 — контракты и операции (из веб-ресерча 25.11.2026):**

| Каталог | type_id | Назначение | Ключевые ограничения |
|---|---|---|---|
| dir_type | `contracts` | API-контракты и карты эндпоинтов | — |
| dir_type | `ops` | runbook и postmortem | — |
| doc_type | `api-contract` | человекочитаемый контракт API поверх OpenAPI/AsyncAPI из репо сервиса | required_sections: «Обзор», «Аутентификация», «Операции», «Ошибки», «Примеры»; front matter: `spec_url`, `spec_format` |
| doc_type | `runbook` | процедура под алерт для дежурного «в 3 часа ночи» | required_sections: «Симптом», «Воздействие», «Диагностика», «Митигация», «Проверка», «Эскалация», «Не делать»; front matter: `last_verified`, `severity`, `owner` |
| doc_type | `postmortem` | блеймлесс-разбор инцидента | required_sections: «Summary», «Impact», «Timeline», «Contributing factors», «What went well», «Action items»; front matter: `severity`, `status` |
| entity_type | `api-endpoint` | операция контракта: method+path, auth, ошибки, schema | `record_id ^api-endpoint:[a-z0-9-]+:(get\|post\|put\|patch\|delete):[a-z0-9/_{}.-]+$`; required: title, method, path, auth, errors |
| entity_type | `domain-event` | факт домена в прошедшем времени (OrderPlaced) | `record_id ^event:[a-z0-9][a-z0-9-]*-v[0-9]+$`; required: title, past_tense_name, producer, payload_ref, origin; consumers — array |
| entity_type | `bounded-context` | граница модели DDD + свой язык | `record_id ^context:[a-z0-9][a-z0-9-]*$`; required: title, language (ubiquitous terms), owner |
| entity_type | `slo` | целевой уровень сервиса: SLI, цель, окно | `record_id ^slo:[a-z0-9][a-z0-9-]*$`; required: title, indicator, target, window, origin |
| entity_type | `dependency` | внешняя система/сервис/очередь, от которой зависим | `record_id ^dep:[a-z0-9][a-z0-9-]*$`; required: title, kind (service/db/api/queue/ext), criticality, origin |
| relation_type | `depends_on` | «X зависит от Y» | endpoints: source [flow, api-endpoint, bounded-context, release], target [dependency] |

`belongs_to` волны 1 расширяется по endpoints: source += `api-endpoint`,
`domain-event`; target += `bounded-context` (описание пишет это в тексте —
движок endpoints не проверяет, D4). Rule из event storming: policy = запись
`rule` (политика «когда событие → реакция»), command = поле `command` у
domain-event, actor = поле `actor` у flow. |

| entity_type | `change` | изменение: движок-контракт + OpenSpec-дельта | `record_id ^change:[a-z0-9][a-z0-9-]*$`; status enum STATUS_FLOW движка; опц. requirements_delta{added,modified,removed} |

| relation_type | `blocked_by` | зависимость изменений (пишет движок) | endpoints: source [change], target [change] |

Пути записей (path_template): `records/flows|rules|incidents|releases|tasks/{slug}.json`,
`records/endpoints|events|contexts|slos|dependencies/{slug}.json`,
`changes/{slug}/change.json`. Не путать: живые задачи — `tasks/{slug}.json`
(entity `task`), снимки Jira — `records/tasks/{slug}.json`.

**Агентные практики из веб-ресерча (вшиваются в промпты типов, не в код):**

1. **Роутер → гайд → источник-ссылки, три слоя** — наша карта: HOME.md (MOC) =
   слой-индекс (аналог llms.txt внутри датасета), скилы/промпты типов = слой
   задач, `docs read` по секциям = слой источника; каждый SKILL.md и промпт
   заканчивается указанием, что читать дальше и когда остановиться.
2. **Документы-контракты, не эссе**: правило формулируется проверяемо
   («эндпоинт возвращает `{data, error}`» — не «держи API консистентным»);
   таблица решений флоу-дока и JSON Schema сущностей — уже исполняемые аналоги.
3. **Свежесть видима**: front matter `updated`/`last_verified`; длинные
   инлайн-инструкции в контекст не собираются — progressive disclosure
   (L1 описание, L2 тело, L3 references — совпадает со скил-стандартом).
4. **Полные схемы против галлюцинаций**: у агента должны быть точные схемы
   (наши `schema.json` + `spec_url` контрактов), а не пересказ — генерация кода
   по полному контракту режет галлюцинации.
5. **Diátaxis: не смешивать режимы чтения** (tutorial / how-to / reference /
   explanation) — в промптах doc_types: template = reference-скелет,
   create-промпт = how-to, примеры = tutorial-материал.
