# Закрытие открытого бэклога багов: волны 0–4

## 1. Критерии успеха

1. Все 51 исходный Markdown-репорт классифицированы по `doc_id`; новые репорты, заведённые по задачам этого плана, учитываются отдельно и также получают решение. `open`, `triaged`, `in_progress`, отсутствующий и неожиданный статусы не считаются закрытием.
2. Каждый `fixed` опирается на проверенный сценарий исходного репорта, а не на любой отказ, пустой результат или наличие строки в справке. Для `wontfix` и `duplicate` нужны причина и ссылка на решение или канонический репорт.
3. На итоговом диффе пройдены pytest, 100% строк и ветвей `src/todoc/`, `validate` с нулём диагностик, `linkcheck` с нулём битых ссылок, проверка генерации справочника и `git diff --check`. Windows-репорты требуют отдельного Windows-прогона; `not_run` не заменяет его.
4. Канонический реестр `docs/state/11-known-issues.md` и [demo-копия](../references/state/11-known-issues.md) совпадают по статусам и целям ссылок с Markdown-репортами. `records/documents/` не входят в этот инвентарь.

## 2. Вне скоупа

- Не выполнять мастер-рефакторинг Э0–Э4 заново, не переименовывать и не удалять репорты, не переоткрывать `fixed`/`duplicate` без новой задачи. Номера 034 и 035 не уникальны: используй пути.
- Не расширять публичный CLI или JSON-контракт без теста и обновления `docs/state/03-cli-reference.md`; генерируемую `docs/state/cli.md` не править вручную.
- Задача с пометкой «решение» исполняется только до своего гейта: без записанного решения не писать код и не выставлять терминальный статус. Это не блокирует независимые задачи.
- Мутирующие пробы запускаются только в изолированных датасетах. Для проверок доступа использовать контролируемые подмены файловых операций; не запускать исторические сценарии на живом `demo`.

## 3. Глобальные ограничения

Начать с 0.0 и 0.1. Затем 0.2–0.6 и приоритетная волна 1; не задерживать её из-за решений по 0.6. Волны 2–4 можно делить на независимые PR. 2.7 завершает приёмку 2.1; 3.10 предшествует финализации маршрутов 3.7–3.8; 3.9 предшествует финальному обновлению зеркал. 3.6 имеет внешний гейт BMAD. Перед первым коммитом зафиксировать базовую ревизию, состояние рабочего дерева и список собственных файлов/фрагментов. Не использовать широкое `git add src/todoc tests` и не включать чужие правки. Коммиты и переводы в терминальные статусы требуют явного разрешения пользователя.

Команды ниже выполняются из корня репозитория в WSL. Для чтения без установки: `env PYTHONPATH=src python3 -m todoc …`. Для гейтов использовать один рабочий интерпретатор из 0.0. Для новых документов `docs new --apply`; после прямой правки существующего документа `todoc sync --root demo --apply <путь>` и обратное чтение. При закрытии сначала подтвердить сценарий и получить коммит реализации или сослаться на существующий; затем после разрешения обновить заметки, синхронизировать и сделать свежий `docs status --id <doc_id> --set <статус> --preview`. Применять согласованный план с `--if-plan-hash`, не использовать хеш предпросмотра, снятого до редактирования заметок. Реестры и статус включать в один согласованный набор правок.

Для каждого теста зафиксировать исходный симптом, точное ожидаемое наблюдение, путь теста и результат прогона. Для новой реализации сначала получить осмысленный FAIL; для уже исправленного поведения опереться на существующий предметный тест или добавить регрессию. Если `TodocError` сериализуется в `main`, проверять публичную точку входа, не сырой `CliRunner.invoke(cli, ...)`. Новые коды закрепить в guidance и тестом формата ответа.

## 4. Архитектура и файловая карта

| Волна | Результат |
|---|---|
| 0 | Рабочие гейты, инвентарь и достоверная приёмка, документационные и проверенные CLI-фиксы |
| 1 | Проверки границ датасета, целостность записи и согласование кодов выхода |
| 2 | Проверяемый запуск и честная поддержка Windows/WSL |
| 3 | Точный контракт CLI и рабочие маршруты от подсказки к команде |
| 4 | Демо, скилы и решения по необязательным изменениям |

Волна 0 затрагивает `tools/bug_acceptance.py`, CLI и документы; волна 1 — `application/{changes,staleness,registry}.py`, `service.py` и пограничные тесты; волны 2–3 — `cli.py`, `output/`, guidance и контрактные тесты; волна 4 — сканер, скилы и справку. Точные точки входа и проверки указаны в задачах ниже.

## 6. Definition of Done

- [ ] По инвентарю §0.1 каждый исходный и добавленный репорт плана имеет явный терминальный статус после разрешения пользователя. Для `fixed` записаны дата, коммит и тест; для решений записаны причины. Нет пропусков, отсутствующих статусов или неоднозначных ссылок по номеру.

Обновить зеркала после 3.9, сверить реестры по путям со статусами исходников и пройти `git diff --check`. Новые диагностики и формы ответа имеют guidance и контрактные тесты.
