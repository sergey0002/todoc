# CLI для агентной работы: постулаты руководства

## Цель, задачи и принципы

**Цель.** Задать практические критерии проектирования CLI для агентных workflows и безопасного вызова команд агентом: детерминированные операции выполняются кодом, семантическая интерпретация остаётся агенту, а вывод помогает завершить задачу без лишних вызовов и перегруза контекста. Контракт должен снижать зависимость от силы модели: ясные команды, аргументы и результаты облегчают работу даже модели с ограниченным контекстом и слабым планированием. Это снижает вероятность ошибок, но не обещает нулевых ошибок; гайд требует проверять поведение на целевых, в том числе самых слабых поддерживаемых, моделях.

**Для кого.** Для разработчиков CLI и агентных систем, а также для тех, кто настраивает модели/клиент на работу с CLI.

**Задачи документа:**
- решить, достаточно ли рассуждения агента или нужна внешняя функция; если нужна — выбрать CLI, MCP или оба интерфейса;
- определить границы команды, аргументы, валидацию, машинный формат, ошибки, лимиты и правила побочных эффектов;
- задать безопасный порядок обнаружения, запуска и проверки результата CLI агентом;
- определить, когда выводить атрибуты, дочерние сущности и необязательные `next_actions`, и как раскрывать подробности по запросу;
- оценивать CLI на полных рабочих задачах: качество, безопасность, число вызовов, latency и суммарный расход контекста.

**Основные принципы:**
1. Семантическое понимание неоднозначного запроса остаётся за агентом/пользователем; повторяемую массовую обработку, точную валидацию и побочные эффекты выполняет код с явным контрактом.
2. Команда и аргументы должны быть однозначными и проверяемыми; человекочитаемый экран не подменяет стабильный машинный интерфейс.
3. Вывод — минимально достаточный для решения и следующего шага. `next_actions` допустимы только как конкретные, ограниченные подсказки, а дочерняя сущность — когда ей нужны отдельная идентичность и работа по ID.
4. Команда из результата не исполняется автоматически; права, намерение пользователя, подтверждение опасного действия и безопасный запуск проверяются отдельно.
5. Оптимизировать нужно весь workflow, а не размер одного ответа: полезная подсказка/атрибут может экономить последующие вызовы, лишняя — расходует контекст.

**Как читать.** Часть I — проектирование CLI; часть II — безопасная работа агента с командами; часть III — оценка качества и pre-release checklist. Примеры показывают проектные контракты, а не обязательный формат для всех продуктов.

**Срез:** 24 ноября 2026 года.  
**Статус правил:** `[STD]` стандарт/техническая спецификация; `[GUIDE]` рекомендация; `[ЭВРИСТИКА]` гипотеза для оценки.

> **Граница норм:** POSIX.1-2024 обязателен для POSIX-conforming utilities, но не задаёт грамматику любого приложения. CLIG, Google, OWASP и vendor docs — руководства, не обязательный стандарт. JSON по RFC 8259 — стандарт; `--json` по умолчанию, JSON envelope ошибок и лимит размера вывода — проектные решения. [POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html) · [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) · [CLIG](https://clig.dev/)

## I. Постулаты проектирования CLI для вызова агентами

### 1. CLI — стабильный контракт, а не текстовый экран для парсинга
**Правило.** Явно документировать грамматику команды, входы, выход, коды завершения, интерактивность и побочные эффекты. Агенту должен быть доступен поддерживаемый машинный интерфейс; парсинг меняющейся human-таблицы не считается контрактом. **[GUIDE]** [CLIG: вывод](https://clig.dev/#output) · [POSIX: utility descriptions](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html#tag_1_4)

- **Удачно:** `acme tickets search --project P7 --limit 20 --json` — понятное действие, явный scope, ограниченная выдача, документированный JSON.
- **Неудачно:** `acme P7 all` — неясны объект, действие, фильтр и формат.

### 2. Назначать одну предсказуемую команду на действие; избегать неоднозначной магии
**Правило.** Использовать устойчивые названия `noun verb` или `verb noun`, одинаковые флаги для одинакового смысла, явные подкоманды. Не угадывать произвольные сокращения, не превращать неизвестную команду в скрытый catch-all. **[GUIDE]** [CLIG: subcommands](https://clig.dev/#subcommands) · [POSIX: syntax conventions](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html)

- **Удачно:** `acme project delete --project-id P7`.
- **Неудачно:** `acme P7` иногда показывает проект, а иногда удаляет его в зависимости от контекста.

### 3. Делать входы явными, типизированными по смыслу и ограниченными
**Правило.** Называть флаги по назначению; документировать формат, единицы, timezone, допустимые значения, дефолты и пределы. Для пользовательского ввода проверять данные до эффекта. Поддерживать `--` для защиты операндов, начинающихся с `-`, там, где это применимо. **[GUIDE/STD]** [CLIG: arguments and flags](https://clig.dev/#arguments-and-flags) · [POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html)

- **Удачно:** `--from 2026-11-01T00:00:00+01:00 --limit 50` (`limit` имеет документированный максимум).
- **Неудачно:** `--date 1 --limit 1000000` — неизвестны формат, timezone, смысл числа и безопасный максимум.

### 4. Разделять параметры команды и содержимое данных
**Правило.** Флаги/argv — для небольших параметров вызова; stdin и документированный `-` — для больших или потоковых данных. Не требовать временный файл, если безопасно поддерживается stdin. **[GUIDE/STD]** [CLIG: аргументы и `-`](https://clig.dev/#arguments-and-flags) · [POSIX: STDIN/OPERANDS](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html)

- **Удачно:** `cat request.json | acme import --input - --no-input --json`.
- **Неудачно:** принимать многострочный документ только через позиционный аргумент shell, затем обрезать пробелы/переносы.

### 5. Не требовать интерактивного ввода от automation
**Правило.** Prompt допустим только при TTY; предоставить `--no-input`/эквивалент и способ передать каждый необходимый параметр явно. В неинтерактивном режиме не зависать: завершаться с полезной ошибкой о недостающем флаге. **[GUIDE]** [CLIG: interactivity](https://clig.dev/#interactivity) · [Google Cloud CLI: prompting](https://docs.cloud.google.com/sdk/gcloud#prompting)

- **Удачно:** без `--project` в pipe-режиме — ненулевой exit status и сообщение «укажите `--project`».
- **Неудачно:** процесс ждёт ответа `Choose project:` в stdin, куда агент уже подал JSON.

### 6. Не передавать секреты в обычных аргументах процесса
**Правило.** Не принимать пароли/API-токены как `--password secret`: аргументы могут попасть в history, process list, логи. Предпочитать credential store, защищённый prompt, ограниченный stdin или файл с контролируемыми правами. Environment variable тоже не считать хранилищем секрета без анализа threat model. **[GUIDE]** [CLIG: secrets](https://clig.dev/#arguments-and-flags)

- **Удачно:** `acme auth login` с системным credential store или защищённым prompt; для автоматики — явно защищённый secret input.
- **Неудачно:** `acme deploy --token=...` или печать токена в verbose-логе.

### 7. Не конструировать shell-команду из текста модели/пользователя
**Правило.** Предпочитать библиотеку/API прямому запуску ОС-команды; если запуск неизбежен — фиксированная allowlist executable, передача программы и каждого аргумента отдельно через argv, проверка допустимого значения и минимальные права. Quoting не защищает от всех argument injection и неверного смысла аргументов. **[GUIDE]** [OWASP: OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html) · [Google Shell Style: quoting/arrays](https://google.github.io/styleguide/shellguide.html#quoting)

- **Удачно:** агент передаёт фиксированной программе отдельные аргументы `--query` и значение запроса через API запуска процесса.
- **Неудачно:** `sh -c` со строкой, в которую подставлен текст пользователя/результат другого tool; `eval` над этим текстом.

### 8. Зафиксировать семантику stdout, stderr и exit status
**Правило.** По умолчанию: stdout — данные/результат; stderr — диагностика, предупреждения, prompts и прогресс; `0` — успех, ненулевой код — ошибка. Числовую карту ненулевых кодов определить и сохранять как часть контракта. **[STD/GUIDE]** [POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html) · [CLIG: basics/output](https://clig.dev/#the-basics) · [Google Cloud CLI: stdout/stderr](https://docs.cloud.google.com/sdk/gcloud#use_of_stdout_and_stderr)

- **Удачно:** stdout содержит только результат; «обновлено 3 записи»/progress идут в stderr; ошибка возвращает ненулевой код.
- **Неудачно:** stdout содержит `Loading…`, таблицу и JSON вперемешку, а ошибка возвращает код `0`.

### 9. Добавлять явный машинный формат, не объявляя его универсальным default
**Правило.** Поддерживать стабильный `--json`, а при полезности — `--plain`; не заставлять агента парсить человекочитаемую таблицу. Human-first по умолчанию — рекомендация CLIG, а не стандарт: выбирать default по основному сценарию и явно документировать его. **[GUIDE]** [CLIG: output](https://clig.dev/#output) · [Google Cloud CLI: format/filter/projection](https://docs.cloud.google.com/sdk/gcloud#determining_output_structure)

- **Удачно:** `acme tickets list --json` выводит документированный JSON-контракт.
- **Неудачно:** считать, что каждая команда/версия всегда выводит JSON без флага, хотя часть команд выводит форматированную таблицу.

### 10. В машинном режиме stdout должен быть чистым и иметь единую политику ошибок
**Правило.** `--json`: один валидный JSON-текст на вызов (обычно именованный объект); не добавлять баннер, цвет, прогресс или prose в этот поток. Заранее решить, где лежит структурированная ошибка: практичный вариант — JSON envelope успеха/ошибки на stdout и exit code как независимый статус; stderr оставить для дополнительных диагностик. Это **эвристика**, а не требование POSIX/CLIG; допустима другая единая документированная политика. **[GUIDE/STD]** [CLIG: output](https://clig.dev/#output) · [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) · [Google Cloud CLI: stdout/stderr](https://docs.cloud.google.com/sdk/gcloud#use_of_stdout_and_stderr)

- **Удачно:** JSON-режим при успехе и ошибке выводит ровно один валидный JSON-объект; при ошибке exit code ненулевой.
- **Неудачно:** stdout начинается с `Error:` или progress bar и затем содержит JSON, либо одна подкоманда выдаёт ошибку в stdout, другая — только текст в stderr, без правила.

### 11. Возвращать минимум достаточных данных, но не терять смысл/полноту
**Правило.** Давать релевантные поля, стабильные IDs, единицы, timestamp/scope/source при необходимости и состояние результата. Для больших наборов — серверная фильтрация, сортировка, `--fields`, bounded `--limit`, cursor/страницы. Если выдача обрезана, явно сообщить `truncated`/число и путь продолжения; не выдавать top-N за полный результат. **[GUIDE]** [CLIG: saying just enough](https://clig.dev/#saying-just-enough) · [Google Cloud CLI: format/filter/projection](https://docs.cloud.google.com/sdk/gcloud#determining_output_structure)

- **Удачно:** `matched_count`, несколько релевантных записей, `truncated: true`, cursor/команда для продолжения.
- **Неудачно:** огромный дамп всех записей или первые 20 строк без сообщения, что всего совпадений 4 000.

### 12. Явно определить framing потоков
**Правило.** Обычный JSON — один JSON-текст; для последовательности объектов задавать framing. JSONL/NDJSON — распространённая конвенция, не формат RFC; стандартизованная альтернатива — RFC 7464 (`application/json-seq`, RS + JSON + LF). **[STD/HEURISTIC]** [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) · [RFC 7464](https://www.rfc-editor.org/rfc/rfc7464.html)

- **Удачно:** CLI объявляет `--json-seq` как RFC 7464 или документированный `--jsonl` с одним JSON-текстом на строку.
- **Неудачно:** печатать `{}{}...` без разделителя и называть это JSON.

### 13. Ошибка должна сообщать причину и исправление; детали — по режиму
**Правило.** Возвращать краткую понятную диагностику, стабильную машинную категорию/код и hint по исправлению, когда он надёжен. Stack trace, внутренние адреса и сырой секретный ответ backend — не default. **[GUIDE]** [CLIG: errors](https://clig.dev/#errors) · [Google Cloud CLI: exit/output](https://docs.cloud.google.com/sdk/gcloud#use_of_stdout_and_stderr)

- **Удачно:** «`--from` должен быть RFC 3339 с timezone; пример: …» + документированный error code/exit status.
- **Неудачно:** только `failed`, только stack trace или исправление, которое без подтверждения запускает потенциально опасную команду.

### 14. Опасные действия должны быть явными, previewable и безопасными при повторе
**Правило.** Для destructive/bulk/external actions показывать точный target; поддерживать dry-run/preview; для высокого риска требовать соразмерное подтверждение. Не считать prompt допустимым в pipe-режиме; предусмотреть явный флаг для automation с безопасной семантикой. Повтор после timeout безопасен только при идемпотентности/idempotency key или проверке статуса: timeout не доказывает, что эффект не произошёл. **[GUIDE]** [CLIG: confirmation/dry-run](https://clig.dev/#arguments-and-flags) · [CLIG: recoverability](https://clig.dev/#robustness)

- **Удачно:** сначала `acme project delete --project-id P7 --dry-run --json`; показать объект; затем — отдельное подтверждённое действие.
- **Неудачно:** после сетевого timeout автоматически повторить `send-payment`/`delete` без проверки результата.

### 15. Управлять прогрессом, временем и отменой, не портя результат
**Правило.** Ставить разумный конечный timeout; разрешать отмену; длительный процесс должен сообщать о прогрессе в stderr/TTY, не засоряя stdout. Цвет/анимацию отключать в pipe и по `NO_COLOR`/`--no-color`; ошибки при скрытых логах не должны теряться. **[GUIDE]** [CLIG: robustness](https://clig.dev/#robustness) · [CLIG: output](https://clig.dev/#output) · [CLIG: signals](https://clig.dev/#signals-and-control-characters)

- **Удачно:** TTY видит progress bar; `--json`/pipe получает чистый результат; Ctrl-C прекращает операцию предсказуемо.
- **Неудачно:** вечное ожидание, spinner escape-коды в сохранённом JSON или Ctrl-C оставляет непонятный частичный side effect.

### 16. Обеспечивать discovery и обратную совместимость интерфейса
**Правило.** `--help`/help подкоманд, примеры, наиболее частые команды и подсказки исправления должны быть доступны offline. Стабильные скрипты опираются на `--json`/`--plain`, коды и флаги; изменения — по возможности additive, breaking changes — с депрекацией. Для конфигурации документировать приоритет источников (рекомендация CLIG: flags → environment → project config → user config → system config) и не менять смысл уже опубликованного флага. **[GUIDE/STD]** [CLIG: help](https://clig.dev/#help) · [CLIG: future-proofing/configuration](https://clig.dev/#future-proofing) · [POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html)

- **Удачно:** `--help` перечисляет формат, stdin, интерактивность, лимиты и примеры; устаревающий флаг сообщает замену.
- **Неудачно:** `--force` меняет смысл между версиями или требуется интернет-документация для понимания установленной команды.

### 17. Для CLI со своим окружением полезна отдельная команда диагностики (`doctor`)
**Правило.** Если программа зависит от конфигурации, сетевых сервисов, прав, кеша или внешних инструментов, дайте единый вход для read-only диагностики: обычно `app doctor`. Разделяйте его с `app status`: `status` — быстрый снимок текущего состояния, `doctor` — набор проверок с результатами, границами scope и предлагаемым восстановлением. Это удачный широко применяемый шаблон, а не обязательная команда для каждого CLI. У проверок должны быть стабильные ID/категория/уровень, понятные условия выхода и опциональный фильтр (`--check`, `--scope`). По умолчанию ничего не исправлять; `--fix` — отдельный, явно описанный режим с dry-run/подтверждением соразмерно риску. **[GUIDE]** [npm doctor](https://docs.npmjs.com/cli/v12/commands/npm-doctor) запускает проверки окружения, допускает выбор поднабора и сообщает рекомендуемые изменения; Homebrew советует прочитать предупреждения, исправлять относящиеся к проблеме и не выполнять разрушительные рекомендации вслепую. [Homebrew troubleshooting](https://docs.brew.sh/Troubleshooting)

- **Удачно:** `acme status --json` кратко показывает состояние сервиса; `acme doctor --check auth,filesystem --json` сообщает проверки/найденные проблемы и безопасные следующие шаги; `acme doctor --check auth --details` раскрывает только auth.
- **Неудачно:** `status` молча меняет конфигурацию; либо всякий запуск простой утилиты требует тяжёлого сетевого self-test, который не относится к её задаче.

### 18. Подтверждать успешное действие кратко, но не сводить результат к непрозрачному `OK`
**Правило.** В стандартном human/agent-режиме коротко подтвердить **что сделано, с каким target и каким результатом**: объект/ID, количество, статус и предупреждения, если они есть. Подсказывать только уместные следующие действия, которые действительно следуют из результата; показывать краткое назначение, аргументы и известный побочный эффект. Подсказка не запускает команду и не заменяет подтверждение. Полный перечень флагов — в `--help`/`help <topic>`; вызов корневого CLI без команды может показать компактное оглавление подкоманд с однострочными описаниями, но не полный мануал и не побочные эффекты. При отсутствующем обязательном аргументе показать именно нужный синтаксис/пример. `--quiet` убирает несущественный вывод; `--json` остаётся стабильным машинным контрактом; verbose/details раскрывает пояснения по запросу. CLIG советует сообщать состояние после изменения и предлагать команды, полезные для следующего шага; Anthropic рекомендует high-signal контекст, осмысленный response format и дозированную детализацию. **[GUIDE]** [CLIG: output](https://clig.dev/#output) · [Anthropic: effective tools](https://www.anthropic.com/research/writing-tools-for-agents)

- **Удачно, итог:** `OK: release 4.2 переведён в staging; release_id=R-42; 3 сервиса, 0 предупреждений. Следующий шаг: acme release status --id R-42 (только чтение; проверить rollout).`
- **Удачно, discovery:** корневой `acme` показывает короткое оглавление вроде `release — публикации; status — текущая среда; doctor — read-only диагностика`; `acme release --help` раскрывает только synopsis, смысл и обязательность аргументов, значения/defaults, примеры и побочный эффект.
- **Неудачно:** только `OK`; или после обычного успеха печатать все подкоманды и их полный help. Не выводить потенциально опасную команду как «следующий шаг» без указания эффекта и не запускать её автоматически.

### 19. Группировать многочисленные ошибки, сохраняя точные счётчики и доступ к каждой детали
**Правило.** Всегда давать итоги по severity/category. Если findings немного, показать каждый кратко; если список длинный — оставить сводку и representative примеры, сгруппировать похожие проблемы и показать `total`, `shown`, `truncated` и cursor/путь к деталям. Например, порог **5 findings** — разумная начальная эвристика, не стандарт: подберите его под терминал, модель, тип задач и токен-бюджет. Группировать только общую причину, не прятать независимые проблемы за одним сообщением. Идентификаторы finding должны быть стабильны в пределах отчёта, severity и source/location — явны. Предлагать команды для диагностики/исправления лишь по релевантным группам; исправления остаются отдельными действиями. CLIG прямо рекомендует группировать много однотипных ошибок ради signal-to-noise ratio. **[GUIDE/ЭВРИСТИКА]** [CLIG: errors](https://clig.dev/#errors) · [Google Cloud CLI: filtering/output](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)

- **Удачно, краткий human-вывод:** `doctor: 18 замечаний (12 errors, 6 warnings), 5 показано; 4 группы. AUTH-03: токен истёк. Следующий шаг: acme auth status --profile P7 (read-only). Ещё: --section permissions --details или --report-file doctor.json.`
- **Удачно, JSON-форма:**

```json
{
  "status": "issues_found",
  "summary": {"checks_total": 24, "passed": 16, "errors": 6, "warnings": 2, "findings_total": 8},
  "groups": [
    {"id": "auth", "errors": 2, "warnings": 0, "count": 2},
    {"id": "permissions", "errors": 4, "warnings": 1, "count": 5},
    {"id": "network", "errors": 0, "warnings": 1, "count": 1}
  ],
  "findings": [{"id": "AUTH-03", "severity": "error", "message": "Токен профиля P7 истёк", "location": "profile:P7"}],
  "page": {"shown": 1, "total": 8, "truncated": true, "next_cursor": "opaque-token"},
  "next_steps": [{"argv": ["acme", "auth", "status", "--profile", "P7"], "why": "Проверить выбранный профиль", "effect": "read-only"}]
}
```

- **Неудачно:** показать первые 5 из 200, не указав 200/обрезание; «исправить permissions» без перечня объектов; либо объединить разные причины в одну группу, из-за чего агент считает её единственной проблемой.

### 20. Для крупных деревьев отдавать оглавление, projection и точечное раскрытие
**Правило.** Большой диагностический/структурный отчёт должен иметь несколько уровней: **(0) краткий итог и счётчики → (1) оглавление групп/путей → (2) выбранная группа/ID/поддерево → (3) подробная запись или исходный лог**. Предлагайте selectors вроде `--section`, `--id`, `--path`, `--max-depth`, `--fields`, `--limit`, `--cursor`, `--report-file`; у каждого — конкретная семантика в `--help`. В кратком outline можно выводить `JSON Pointer = типизированное значение` (`/services/billing/status = "degraded"`), но для повторяющихся элементов используйте стабильные IDs, не неустойчивый индекс массива. Не называйте плоское представление `path=value` «патчем»: если это **изменение** JSON-ресурса, используйте определённый контракт diff/patch, например RFC 6902 JSON Patch (`op`, `path`, `value`). **[GUIDE; RFC 6901/6902 — только для синтаксиса JSON Pointer/Patch]** Google Cloud CLI документирует форматирование, фильтры, projections и лимиты для выбора только нужных полей; RFC 6901 задаёт адресацию значения JSON, а RFC 6902 — формат операций изменения JSON. [gcloud scripting](https://docs.cloud.google.com/sdk/docs/scripting-gcloud) · [RFC 6901: JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) · [RFC 6902: JSON Patch](https://www.rfc-editor.org/rfc/rfc6902)

- **Удачно:** `acme inspect --format=paths --max-depth 2` → `services.billing.status = "degraded"`, `services.billing.findings = 3`; затем `acme inspect --path /services/billing/findings --limit 10` или `acme inspect --id F-104 --details`.
- **Неудачно:** один гигантский JSON/дерево без оглавления, числа совпадений, стабильных ключей и способа запросить ветвь; или массив результатов, обрезанный молча.

### 21. Учитывать кэш модели, но не проектировать вывод в расчёте на кэш-хит
**Правило.** Кэш prompt у провайдера может удешевить/ускорить повторную обработку **совпадающего префикса**; это не бесплатное хранилище произвольного результата CLI. Кэшированные input tokens по-прежнему входят в prompt/context budget; новые tool-результаты, уникальные хвосты, output tokens, miss/write и cache expiry имеют собственную стоимость. У OpenAI и Anthropic детали различаются по модели, точному совпадению prefix, breakpoints/минимальному объёму/TTL и тарифам. Держите повторно используемые инструкции/схемы стабильными в начале запроса, переменное содержимое — позже; измеряйте `cached_tokens`/usage и latency в целевом клиенте. Не увеличивайте первый вывод ради предположения, что последующие чтения будут бесплатными. Отдельно: MCP `ttlMs/cacheScope` кэширует результаты/описания на стороне MCP-клиента, это не то же самое, что prompt/KV cache модели. **[GUIDE]** [OpenAI: Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) · [Anthropic: Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) · [MCP Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)

- **Удачно:** краткая сводка сначала; повторно нужную ветвь/деталь агент читает по ID. Стабильные системные инструкции и tool schemas могут попасть в prompt cache, если соблюдены условия провайдера.
- **Неудачно:** отдавать 30 000 строк «на будущее, вдруг cache hit»; считать, что cache hit освобождает место в context window или отменяет стоимость уникального отчёта.

### 22. Строить дерево документации как производный компактный индекс
**Правило.** Для репозитория с несколькими Markdown-документами CLI может автоматически построить JSON-каталог: документы → разделы H1–H6 → вложенные подразделы. Markdown остаётся источником истины; индекс — восстанавливаемый артефакт навигации и поиска, а не вторая копия всех текстов. Парсить нужно тем же flavor/parser, что использует проект (CommonMark, GFM, MDX и т. п.), а не regex по строкам: заголовкоподобный `#` внутри fenced code block — не заголовок; есть также Setext-заголовки. Хранить минимум: стабильный `id`, относительный `path`, `title`, `level`/`parent_id`, при необходимости renderer-specific `anchor`, диапазон исходных строк с явно заданными границами (inclusive/exclusive) и `children_count`; полный текст и embeddings не помещать в каждый ответ дерева. ID вида `path + heading slug + duplicate ordinal` детерминирован, но может меняться при переименовании; если нужны постоянные ссылки, задавать явные anchor/ID. Свежесть индекса проверять по per-file content hash и версии parser/index schema (одного git `HEAD` недостаточно для dirty working tree); перестраивать только изменившиеся документы. Автообновление при обнаружении stale index удобно для локальной работы, а явная `docs index build` — для CI/детерминированной проверки. Сам JSON outline можно держать компактным manifest; полнотекстовый поиск — отдельный индекс, например встроенный SQLite FTS5 для локального корпуса, если он есть в сборке. **[GUIDE]** [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) описывает структуру и синтаксис заголовков/кодовых блоков, но не задаёт ваш JSON-формат или глобально стабильные ID; [SQLite FTS5](https://www.sqlite.org/fts5.html) даёт локальный full-text `MATCH`, BM25 ranking и функции `snippet`/`highlight`.

- **Удачно:** `acme docs tree --within docs/architecture/ --max-depth 3 --format json` возвращает только оглавление выбранного поддерева, а индекс на диске обновляется при изменении исходных `.md`.

```json
{
  "revision": "git:abc123",
  "documents": [{
    "id": "doc:architecture/search.md",
    "path": "docs/architecture/search.md",
    "title": "Search",
    "children": [{
      "id": "doc:architecture/search.md#hybrid-search",
      "title": "Hybrid search",
      "level": 2,
      "lines": [31, 58],
      "children": [{
        "id": "doc:architecture/search.md#hybrid-search-reranking",
        "title": "Reranking",
        "level": 3,
        "lines": [42, 53],
        "children": []
      }]
    }]
  }]
}
```

- **Неудачно:** регулярно заново передавать модели полное дерево и содержимое каждого файла; или разбирать Markdown регулярным выражением, из-за чего кодовый пример `# heading` становится ложным разделом. Для очень маленького корпуса индекс/векторная база может быть лишней сложностью: начните с `rg`, прямого чтения исходных файлов или компактного manifest.

### 23. Искать сначала дёшево, раскрывать текст дозированно, усложнять ранжирование по eval
**Правило.** Выделите CLI поверхность `docs tree` (оглавление), `docs search` (короткий ранжированный список) и `docs show` (полный выбранный раздел; принимать несколько `--id`). Поиск должен сначала ограничивать корпус фильтрами `--within`/тип/версия, затем ранжировать **разделы**, сохраняя `path`, heading breadcrumb, стабильный `id` и source line range. Задайте в контракте, что `--within <path|section-id>` охватывает весь выбранный подкаталог/раздел вместе с дочерними заголовками (рекомендуемый default), а как запросить только сам узел. В snippets возвращать предложение целиком с совпадением и минимумом соседнего контекста; если установленный лимит обрезал его — сообщать `snippet_truncated`, не выдавая фрагмент за полное предложение. Не выводить тело документа, raw embedding и все retrieval scores по умолчанию.

Начинайте с lexical baseline: BM25 хорошо находит точные термины, редкие имена, версии и error codes; поднимайте title/heading-path выше body. Проверяйте tokenizer на языках корпуса (включая русский и смешанный RU/EN) и на идентификаторах вроде `C++`, `TS-999`, `camelCase` и путях: агрессивный stemming/удаление пунктуации может как улучшить, так и сломать поиск; exact ID/path search сохраняйте отдельно. Семантический retriever добавляйте, если запросы часто перефразированы; объединяйте его кандидатов с BM25 по стабильному section ID, например RRF, когда шкалы score не сопоставимы. Cross-encoder reranker — опциональный второй этап только для ограниченного candidate set: он может улучшить порядок, но добавляет runtime latency/cost. Heading breadcrumb — дешёвое объяснение контекста; генерацию LLM-context на каждый chunk делайте только если она полезна на своём наборе и оправдывает стоимость индексации. Любые удалённые embeddings/reranker/context-generation API могут передавать им текст документа: используйте их только после проверки privacy/data-retention policy и разрешённых границ корпуса. `rank` — понятная позиция результата в текущей выдаче; для равных результатов задайте детерминированный tie-break (например, по `id`). Score показывайте только с названием метода/версии в `--explain`: BM25/vector/RRF score не является вероятностью релевантности и напрямую не сравнивается между моделями/индексами. **[GUIDE]** [Anthropic: Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval) демонстрирует complementary BM25 + embeddings + reranking и оговаривает границы собственного эксперимента; [OpenSearch: RRF](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/) рекомендует rank fusion, когда score-калибровки нет; [Elastic: ranking](https://www.elastic.co/docs/solutions/search/ranking) описывает дорогой rerank как второй этап после быстрого отбора кандидатов.

**Контракт вызова.** Делайте грамматику query явной. Повторный `--term` может означать альтернативы при `--match any` или обязательное пересечение при `--match all`; отдельно документируйте `--phrase` и opt-in `--regex`. Не подразумевайте, что строка `xx|yy` сама задаёт OR: при передаче literal через shell её нужно заключить в кавычки (`--query 'xx|yy'`), а альтернативы в примере ниже задаются двумя `--term` и `--match any`. regex — отдельный opt-in режим со своей явно описанной грамматикой. Пример ниже — проектное соглашение; `8` — иллюстративный лимит, не стандарт.

```sh
acme docs search --within docs/architecture/ \
  --term 'BM25' --term 'hybrid' --match any --limit 8 --format json

acme docs show \
  --id 'doc:architecture/search.md#hybrid-search' \
  --id 'doc:architecture/search.md#hybrid-search-reranking' \
  --format json
```

**Компактный search result, не полный dump:**

```json
{
  "revision": "git:abc123",
  "total": 12,
  "returned": 1,
  "truncated": true,
  "results": [{
    "id": "doc:architecture/search.md#hybrid-search",
    "path": "docs/architecture/search.md",
    "title": "Hybrid search",
    "heading_path": ["Architecture", "Search", "Hybrid search"],
    "rank": 1,
    "relevance": {"method": "rrf", "matched_by": ["bm25", "dense"]},
    "matched_terms": ["BM25", "hybrid"],
    "snippet": {"text": "… BM25 combines exact term matching with semantic retrieval. …", "line_start": 42, "line_end": 43}
  }],
  "next_cursor": "opaque-token"
}
```

`path` — исходный файл, `heading_path` — breadcrumb, `id` — адрес для следующего `show`; это не JSON Patch. `next_cursor` для этого поиска — собственный контракт приложения, не автоматическая пагинация CLI/MCP; для продолжения передавайте его неизменённым через документированный `--cursor`. Для token economy ограничивайте число результатов, snippet и общий output bytes, а full section запрашивайте только по выбранным ID. Символьный лимит не равен универсальному token limit: если нужен точный `--token-budget`, укажите tokenizer/model и учитывайте estimation error; предпочтительнее измерять фактические input tokens на целевом harness. Retrieval не всегда экономит tokens: для маленького корпуса или задачи, требующей целого документа, один `docs show` может быть дешевле нескольких search→detail round-trips; сравнивайте суммарные tokens/latency до первого правильного ответа. Векторный индекс и промежуточные кандидаты reranker-а обрабатывайте внутри CLI; не возвращайте embeddings или сырые candidate payload в stdout. [ripgrep User Guide](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md) полезен как baseline для recursive search, glob и literal/regex режимов; его `--json` — поток search events, а не произвольное JSON-дерево документов.

- **Удачно:** сначала `docs search --limit N` отдаёт `total`, rank, путь, breadcrumb и короткое предложение с line range; затем один `docs show --id ... --id ...` возвращает только выбранные разделы.
- **Неудачно:** передавать `--grep 'xx|yy'` без определённой грамматики (литерал это или regex-альтернатива), возвращать сотни целых файлов с каждым совпадением или показывать необъяснённое число score как «92% релевантно».

### 24. Решать, нужна ли функция, и где её разместить: агент, CLI, MCP или человек
**Правило.** Не превращать каждую мыслительную операцию в команду. Команда/tool оправданы, если без них агенту недоступны актуальные/частные данные, требуется точная воспроизводимая операция, большой объём обработки, доверенная валидация или реальный side effect. Если ответ уже полностью содержится в контексте, расчёт мал и проверяем, а внешних данных/действий нет, лишний вызов чаще добавит задержку, tokens и поверхность отказа. Семантический выбор, трактовка неоднозначного намерения и синтез небольшого числа фактов обычно остаются у агента; получение источников, массовая фильтрация, расчёты, проверки и запись — у детерминированного кода. При смешанной задаче разделяйте этапы: инструмент возвращает ограниченные кандидаты/доказательства, агент их интерпретирует. **[GUIDE]** [Anthropic: choosing tools](https://www.anthropic.com/engineering/writing-tools-for-agents) · [Anthropic: context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

```text
Нужны ли новые данные/действие или точная работа, которой нет в контексте?
├─ Нет → агент рассуждает над уже предоставленным; новую команду/tool не добавлять.
└─ Да → результат выводится воспроизводимыми правилами?
   ├─ Нет → агент интерпретирует смысл/evidence; при критичной неоднозначности уточняет у человека.
   └─ Да → код детерминированно получает, фильтрует, агрегирует, считает,
      валидирует или меняет данные. Где живут данные и исполнение?
      ├─ Локальный repo/filesystem/stdin/stdout, shell/pipeline или имеющийся CLI
      │  → CLI с ограниченным машинным контрактом.
      ├─ Сервисная capability должна обнаруживаться/вызываться через MCP-host
      │  → tool для операции; resource для адресуемого контекста.
      └─ Задача нужна обоим видам клиента → общая domain/API-логика,
         тонкие CLI/MCP adapters; не дублировать бизнес-правила.

Для любого варианта: если задача смешанная, отдавать агенту компактные
кандидаты/evidence, а не поручать коду угадывать свободный смысл.
```

CLI и MCP — не взаимоисключающие «режимы для человека/ИИ»: CLI может обращаться к удалённому сервису, а MCP-сервер может работать локально. При выборе учитывайте место данных и исполнения, кто и где авторизует вызов, доступность безопасного process/CLI у host, необходимость обнаружения по schema для разных MCP-клиентов, latency/объём и способ аудита. CLI естествен для repo/filesystem и shell-потоков; MCP — когда capability публикуется server-side для совместимых hosts с явными типизированными tools/resources и серверной проверкой прав. Не добавляйте интерфейс лишь из-за ярлыка «для агента». В MCP-спецификации tools — model-controlled, resources — application-driven; это семантика протокольных поверхностей, не требование переносить каждую команду. Не оборачивайте каждый endpoint в отдельный tool/command: начните с повторяемых high-value задач с ясным результатом; объединяйте шаги, только если они естественно образуют один частый workflow и не прячут разные риски. **[STD/GUIDE]** [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [MCP Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources) · [OpenAI: function calling](https://developers.openai.com/api/docs/guides/function-calling)

#### Примеры выбора по дереву

**Хорошие примеры**
1. Логи уже лежат в локальном repo; задача — посчитать частоту ошибок по сервисам в миллионе строк. `acme logs summarize --since 24h --group service --limit 10 --json` делает точный проход и возвращает агрегаты, несколько ID примеров и признак усечения. **Почему хорошо:** объёмная повторяемая работа выполняется кодом, не контекстом модели; модель тратит ограниченный ввод на интерпретацию сводки.
2. Нужен текущий статус приватного заказа из сервисной системы: MCP `get_order(order_id)` возвращает только статус, даты и идентификатор последнего платежа; агент объясняет неоднозначную ситуацию по этим фактам. **Почему хорошо:** актуальные авторизованные данные остаются за service boundary; tool не решает семантический спор вместо модели. Если заказ/факты уже полностью представлены в запросе и свежесть не важна, дополнительный вызов вообще не нужен.

**Плохие примеры**
1. `acme --request 'найди всё старое и исправь что нужно'` внутри классифицирует свободный текст регулярками и меняет данные. **Почему плохо:** критерий «старое/нужно» неоднозначен, regex не понимает смысл, а неявная команда смешивает поиск и рискованный side effect.
2. `acme export --all --json` отдаёт миллионы строк модели «для анализа» либо универсальная `acme execute --text ...` сама выбирает query и действие. **Почему плохо:** неограниченный ввод перегружает контекст и повышает вероятность пропуска; у универсального интерфейса нет узких аргументов/правил, которые слабая модель могла бы надёжно соблюдать. Вместо этого код агрегирует/фильтрует и отдаёт небольшую выборку с ID; действие задаётся отдельно.

### 25. Проектировать входы CLI по решению, а не по попытке regex-понять пользователя
**Правило.** У каждой команды должен быть один ясно названный verb/workflow и только необходимые для него параметры. Принимайте структурированные flags/JSON/stdin с типами, единицами, scope, пределами, defaults и семантикой absent vs `null`; большие наборы — через stdin/файл и bounded batch. Не просите модель повторить значения, уже известные CLI из безопасной конфигурации/авторизованного контекста; но критичный target не выводите молча из неоднозначного cwd/account. Required делайте только поля, без которых действие невозможно; если безопасный default существует — опишите его и поведение. Для фиксированного синтаксиса (формат ID, дата, enum) применим parser/allowlist/regex; regex проверяет форму, **не** намерение, бизнес-смысл, существование объекта или право на него. Сначала определить действие и параметры, затем syntax/business validation и authorization независимо друг от друга. Свободный текст допустим как поисковый `--query`, если его роль — именно query, а не скрытая инструкция выполнить любое действие. **[GUIDE]** [OWASP: Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) разделяет syntax/semantic validation и отдельно отсылает к authorization; [CLIG: arguments and flags](https://clig.dev/#arguments-and-flags)

**Хорошие примеры**
1. `acme orders search --status overdue --limit 50 --json`; пользовательский текст может быть `--query 'как отменить зависший платёж?'`, но поиск лишь возвращает результаты. **Почему хорошо:** query явно является текстом для поиска, scope/limit понятны, запрос не инициирует изменение.
2. `acme tickets close --id T-104 --resolution duplicate --json`. **Почему хорошо:** действие, стабильная цель и enum-причина заданы отдельно; CLI может проверить формат и права до side effect.

**Плохие примеры**
1. `acme --request 'найди подозрительные платежи и, если нужно, отменяй'`. **Почему плохо:** поиск, субъективный критерий и необратимое действие смешаны в одном свободном поле; командный контракт не выражает, что агент действительно решил.
2. `acme tickets close --id T-104 --status maybe --force`, где `--status` не ограничен enum, `--force` скрывает эффект, а проект/tenant молча берётся из неочевидного default. **Почему плохо:** значение не валидируется по смыслу и target может оказаться не тем; required scope и эффект должны быть явны, authorization — отдельна.

### 26. Выбирать выходные поля по следующему шагу агента, а не выгружать объект целиком
**Правило.** Перед добавлением каждого поля спросите: **изменит ли оно решение/следующий вызов; нужно ли оно для точной идентификации target, проверки результата, полноты или ссылки на источник; можно ли вывести его надёжно из других полей; сколько добавляет tokens, чувствительных данных и неоднозначности?** В базовый ответ входят статус выполнения и основное значение; стабильный ID вместе с понятным именем, если нужен follow-up; только свойства, меняющие выбор/ответ; scope/единицы/время/source, если без них смысл неполон; число совпадений и `truncated`/cursor для больших выдач. Не возвращайте «все колонки БД» только потому, что они существуют. Debug/trace/backend internals — по запросу; секреты и нерелевантные PII не включать вовсе. Минимальный output должен быть **достаточным**, а не настолько бедным, чтобы каждый нормальный workflow требовал ещё один вызов. Для bulk-результатов агрегируйте/фильтруйте до stdout; при необходимости detail/detail-by-ID доступен отдельно. **[GUIDE]** [Anthropic: meaningful context and token efficiency](https://www.anthropic.com/engineering/writing-tools-for-agents) · [Google Cloud CLI: projections/filters](https://docs.cloud.google.com/sdk/docs/scripting-gcloud)

**Хорошие примеры**
1. Изменение возвращает `{"status":"updated","target":{"id":"R-42","name":"Payments staging"},"changed":{"version":"4.2"},"warnings":[]}`. **Почему хорошо:** можно проверить target и фактическое изменение, объяснить результат и безопасно продолжить.
2. Поиск возвращает `{"total":240,"returned":3,"truncated":true,"next_cursor":"…","items":[{"id":"T-104","title":"Login errors","status":"open"}]}`. **Почему хорошо:** достаточно для выбора кандидата и следующего `show --id`; total/cursor не дают принять частичную выдачу за полную.

**Плохие примеры**
1. После успешного изменения вернуть только `OK`. **Почему плохо:** модель не может проверить, что именно изменилось и на каком объекте; может повторить операцию или сообщить пользователю недоказанный итог.
2. Поиск возвращает сотни полных записей с внутренними столбцами, либо первые 3 из 240 без ID и признака усечения. **Почему плохо:** первый вариант перегружает контекст и раскрывает лишнее, второй мешает выбрать запись и понять полноту.

#### Явно подсказывать модели полезную следующую команду — условно, не всегда
Если CLI знает **конкретный и доступный** follow-up, JSON-контракт может включать проектное поле `next_actions`. Возвращайте один наиболее полезный вариант, редко — до трёх альтернатив, только когда это сокращает неопределённость/лишний вызов; укажите назначение и аргументы. Для команды используйте `argv` как массив отдельных токенов, не склеенную shell-строку. Это подсказка, не вызов: агент сам сверяет её с пользовательской целью, `--help`, доступными правами и policy; вывод не должен запускать команду автоматически. Не предлагайте запись/удаление/публикацию, если пользователь этого не просил; для допустимых опасных действий нужны обычные preview/confirmation правила. Неизвестное намерение — повод задать вопрос, а не сгенерировать «полезную» команду. `next_actions` — проектное поле CLI, не универсальный стандарт; когда полезного продолжения нет, не выдумывайте его (если поле обязательно по JSON schema, верните пустой массив).

```json
{
  "results": [{"id": "T-104", "title": "Login errors", "status": "open"}],
  "next_actions": [{
    "argv": ["acme", "tickets", "show", "--id", "T-104", "--json"],
    "purpose": "получить подробности выбранного тикета"
  }]
}
```

`argv` передают процессу отдельными аргументами, не через `bash -c` и не через `eval`; значение из результата сначала проверяют как данные.

**Ещё хороший пример:** поиск вернул 18 похожих тикетов, и только пользователь/агент может решить, какой релевантен. CLI возвращает ограниченный список ID и не заполняет `next_actions` восемнадцатью `tickets show`. **Почему хорошо:** система не подменяет семантический выбор и не дублирует каталог команд в каждом результате.

**Плохие примеры**
1. Каждый ответ содержит список всех возможных команд (`show`, `update`, `delete`, `export`, `assign`, …), независимо от результата. **Почему плохо:** это копия `--help`, увеличивает контекст и делает нужный шаг менее заметным.
2. После read-only поиска CLI предлагает `acme tickets delete --id T-104` без просьбы пользователя или отдаёт строку для `bash -c`. **Почему плохо:** подсказка не является разрешением на side effect; shell-строка создаёт риск инъекции и некорректного quoting. Для действия нужны явная цель, отдельная команда, проверка policy и подтверждение по риску.

#### Дочерний объект или атрибут: решить по идентичности, рабочему процессу и объёму

Сначала различайте три вещи: **атрибут** — значение родителя; **вложенная summary-запись** — ограниченное представление связанного объекта; **дочерняя сущность** — объект, который можно независимо идентифицировать и использовать между шагами. Создание дочерней сущности **не означает** создание отдельной CLI-команды на каждый её экземпляр.

```text
1. Значение только описывает родителя и не выбирается/меняется отдельно?
   ├─ Да → обычный атрибут родителя (status, owner, last_deployment_at).
   └─ Нет → дочерний объект имеет собственный стабильный ID, жизненный цикл,
      права, историю или отдельные операции?
      ├─ Нет → не создавать сущность; вложить только нужное поле/summary
      │  либо вовсе не возвращать его.
      └─ Да → отдельная сущность с ID; в ответе родителя — ID и краткий summary.

2. Сколько подробностей нужно именно для текущего шага?
   ├─ Несколько записей нужны для сравнения сейчас → bounded summaries
   │  с полями, реально влияющими на выбор.
   ├─ Список велик или полная запись пока не нужна → count + малая выборка,
   │  `truncated`/cursor и `show --id` для выбранного ребёнка.
   └─ Полные данные нужны сейчас и набор заведомо мал → вернуть нужную проекцию,
      но ограничить размер/поля и показать полноту.

3. Нужна ли новая команда?
   ├─ Уже есть `list/show/update <child> --id ...` → использовать её.
   └─ Новый тип действия действительно отсутствует → добавить одну команду
      для операции/типа, а не команду на каждый ID или атрибут.
```

**Хорошие примеры**
1. Карточка проекта содержит `{"id":"P-7","status":"degraded","owner":"payments"}`. **Почему хорошо:** эти скалярные значения нужны, чтобы понять состояние самого проекта; для них не нужны отдельные сущности или `get_project_status`/`get_project_owner`.
2. У проекта 128 deployments с отдельными ID, состоянием и собственной историей. CLI возвращает число, короткие summaries с ID и cursor; только выбранный deployment раскрывается через `acme deployments show --id D-204 --json`. **Почему хорошо:** child можно независимо запросить, но весь архив не попадает в контекст.

```json
{
  "project": {"id": "P-7", "status": "degraded", "owner": "payments"},
  "deployment_summary": {
    "total": 128,
    "items": [{"id": "D-204", "status": "failed"}],
    "truncated": true,
    "next_cursor": "opaque-token"
  },
  "next_actions": [{
    "argv": ["acme", "deployments", "show", "--id", "D-204", "--json"],
    "purpose": "получить детали выбранного deployment"
  }]
}
```

**Плохие примеры**
1. В каждый ответ о проекте вкладываются все 128 полных deployment-объектов вместе с логами, конфигурацией и историей. **Почему плохо:** ввод растёт без связи с текущим вопросом; важные строки теряются среди деталей, возрастает риск усечения и лишнего раскрытия данных.
2. Для каждой колонки и каждой записи заводятся отдельные команды: `get_project_owner`, `get_project_status`, `get_deployment_D-204`, `get_deployment_D-205`. **Почему плохо:** команда дублирует атрибут или кодирует конкретный ID в имени; каталог разрастается, становится нестабильным и заставляет модель выбирать из лишних вариантов. Нужны поля родителя и одна общая `show --id` для типа объекта.

Проверяйте пользу полей абляцией на реальных workflow: сравните output schema с/без `next_actions`, вложенных деталей и отдельных атрибутов. Оценивайте task success, неверные действия, лишние round-trips, суммарные input tokens и latency. Подсказка следующей команды может экономить контекст и вызовы, если она точна; если не меняет решение, дублирует `--help` или перечисляет все возможности CLI, уберите её. Богатые details оставляйте под `--fields`/`--details`. Это проектный критерий для измерения, не стандарт. Стабильный `--json` остаётся контрактом; human summary и verbose output — отдельные режимы, не текст для парсинга.

## II. Постулаты безопасного использования CLI агентом

1. **Сначала обнаружить контракт:** прочитать `--help` нужной подкоманды; не выдумывать флаги/сокращения. Использовать только документированный машинный режим и проверять его формат. [CLIG: help](https://clig.dev/#help)
2. **Запускать без интерактивных сюрпризов:** передавать обязательные значения явно, использовать `--no-input`; не отправлять JSON в stdin команды, которая ожидает клавиатурный ответ. [CLIG: interactivity](https://clig.dev/#interactivity)
3. **Собирать stdout, stderr и exit code раздельно:** проверить exit code прежде чем считать stdout успехом; разбирать stderr как машинные данные только если таков опубликованный контракт. [POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html) · [Google Cloud CLI](https://docs.cloud.google.com/sdk/gcloud#use_of_stdout_and_stderr)
4. **Не вставлять недоверенный текст в shell-строку:** использовать безопасный вызов программы с отдельными argv; валидировать destination, path и option injection, а не только shell-метасимволы. [OWASP OS Command Injection](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html) · [Google Shell Style](https://google.github.io/styleguide/shellguide.html#quoting)
5. **Не раскрывать секреты:** не передавать токены в аргументах и не печатать их; не пересылать PII/секрет из вывода одной команды в другую без необходимости и разрешения. [CLIG: secrets](https://clig.dev/#arguments-and-flags) · [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)
6. **Ограничивать объём:** добавлять фильтры, лимиты, projections и pagination; преобразовывать/агрегировать большие результаты до помещения в контекст. [Google Cloud CLI](https://docs.cloud.google.com/sdk/gcloud#determining_output_structure) · [Anthropic: context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
7. **До риска — preview:** при удалении, отправке, публикации и финансовом/массовом эффекте проверить target и dry-run; получать пользовательское подтверждение по правилам приложения. [CLIG: confirmation](https://clig.dev/#arguments-and-flags)
8. **После timeout не дублировать побочный эффект вслепую:** сначала запросить статус/idempotency key или проверить объект, затем решать, повторять ли. [CLIG: recoverability](https://clig.dev/#robustness)

## III. Оценка качества CLI для агентов

- Тестировать реальные задачи, а не только парсинг флагов: успешность, правильность target/получателя, валидность параметров, число вызовов, восстановление после ошибки, latency, токены/объём stdout и опасные эффекты. Включать самую слабую модель и самый тесный контекстный бюджет, которые продукт обещает поддерживать; ясный интерфейс снижает ошибки, но не может гарантировать их отсутствие. [Anthropic: tool evaluation](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Проверять матрицу режимов: TTY/non-TTY, pipe/file, `--json`, `--plain`, `--no-input`, пустой/большой ввод, Unicode, неверный формат, timeout/cancel, повтор после частичного успеха. [CLIG: robustness](https://clig.dev/#robustness) · [POSIX.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html)
- Отдельно оценивать формат ошибок, корректность exit code, отсутствие текста/ANSI в JSON и поведение при повреждённой/частичной выдаче. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) · [Google Cloud CLI](https://docs.cloud.google.com/sdk/gcloud#use_of_stdout_and_stderr)
- Для `doctor` и многоуровневых отчётов тестировать здоровое/неполное окружение и 0, 1, около выбранного порога и много findings; проверить согласованность totals, группировки, truncation/cursor, получение деталей и отсутствие скрытого исправления. Сравнивать summary→detail с полным выводом по task success, объёму контекста, числу вызовов и latency; кеш проверять по фактическому usage.
- Для `docs search` создать набор реальных запросов с размеченными релевантными section IDs (точные identifiers/error codes, обычные keyword-запросы, перефразировки, нулевой результат); сравнить `rg`/BM25 baseline, hybrid+RRF и reranker. Отслеживать Recall@k, MRR/nDCG, успешность ответа с корректной ссылкой на источник, фактически потреблённые tokens по всему task (включая повторные вызовы/ответы), latency и стоимость индексации/query; сравнивать tokens на одну успешно решённую задачу при сопоставимом качестве. Rank-evaluation требует типичных запросов и relevance judgements на каждый запрос; не выбирать веса/лимит по одному примеру. [Elasticsearch: ranking evaluation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval)
- Сравнивать версии на фиксированном и held-out наборах; не объявлять выбранную длину, число вызовов или экономию токенов универсальной без измерений. [Anthropic: tool evaluation](https://www.anthropic.com/engineering/writing-tools-for-agents)

### Минимальный pre-release чек-лист

- [ ] Каждая команда закрывает проверенный workflow; выбор CLI vs MCP обоснован местом данных/исполнения, host-возможностями и правами, а не ярлыком «для агента».
- [ ] Семантическое понимание/неоднозначный выбор не спрятаны в regex или свободно-текстовом catch-all; повторяемая массовая операция выполняется детерминированно.
- [ ] Каждая output-проекция оправдана следующим шагом; `next_actions` точны, ограничены и не запускаются автоматически.
- [ ] Проверена самая слабая поддерживаемая модель при целевом малом контекстном бюджете; нет обещания «безошибочности» вместо evaluation и защитных проверок.
- [ ] Дочерние сущности имеют самостоятельную причину/ID; большие коллекции представлены count + bounded summaries + явное продолжение, а не полным dump.
- [ ] Команда/флаги однозначны; `--help` содержит примеры и типы/форматы.
- [ ] Все действия доступны без TTY; есть `--no-input`.
- [ ] Секреты не попадают в argv, stdout/stderr и логи.
- [ ] stdout — только данные; stderr — диагностика; exit status надёжен.
- [ ] `--json` — чистый, стабильный и документированный формат; ошибка имеет единую политику.
- [ ] Большие ответы ограничены, проецируются и явно указывают полноту/продолжение.
- [ ] Для docs-index совпадают Markdown flavor/parser и renderer; обнаруживается stale index; ID/path/heading/line ranges проверены на дублирующихся заголовках и содержимом code fence.
- [ ] Поиск документации имеет явную query grammar и path scope; JSON-выдача ограничена, содержит rank/snippet/source lines/total/truncation; `show` раскрывает один или несколько стабильных IDs.
- [ ] BM25/grep — измеренный baseline; embeddings, RRF и reranking включаются только при заметном выигрыше на размеченных задачах и приемлемой цене/приватности.
- [ ] Неисполняемый текст отделён от команд; пути/URL/операции ограничены и валидируются.
- [ ] Side effect имеет dry-run/подтверждение, безопасный retry/status check и timeout.
- [ ] Пройдены pipe/TTY/security/evaluation тесты на целевых агентных клиентах.

## Источники: что является чем

### Стандарты и спецификации
- [POSIX.1-2024, Shell and Utilities](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap01.html) — IEEE Std 1003.1-2024; правила относятся к POSIX-conforming utility.
- [RFC 8259 — JSON](https://www.rfc-editor.org/rfc/rfc8259.html) — IETF Internet Standard.
- [RFC 7464 — JSON Text Sequences](https://www.rfc-editor.org/rfc/rfc7464.html) — IETF Standards Track, Proposed Standard; не путать с NDJSON.
- [RFC 6901 — JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) — строковая адресация значения в JSON.
- [RFC 6902 — JSON Patch](https://www.rfc-editor.org/rfc/rfc6902) — операции изменения JSON-документа; не формат простой сводки `path=value`.

### Рекомендации, не формальные требования
- [CLIG](https://clig.dev/) — дизайн CLI, help, stdout/stderr, TTY, ошибки, стабильность.
- [npm doctor](https://docs.npmjs.com/cli/v12/commands/npm-doctor) и [Homebrew Troubleshooting](https://docs.brew.sh/Troubleshooting) — примеры диагностики продукта, не универсальное требование к CLI.
- [Google Cloud CLI: scripting](https://docs.cloud.google.com/sdk/docs/scripting-gcloud) — предсказуемые форматы, фильтры и проекции.
- [Google Cloud CLI](https://docs.cloud.google.com/sdk/gcloud) — документированные streams, prompting, format/filter/projection.
- [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) — shell quoting/arrays.
- [OWASP OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html) — безопасный запуск ОС-команд.
- [OWASP Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) — синтаксическая и семантическая проверка данных отдельно от авторизации.
- [Anthropic: Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents) — проектирование и evaluation инструментов.
- [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) — управление контекстом.
- [OpenAI: Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) и [Anthropic: Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) — поведение и условия prompt cache у конкретных провайдеров; не гарантия MCP или CLI.

### Markdown-парсинг и поиск по документам
- [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) — базовый синтаксис Markdown, блоки/заголовки; расширения проекта могут требовать GFM/MDX-aware parser.
- [SQLite FTS5](https://www.sqlite.org/fts5.html) — локальный полнотекстовый индекс, MATCH, BM25, phrase query, snippet/highlight; FTS5 может зависеть от способа сборки SQLite.
- [ripgrep User Guide](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md) — recursive search, фильтры и regex; удобный baseline для точного поиска, но не структурный индекс разделов.
- [OpenSearch: Hybrid search](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/) и [Reciprocal rank fusion](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/) — сочетание lexical/vector retrieval и объединение результатов по rank.
- [Elastic: Ranking and reranking](https://www.elastic.co/docs/solutions/search/ranking) — двухэтапная схема: быстрый candidate retrieval → более дорогой reranker.
- [Elastic: Ranking evaluation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval) — тестовые запросы, relevance judgements и retrieval metrics.
- [Anthropic: Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval) — BM25 + embeddings, контекстная индексация и reranking; опубликованные выигрыши относятся к их экспериментам и не гарантируют тот же результат на другом корпусе.
