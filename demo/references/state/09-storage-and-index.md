# 09. Хранилище: индекс, снимок, кэш

## Разделение «истина» и «производное»

| Что | Где | Можно удалить? |
|---|---|---|
| Документы и записи пользователя | DATA_ROOT (`.md`, `.csv`, `.json`) | нет — это истина |
| Конфигурация и типы | `.todoc/dataset.json`, `rules/`, `*_types/`, `templates/`, `schemas/`, `queries/` | нет — настраивается вручную |
| Индекс | `.todoc/index/` | да, пересобирается `index rebuild` |
| Кэш парсинга | `.todoc/cache/parse/` | да, пересоздаётся |
| Сгенерированные артефакты | `.todoc/generated/` | да |

В `.gitignore` производные каталоги исключены (`**/.todoc/index/`, `**/.todoc/cache/`,
`**/.todoc/generated/`), конфигурация — отслеживается.

## Снимок индекса

Индекс — это **кэш**, а не история: он один и инвалидируется по содержимому.

```
.todoc/index/
├── CURRENT.json                 # {schema_version, dataset_id, generation_id,
│                                #  config_digest, corpus_digest, created_at}
├── stats.json                   # path → {hash, mtime, size}: дайджест без перечитывания
└── current/
    ├── meta.json
    ├── folders.json
    ├── documents.json
    ├── records.json
    ├── relations.json
    └── diagnostics.json
```

Публикация атомарна:

1. данные пишутся во временный каталог `.tmp-current`;
2. каждый JSON перечитывается и проверяется на разбор;
3. временный каталог переименовывается в `current/`, прежний снимок удаляется;
4. только после этого атомарно перезаписывается `CURRENT.json`.

При любой ошибке временный каталог удаляется, а старый `CURRENT.json` остаётся — читатель никогда
не видит наполовину готового снимка. Отсутствие полного снимка — `generation.incomplete` (exit 6)
с подсказкой запустить `index rebuild`.

`config_digest` — SHA-256 по всем `*.json` внутри `.todoc/`, кроме `index/`, `cache/`, `generated/`.
`corpus_digest` — SHA-256 по отсортированным парам `(rel_path, content_hash)` плюс `config_digest`;
именно он решает, нужна ли пересборка. `created_at` в дайджест не входит: метаданные не должны
инвалидировать индекс.

Старая раскладка `generations/<12 hex>/` (один каталог на каждый запуск) удаляется при первой же
публикации.

### Что важно знать

- **Команда чтения не переиздаёт снимок.** Все читающие команды идут через единственную точку
  инвалидации `ensure_index()`: если `corpus_digest` совпал, снимок переиспользуется.
  `generation_id` при этом не меняется — по нему видно, что публикации не было.
- **Размер не растёт от числа запусков.** На демо: 337 КБ индекса при 2,4 МБ документов, и те же
  337 КБ после серии из 5 чтений и 5 пересборок. До редизайна там было 27 МБ и 94 снимка.
- **`index rebuild` по умолчанию не форсирует.** Без `--force` он переиспользует валидный снимок
  и возвращает `reused: true`; `--force` пересчитывает всегда.
- **`stats.json` делает повторное сканирование дешёвым.** Хеш файла берётся из кэша, если `mtime`
  и `size` не изменились, поэтому нетронутые файлы не перечитываются.
- **`status` не пересобирает индекс.** До первой пересборки он возвращает `generation_id: null`
  и нули; сначала выполните `index rebuild`.

## Устаревание зависимостей

Документ может объявить, от какого **фрагмента** другого файла он зависит — в `derived_from`
front matter (строки-якоря) или записи (объекты):

```yaml
derived_from: ["bench/results/benchmark.json#/meta/date@sha256:661df7…"]
```

Якорь — это `путь[#фрагмент]@sha256:…`, где фрагмент либо JSON Pointer (`/meta/date`), либо
`section:<заголовок>`. Хеш считается **от фрагмента**, а не от файла: правка несвязанного поля
не помечает документ устаревшим. Без якоря (`путь@sha256:…`) хеш берётся от всего файла.

`todoc stale` сравнивает заявленные хеши с фактическими и выдаёт
`staleness.dependency_changed` либо `staleness.dependency_missing` (severity `warning`).
Если указатель или заголовок перестал разрешаться, это тоже `dependency_changed`, но с сообщением
«якорь не разрешается» — средство другое: переименованный якорь, а не изменившиеся данные.

Подтверждение, что дрейф не релевантен:

```
todoc stale --ack <путь> --reason "причина" [--apply]
```

Без `--apply` команда только показывает план (review-first). Подтверждение пишется в тот же
front matter полями `stale_acknowledged_at`, `stale_ack_reason`, `stale_ack_hashes` и хранит
хеши фрагментов **на момент подтверждения**: как только любой из них изменится снова,
диагностика возвращается.

## Кэш парсинга

Ключ: `sha256(dataset_id | rel_path | content_hash | parser_version)[:16]`,
`parser_version` — `todoc-0.1.0`. Файл: `.todoc/cache/parse/<key>.json`.

Текущее поведение: кэш **пишется, но не читается для ускорения** — при сканировании запись
создаётся, если ключа ещё нет, а ускорения парсинга это не даёт (известная проблема).
Повреждённый файл кэша игнорируется (`read_parse_cache` возвращает `None`).

В демо кэш растёт от прогона к прогону: ключ включает хеш содержимого, поэтому каждая
изменённая версия файла добавляет новую запись, а устаревшие не удаляются.

## Атомарная запись файлов

Все записи (`records create`, `docs edit`, `fix`, публикация индекса, кэш) проходят через
`atomic_write`: временный файл в том же каталоге → `fsync` → `os.replace`. При исключении
временный файл удаляется. Это даёт: либо старое содержимое, либо новое; частично записанных
файлов не остаётся.

## Хеши

- `sha256:<hex>` содержимого файла — в `documents[].hash` и в WritePlan;
- `--if-hash` у `docs edit` и `fix` — оптимистичная блокировка: несовпадение даёт
  `write.hash_mismatch` и exit 5. У `records create` блокировки по хешу нет: план
  создаётся с `expected_hash=None`, а защита — «только создание»: занятый
  `record_id` даёт `record.duplicate_id`, занятый путь — `record.target_exists`,
  оба с exit 5. Флаг `--if-hash-new` принимается, но не проверяется
  (см. [известные проблемы](11-known-issues.md)).
