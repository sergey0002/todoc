# 16. Отчёт по остаткам

Дата: 2026-11-25. Всё ниже проверено запуском команд в рабочем дереве на `master` (`6311b825`).

## Что закрыто в этой итерации

| Пункт | Что было | Что стало | Как проверено |
|---|---|---|---|
| **P1-11** | Конституция обещала вычисляемое выражение `reps × weight_kg`, которого в ядре нет | Обещание убрано из спецификации: в типе объявляется `prompt` и `unit`, ядро суммирует одно числовое поле; ответ описывает фактически выполненную операцию | `records aggregate`, `check-config`; +8 тестов |
| **P1-3** | Кэш парсинга только писался — попадание не ускоряло ничего | Попадание читается, промах парсится и сохраняется, запись в затрагиваемые данные сбрасывает кэш | холодный 0.671 с → тёплый 0.212 с = **3.17×** на демо |
| **P1-9** | Обхода не было, только «держите файлы вне DATA_ROOT» | Три варианта с ценой и совместимостью, рекомендация **C затем B** | раздел P1-9 в [11-known-issues.md](11-known-issues.md) |
| **P2** | 3 пустых каталога-заглушки, мёртвый `RESERVED_ALIASES`, сниппет по первому совпадению, случайный `dataset_id` | всё четыре закрыто | +3 теста на сниппет, +5 на `dataset_id` |

Побочно найдено и закрыто: **K8 в бенчмарке засчитывался, когда измерять было нечем**.
Без PyYAML он сообщал «0 файлов разобрано, 0 с ошибкой» и оставался `pass` с 1.0 —
вызывающий код смотрел только на `bad == 0`, а ключ `skipped` вычислялся и не использовался.
Теперь это `fail` с пометкой «не измерено», а `pyyaml` входит в `extras [dev]`.

## Остатки

### 1. P1-9 — любое `.json` с `record_id` считается записью (ждёт решения)

**Единственный открытый дефект, который ломает работу агента сегодня.** Файл
`stray-input.json`, оставленный в корне датасета, попадает в индекс как запись, и последующий
`records create` с тем же `record_id` падает с `record.duplicate_id` — сообщение указывает не
на причину.

Механика: `_validate_records` считает записью любой отсканированный `.json` с ключом
`record_id`; ни каталог, ни тип не проверяются.

| Вариант | Цена | Совместимость |
|---|---|---|
| A. `records/` как единственная область записей | просто | **ломает** существующие базы |
| B. Явные правила игнорирования в `dataset.json` | средняя | не ломает: список пуст по умолчанию |
| C. Диагностика «запись вне объявленного пути» | малая | не ломает: предупреждение, не отказ |

**Нужно решение:** какой вариант. Рекомендация — C, затем B. Вариант A не реализован
намеренно: он молча перестанет видеть записи в существующих датасетах, а это нарушение
P1 (файлы — источник истины). Решать это за пользователя нельзя.

### 2. `ok skills` — авто-ремонт навыков (самый дешёвый из открытых)

`SKILL.md` в репозитории есть, но расхождение с фактическим CLI никто не проверяет. Когда
сигнатура команды меняется, навык устаревает молча, и агент узнаёт об этом по ошибке
выполнения, а не по диагностике.

Внешних зависимостей не требует: обход дерева Click уже есть (им измеряется число листовых
команд), осталось сравнить заявленное в `SKILL.md` с фактическим и выдать диагностику.

### 3. Метрики графа не доведены до CLI

`build_backlink_index` в `adapters/formats/markdown.py` написана и покрыта тестами, но
**из приложения не вызывается ни разу** — только из тестов. Обратные ссылки, изолированные
заметки и центральность через CLI недоступны; есть только `relations graph` (BFS по
типизированным рёбрам).

То есть механизм наполовину готов: индекс считается, но не выставлен наружу. Это и cheapest
пункт из функциональных, и единственный, где работа уже частично сделана.

### 4. P1-12 — `history.require_change_for_multi_file` (отложено осознанно)

Флаг из плана §17.4 не реализован, и причина содержательная: **пути многофайловой записи в
ядре не существует**. `apply_write_plan`, `apply_fix` и `apply_edit_ops` пишут ровно один файл;
`change apply` — единственная многофайловая операция, и она уже идёт через изменение.

Флаг был бы проверкой, у которой нечего проверять. Вернётся в очередь вместе с появлением
многофайловой записи вне изменений.

### 5. MCP, синхронизация, UI, семантический поиск (отложено)

Measured-разрыв с `open-knowledge` (см. [15-benchmark.md §4](15-benchmark.md)). Всё это
надстройки поверх CLI, на корректность текущего поведения не влияют.

Правило, которое при этом действует: ядро остаётся офлайновым и без БД (K30), всё тяжёлое —
только в optional extras. Иначе теряется главное измеренное преимущество.

### 6. K22 = 0.97 — единственный критерий не на максимум

`Recall@3 = 0.94` на 12 запросах: один размеченный релевантный документ не попадает в первые
три. Сниппет в этой итерации стал браться по наиболее релевантному окну, но на ранжирование
это не влияет — порядок результатов считается отдельно.

Что могло бы закрыть: семантический поиск как второй метод ранжирования (нужен
`sqlite-vec` или `sentence-transformers` — оба только optional extra, лексика остаётся
дефолтом). Цена несопоставима с выигрышем в 0.03 балла, поэтому пункт не в приоритете.

## Предлагаемый порядок

1. **P1-9** — нужно только решение, какой вариант; работа на несколько часов.
2. **`ok skills`** — без внешних зависимостей, закрывает молчаливое устаревание навыков.
3. **Метрики графа в CLI** — функция уже написана и протестирована, осталось выставить.
4. P1-12 — после появления многофайловой записи вне изменений.
5. MCP / синхронизация / UI / семантический поиск — когда появится запрос на них.
