# 11. Известные проблемы

Каждый пункт проверен запуском команды 2026-11-25; приведено воспроизведение. Полный исторический
список находок — в [аудите реализации](../../plan/audit-implementation.md). Что измерено и закрыто
в этой итерации — в [15-benchmark.md](15-benchmark.md).

## Критичные (P0)

Открытых P0 нет. Последний (`record_id` с двоеточием) закрыт 2026-11-25 — см. «Исправлено» ниже.

## Важные (P1)

### P1-1. Закрыт 2026-11-25 — индекс пересобирался на каждую команду чтения

Все читающие команды шли через `rebuild_index()`. Было: `docs search` 1511 мс, `docs read`
1059 мс, `records list` 1060 мс на 256 документах при `status` 150 мс.

Закрыто введением единственной точки инвалидации `ensure_index()`: снимок переиспользуется,
пока `corpus_digest` (SHA-256 по парам `(rel_path, content_hash)` плюс `config_digest`) не
изменился. `stats.json` хранит `hash/mtime/size`, поэтому нетронутые файлы не перечитываются.
Стало по бенчмарку: `docs search` 624 мс, `docs read` 168 мс, `records list` 160 мс.

### P1-2. Закрыт 2026-11-25 — поколения индекса не удалялись

Каждая пересборка добавляла каталог `generations/<12 hex>/`, поэтому размер `.todoc/index/`
рос с каждой командой чтения: в демо накопилось 94 поколения и 27 МБ при 2,4 МБ документов.

Закрыто переходом на один снимок `current/`, который перезаписывается на месте; прежняя
раскладка `generations/` удаляется при первой публикации. Стало: 337 КБ, и тот же размер
после серии из 5 чтений и 5 пересборок.

### P1-3. Кэш парсинга только пишется

Файлы в `.todoc/cache/parse/` создаются, но на скорость парсинга не влияют.

### P1-4. Мёртвые флаги

| Флаг | Поведение |
|---|---|
| `doctor --scope` | игнорируется: `--scope nonsense` всё равно выполняет все 3 проверки |
| `records create --if-hash-new` | принимается, не используется |

`docs new --template` больше не мёртвый: флаг принимает id типа документа или путь
к файлу шаблона и реально подставляет содержимое (см. `04-config-and-types.md`).

### P1-5. `docs read`: `--rows` применяется до `--where`

`--rows 3 --where doc_type=guide` вернул 0 строк, `--rows 75 --where doc_type=guide` — 3.

### P1-6. `status` показывает нули до первой пересборки

`status` читает опубликованное поколение; сразу после `init` — `generation_id: null`, `documents: 0`.

### P1-7. Нет CI, контрактных тестов и лицензии

Проверено: нет `.github/workflows`, нет `LICENSE`. Тесты (437) и покрытие 100 % запускаются только локально.

Отдельно про упаковку: `pyproject.toml` объявляет `license = { text = "MIT" }`. Сборка
(`python -m build`) проходит, wheel и sdist создаются, но setuptools выдаёт предупреждение,
что эта форма устарела и к **2027-02-18** её нужно заменить на SPDX-строку
(`license = "MIT"` плюс `license-files`), иначе сборки перестанут поддерживаться.
Файла `LICENSE` при этом нет, то есть заявленная лицензия не приложена к репозиторию.

### P1-8. У трёх JSON-диагностик нет позиции

`json.duplicate_key`, `json.invalid_constant`, `json.too_deep` не несут `line`/`column`:
`object_pairs_hook` и `parse_constant` в стандартном `json` позицию не получают.
Это единственный незакрытый критерий бенчмарка — K7 = 0.55 (6 из 11 диагностик с номером строки).
Решение: собственный сканер JSON либо зависимость вроде `jsonscanner`/`ijson`.

### P1-9. Любой `.json` внутри DATA_ROOT считается записью

Проверено: файл `stray-input.json`, положенный в корень датасета, попадает в индекс как запись,
и последующий `records create` с тем же `record_id` даёт `record.duplicate_id`.
Следствие для агентов: входные и временные файлы нужно держать вне DATA_ROOT (бенчмарк так и делает).
Решение: либо каталог `records/` как единственная область записей, либо явное игнорирование по правилу.

### P1-10. Закрыт 2026-11-25 — `fix --apply` писал путь от корня, а не от файла

`suggested_fixes[].replacement` брался из индекса `by_basename`, где пути отсчитываются от
DATA_ROOT, тогда как Markdown-ссылка резолвится от каталога файла: фикс оставлял ссылку
битой. Исправлено функцией `_link_replacement()` — путь пересчитывается относительно
каталога файла (`posixpath.relpath`), а для wikilink остаётся stem. Попутно закрыт соседний
дефект: `fix --apply` на wikilink падал в `fix.cannot_apply`, потому что `old_target`
выводился только из формы `](…)`. Подробности и воспроизведение — в таблице «Исправлено».

### P1-11. `metric_fields.<field>.formula` объявляется, но игнорируется

`records aggregate` всегда возвращает `sum(<metric>)`: формула собирается строкой
`f"sum({metric_field})"` в `query.py:90` и не читается из описателя типа. Проверено:
замена `metric_fields.value.formula` на `reps * weight_kg` в `type.json` не меняет вывод —
остаётся `sum(value)`.

Следствие: сценарий S7 конституции («сумма `reps × weight_kg` в `kg·reps`») не выполняется —
поддерживается только сумма одного числового поля. Единицы при этом работают: они берутся
из значения записи и проверяются по группам (`group_units`), а смешение единиц внутри одной
группы даёт `query.unit_mismatch`.

## Незначительные (P2)

- Пустые порты-заглушки (`ports/`, `adapters/indexes/`, `adapters/cache/`, `adapters/search/`) —
  контракт портов не описан кодом.
- `RESERVED_ALIASES` объявлен, но в резолве не участвует.
- Фрагмент поиска строится по первому совпадению, а не по наиболее релевантному.
- `dataset_id` генерируется случайно при `init`, что мешает воспроизводимым демо-датасетам.
- `SKILL.md` в репозитории есть, но авто-ремонта навыков (`ok skills`) нет.
- Нет MCP-адаптера, синхронизации и UI — measured-разрыв с `open-knowledge`
  (см. [15-benchmark.md §4](15-benchmark.md)).

## Приоритет исправлений

1. P1-8 (позиции в JSON-диагностиках) — закрывает K7 до 1.0; единственная частичная оценка бенчмарка.
2. P1-11 (формула агрегации из типа) — без этого сценарий S7 не выполняется.
3. P1-3 (рабочий кэш парсинга) — скорость.
4. P1-7 (CI + LICENSE + SPDX до 2027-02-18) — воспроизводимость проверки качества и релиз.

Закрыты 2026-11-25: P0-1, P1-10, P1-1, P1-2 (см. «Исправлено» и отметки выше).
