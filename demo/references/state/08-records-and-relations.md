# 08. Записи, отношения и история фактов

JSON-запись содержит `record_id` и `entity_type`. Тип сущности определяет допустимые поля и их схемы. Правила пути, обязательные поля, представления и метрики задаются описателем типа. `docs list` может показать физический JSON как документ, а `records list` возвращает логическую запись.

| Операция | Контракт |
|---|---|
| Создание | `records create --type T --input-file FILE` готовит план. `--apply` создаёт файл с защитой от повторного ID и занятого пути |
| Чтение | `records read --id ID --record-view NAME` возвращает полную или именованную проекцию. `--view` поддерживает совместимый старый вызов. Неизвестное представление даёт fallback |
| Правка | `records edit` использует JSON-патч метаданных и проверяет схему. `records status` меняет статус записи по описателю |
| Выборка | `records list` фильтрует по типу, датам, отношению `TYPE=ID`, тегам и атрибутам перед пагинацией |
| QuerySpec | `records query --query-file FILE` использует `entity_type`, `filters` и `limit`. Фильтры записи поддерживают `$in`, `$gte` и `$lte`. Дополнительно применяются общие фильтры метаданных |
| Метрики | `records aggregate --type T --metric FIELD` суммирует числовое поле, поддерживает группировку и проверяет совместимость единиц в каждой группе |

`records list` и `records query` проверяют `entity_type` до чтения индекса: известный тип без записей даёт пустой успех, неизвестный — `query.unknown_type`, тип из другого пространства имён — `query.namespace_mismatch`. QuerySpec принимает `schema_version: 1`, `name`, `entity_type`, `filters`, `limit` и `sort_hint`; неизвестные ключи, операторы и версия дают `query.invalid_file`.

### QuerySpec: операторы и пример

`filters` — объект «поле → условие». Поле может быть точечным путём (`volume.value`). Условие — либо скаляр (точное равенство), либо объект с одним из операторов `$in`, `$gte`, `$lte`:

```json
{
  "schema_version": 1,
  "name": "heavy-workouts",
  "entity_type": "workout",
  "filters": {
    "date": {"$gte": "2026-11-01", "$lte": "2026-11-30"},
    "volume.value": {"$gte": 50},
    "status": {"$in": ["done", "planned"]}
  },
  "limit": 50
}
```

- `$in` сравнивает значение целиком: для поля-списка (например, `tags`) он не означает «содержит элемент». Теги отбирайте флагами `--tag-in`/`--tag-all`.
- `$gte`/`$lte` сравнивают числа или строки; несравнимые типы дают `query.invalid_file`.
- Неизвестный оператор или лишний ключ — `query.invalid_file`; файл проверяется до чтения индекса.
- Готовый минимальный пример — `demo/.todoc/queries/tasks-by-project.json`.

Структурированная правка использует массив `metadata` с операциями `set`, `remove`, `add_item` и `remove_item`. Ключ идентификации и обязательные поля защищены контрактом. Для применения передайте хеш предпросмотра.

## Связи и время

Типизированное ребро хранит `type_id` и `target`. Валидатор проверяет известность типа и разрешимость цели, строит координаты исходного отношения. Граф и дерево сохраняют направление и происхождение. Дерево показывает циклы и сохраняет контекст предков при пагинации. Упоминания из Markdown имеют отдельную метку происхождения.

`--as-of` в `records query` ограничивает факты временем правды. Интервал закрывается по `valid_to` или `superseded_at`, открывается по `valid_from`. `timeline` объединяет события журнала и темпоральные факты. `records undo-relation` восстанавливает отношение по сохранённой истории, с проверкой `--if-hash` при применении.
