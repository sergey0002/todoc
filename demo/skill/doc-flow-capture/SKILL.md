# Захват флоу-документа

## Когда применять

- Изменение (`change:<slug>`) или задача затронула бизнес-процесс;
- появился новый процесс, который нужно описать как флоу.

## Шаги

1. Прочитать эталон типа: `todoc types prompt flow-doc --op create --root KB`.
2. Собрать факты: запись `flow:<slug>` (актор/состояния/исходы), затронутые
   `rule:<имя>-v<N>` (examples = строки таблицы решений), `change:<slug>` (зачем).
   Нет записи флоу — создать её сначала: `todoc types prompt flow --op create`.
3. Черновик: `todoc docs new --root KB --type flow-doc --title "<Название>" --path flows/<имя>.md`
   (явный латинский путь), наполнить 4 секции: Жизненный цикл (stateDiagram из states),
   Таблица решений (строки из examples правил; колонка «Режим»: auto | ask-user | пусто),
   Диаграмма исходов (flowchart = визуализация таблицы), Lineage (поле/откуда/ответственный).
4. Обновление существующего: если это сгенерированная витрина (`flow render --write`) — правь запись-источник `flow:*`, запусти `todoc sync --root KB <путь-к-записи>` и пересобери витрину; если ручной `flow-doc` без `derived_from` — правь напрямую и выполни `todoc sync --root KB <путь>`.
5. Ревизия правил: правило изменилось — новая запись `rule:<имя>-vN+1` + ребро
   `supersedes`; существующую не редактировать.
6. Проверка: `todoc validate --root KB --all` — 0 диагностик; `docs read --section`
   по каждой секции; скан заглушек (TBD/TODO) пуст.

## Стоп-условия

- Условий переходов нет в данных — остановись и уточни, не выдумывай.
- Ссылки на несуществующие записи/файлы не ставить: текстовый ID или создать запись.
