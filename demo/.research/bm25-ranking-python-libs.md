# Ресёрч: Python-библиотеки BM25/BM25F и двуязычного стемминга (`RU+EN`) поверх JSON-индекса `todoc`

- Тип: `research-report`
- Дата среза: 2026-11-26 (живая проверка PyPI JSON API и GitHub API)
- Идентификатор: `doc:.research/bm25-ranking-python-libs.md`

## 1. Архитектурное ограничение: единый JSON-кэш `todoc` (без второго хранилища вроде SQLite)

В `todoc` (`src/todoc/application/registry.py`) весь индекс уже устроен как атомарный переносимый **JSON-снапшот** в `.todoc/index/current/`:
- `folders.json`, `documents.json`, `records.json`, `relations.json`, `mentions.json`, `diagnostics.json` (в сумме ~570 КБ на 450+ документов и 205 записей);
- плюс пофайловый JSON-кэш разбора `.todoc/cache/parse/<key>.json` (чтобы не перепарсивать неизменившиеся файлы).

**Следствие:** тащить параллельную БД со своим бинарным форматом на диске (`SQLite FTS5`, бинарные сегменты `Whoosh` или `Tantivy`) не нужно — это создаст второй рассинхронизируемый кэш. Все выборки (`docs`, `records`, `tree`, `skills`) должны фильтроваться по единому JSON-снапшоту в памяти, а поисковый индекс должен лежать **там же в виде JSON** (например, `.todoc/index/current/lexical.json` + токены полей в `.todoc/cache/parse/*.json`).

Значит, нам нужны не «серверы/БД полнотекстового поиска», а **готовые Python-библиотеки для лингвистики (`RU+EN` стемминг Портера), in-memory / JSON-сериализуемого `BM25`/`BM25F` и нечёткого `grep`-матчинга**.

## 2. Слой А — Стемминг Портера и его лучшие аналоги в Python (`RU + EN`)

Классический **Porter1 (1980)** работает только с английской латиницей. Сам Мартин Портер развил его в **Snowball**: **Porter2** для английского + официальный **русский стеммер Портера/Snowball** для кириллицы. Эту часть точно нужно брать готовой библиотекой:

| Библиотека (PyPI) | Актуальная версия (дата) | Лицензия | Зависимости и вес | Языки | Особенности | Вердикт для JSON-кэша `todoc` |
|---|---|---|---|---|---|---|
| **`snowballstemmer`** | `3.1.1` (2026-06-03) | `BSD-3-Clause` | **0 зависимостей**, чистый Python (~150 КБ) | **29 стеммеров** (`russian`, `english` Porter2 и др.) | Официальный пакет авторов Snowball. Если установлен `PyStemmer`, **автоматически** переключается на C-ускоритель без смены API. | **№1 Базовый выбор** (обязательно брать) |
| **`PyStemmer`** | `3.1.0` (2026-05-22) | `MIT / BSD` | **0 Python-зависимостей**, Cython/`libstemmer_c` (71 готовый wheel) | Те же **29 языков** (`russian` + `english`) | В **25–30× быстрее** чистого Python, 100% совместим со `snowballstemmer`. | **№1 Опциональный ускоритель** (`todoc[fast]`) |
| **`pymorphy3`** | `2.0.6` (2025-10-09) | `MIT` | `dawg2-python` + `pymorphy3-dicts-ru` (~15 МБ) | Только русский (нужен Porter2 для `EN`) | Словарная лемматизация (`людям → человек`, `задачами → задача`), точнее суффиксного стемминга на сложных падежах (RusBEIR 2025), но весит ~15 МБ. | Опция `todoc[ru-morph]`, если мало стемминга |
| **`nltk`** | `3.9+` | `Apache-2.0` | ~15–50 МБ + внешняя докачка корпусов | 15+ языков | Избыточен и неудобен в офлайне. | **Не брать** |

## 3. Слой Б — Готовые библиотеки ранжирования `BM25` / `BM25F` для работы по JSON-индексу в памяти

Сравнение библиотек именно через призму **«храним индекс в JSON / считаем в памяти по отфильтрованной выборке с приоритетами `tags > title > headings > body`»**:

| Вариант | Версия PyPI (релиз) | Зависимости | Хранение прямо в JSON | Приоритеты полей (`BM25F` / boosts) | Как работает на выборке `-q q1 -q q2 --limit 100` | Вердикт |
|---|---|---|---|---|---|---|
| **1. `lunr` (`lunr.py`)** + `snowballstemmer` | `0.8.1` (2026-11-01, `MIT`) | **0 базовых зависимостей** (чистый Python; на нём работает поиск в MkDocs) | **Да, нативно!** `idx.serialize()` даёт чистый JSON-объект для `.todoc/index/current/lexical.json`, `Index.load(data)` мгновенно поднимает его в память | Да: `boost` на каждое поле (`tags: 8`, `title: 5`, `headings: 2.5`, `body: 1`) | Встроенный BM25, джокеры `*grep*`, нечёткий поиск `word~1`, кастомный стеммер в pipeline (`snowballstemmer` `RU+EN` вместо `nltk`). Совместим с `Lunr.js` для будущего веб-UI! | **Лучшая готовая JSON-native библиотека 1-в-1 под архитектуру `todoc`** |
| **2. `snowballstemmer` + компактный `BM25F` в `search.py` (+ опц. `rapidfuzz`)** | `3.1.1` (`BSD-3`) | **0 лишних зависимостей** | **Да, 100% наш формат** `.todoc/index/current/lexical.json` + кэш токенов по файлам в `.todoc/cache/parse/*.json` | **Полный классический `BM25F`** (и веса полей `W_f`, и разная нормализация длины `B_f`: `tags_B=0.0`, `title_B=0.25`, `body_B=0.75`) | ~70 строк чистой математики `math.log` поверх JSON-словаря: мгновенно пересортировывает **любое** уже отфильтрованное множество (даже без отсечения элементов со `score=0`) + буст точной `grep`-подстроки | **Самый гибкий и управляемый вариант** (вся сложная лингвистика в `snowballstemmer`, а формула весов под полным контролем) |
| **3. `bm25s`** (`xhluca/bm25s`) | `0.3.16` (2026-10-28, `MIT`) | **`numpy`** (~51 МБ в `.venv`) | Частично (словарь в JSON + матрицы весов `.npy`) | Нет `BM25F` из коробки (нужно складывать скоры отдельных индексов полей) | Сверхбыстрый спарс-скоринг на NumPy (в 500× быстрее `rank-bm25`), варианты `lucene`/`robertson`/`bm25+`, прямая поддержка `PyStemmer` | Имеет смысл только если в проекте допустим `numpy` и базы `>50k` файлов |
| **4. `whoosh-reloaded`** (`RamStorage`) | `2.7.5` (`BSD-2`) | Чистый Python (`cached-property`) | Нет (свой бинарный формат сегментов; либо перестраивать `RamStorage` на лету) | Эталонный `BM25F` + встроенные Snowball `RU+EN` | Хорош как готовый BM25F-движок в RAM на лету для сотен документов, но в JSON свой индекс напрямую не сериализует | Избыточен при наличии собственного JSON-кэша |
| **5. `rapidfuzz`** *(компаньон для нестрогого `-q`)* | `3.14.6` (2026-08-30, `MIT`) | **0 Python-зависимостей** (102 готовых C++ wheel) | Не требует индекса (считает по строкам из JSON на лету) | Применяется с весами по полям (`title`, `tags`, `path`) | Быстрый C++ расчёт частичных вхождений и опечаток (`partial_ratio`, Левенштейн) для мягкого поиска в стиле умного `grep` | Отличная добавка к вариантам 1 или 2 для устойчивости к опечаткам |
| ❌ **`rank-bm25`** | `0.2.2` (2022-02) | `numpy` | Нет (пересчёт с нуля в RAM) | Нет | Заброшен с 2022 г., медленный, без полей | **Не брать** |

## 4. Как это ложится на единый JSON-пайплайн всех выборок `todoc`

1. **При парсинге файла (`write_parse_cache` в `.todoc/cache/parse/<key>.json`):**
   - Для каждого `.md`, `.json` (`record`) и `.config.json` папки один раз извлекаются поля (`id`, `tags`, `title`, `headings`, `body`) и прогоняются через **`snowballstemmer`** (`russian` + `english`). Неизменившиеся файлы при пересборке индекса не перестеммируются вообще!
2. **При публикации снапшота (`.todoc/index/current/lexical.json`):**
   - Рядом с `documents.json` и `records.json` атомарно пишется `lexical.json` (либо сериализованный индекс `lunr.py`, либо компактная карта `BM25F`-частот и средних длин полей).
3. **При любом запросе выборки (`docs`, `records`, `tree`, `skills`):**
   - Сначала в памяти по `folders.json` / `documents.json` / `records.json` отрабатывают **все структурные фильтры** (`--within`, `--dir-type`, `--doc-type`, `--entity-type`, `--tag-in`, статусы) → получаем точный список кандидатов.
   - Затем поверх этого списка считается сложная релевантность по `-q "запрос 1" -q "запрос 2"` (`BM25F` с приоритетами `id > tags > title > headings > folder_cfg > body` + бонус за точное подстрочное совпадение как в `grep`).
   - В режиме поиска остаются совпавшие (`score > 0`); при флаге сортировки выборки по релевантности **все кандидаты сохраняются**, выстраиваясь от максимального `score` к `0`, и обрезаются по `--limit 100`.

## 5. Итоговая выжимка: какой стек библиотек брать

- **Обязательное ядро (1 лёгкий пакет без зависимостей):** **`snowballstemmer>=3.1`** (+ опционально **`PyStemmer>=3.1`** для 30× C-ускорения).
- **Для самого ранжирования по JSON-кэшу — выбор из двух чистых вариантов без бинарных БД и без `numpy`:**
  1. **`lunr>=0.8`** (если хочется 100% готовую библиотеку, которая из коробки сериализует BM25-индекс с бустами полей прямо в JSON и понимает `*wildcards*` и `~fuzzy`);
  2. **Собственный `BM25F`-ранжировщик на ~70 строк в `application/search.py` поверх `lexical.json` + опционально `rapidfuzz>=3.14`** (если нужен настоящий полевой `BM25F` с разной нормализацией длины `tags_B=0` vs `body_B=0.75` и полным контролем над пересортировкой любых выборок без отсечения).
