# Архитектурное предложение: модульный CLI и единые границы данных todoc

**Статус:** предложение для обсуждения, не утверждённый план и не описание уже
реализованной архитектуры. **Срез аудита:** рабочая ветка `arena/c379c82e-todoc`,
с незакоммиченными изменениями поверх `7b8adedf3c1a08375b7e681628a6171cf54a8f32`;
удалённый master на момент проверки — `c9256c2f5401e4f4be400382a9773f6f39f3d4d1`.
Срезы ещё не объединены. До реализации их нужно перепроверить. Документ не
разрешает merge, изменение правил, реализацию фич или перенос данных.

**Новая сессия:** пользователь выбрал чистый master и публикацию только четырёх
документов; старые тесты и код не переносятся. Проверить наличие документов и
создать новые регрессии по инвариантам плана unified. Порядок работ задаёт
`docs/plan/todoc-master-refactoring-plan.md`; §§13–20 этого документа объясняют
старт и архитектурные гейты SOLID. Исторические сведения о старом снимке не
означают, что его изменения реализованы в master.

## 1. Короткий ответ

**Да, системный рефакторинг разумен:** проблемы касаются не только формы ответа
CLI. Сейчас обязанности распределены между крупным `cli.py`, `DatasetContext`,
сервисами, индексом, parse-кэшем и кодом истории; некоторые команды обходят
общие границы. Если сначала переписать команды для единого вывода, а затем
вводить драйверы, часть обработчиков и тестов придётся менять ещё раз.

**Но не рекомендую переписать всё одним большим коммитом и не рекомендую
пропускать вообще каждое чтение через постоянный кэш.** Предлагается единый
application API и единые логические точки доступа к данным, независимые порты
индекса и истории, модульный Click-адаптер и единый конвейер вывода. Новые
границы вводятся по вертикальным срезам с проверками, сохраняя реальные данные
и уже работающие сценарии. **Источник истины — файлы датасета; индекс —
производная оптимизация; история — ценные невосстанавливаемые данные.**

Унифицированный доступ к выборкам не равен обязательному обращению к дисковому
кэшу: при cold/stale/corrupt cache или работе без права записи сервис может
построить актуальное представление в памяти из файлов. Чтение конкретных исходных
байтов, валидация, `doctor`, история, `state` и исправление повреждённого индекса
имеют отдельные потребности и не должны зависеть от здорового кэша.

Пользовательский вопрос — **выбор направления**, а не разрешение автоматически
реализовать SQLite, плагины, новые команды, сетевые сервисы или изменить
пользовательскую семантику. Сначала нужны решения из §12 и отдельный план.

## 3. Варианты и рекомендация

| Вариант | Плюсы | Минусы и решение |
|---|---|---|
| A. Только унифицировать вывод | Быстрее получить единый внешний JSON. | Оставляет обходы storage, дублирование query и записи; будущая SQLite-работа снова затронет CLI. Недостаточно. |
| B. **Модульное ядро и миграция по срезам** | Общие контракты, совместимость и проверяемая замена границ; можно сохранить текущий JSON и живые функции. | Потребуются время на contract/golden-тесты, временные адаптеры и строгий контроль зависимости. **Рекомендуется.** |
| C. Полный big-bang rewrite CLI + ядра + SQLite | Теоретически меньше временных переходников. | Одновременно меняются грамматика, данные, драйверы, производительность и история; трудно локализовать регрессии и восстановить состояние. Не рекомендую. |
| D. Только абстрактный plugin framework | Позволяет декларировать расширяемость. | Без реальных адаптеров и общих тестов интерфейс может маскировать прямой доступ к JSON; нагрузка и API замораживаются преждевременно. Не делать первым. |

«Полный рефакторинг» здесь означает целевой охват **всех** семейств CLI и
пересечение с application/storage, а не обязательную замену каждого рабочего
алгоритма. По каждому участку сначала решать: оставить, извлечь, адаптировать,
заменить или удалить после миграции. Временные совместимые обёртки допустимы
внутри ветки, с владельцем и сроком удаления, но не два бессрочных контрактных
ядра и не выбор поведения по случайному обработчику.

## 4. Целевая архитектура

```text
 CLI Click                   будущие MCP / UI / SDK (не реализуются сейчас)
 argv → Request              вход → Request
           \                   /
            Application facade / composition per invocation + dataset
                ├─ capability/discovery + validation of request
                ├─ Query use cases → QuerySession / ReadModel
                │       ├─ SourceReader + scope/config/parse
                │       ├─ IndexRead + ParseCacheRead (optional acceleration)
                │       └─ HistoryRead / source-specific reads where required
                ├─ Action use cases → Plan → explicit Apply + actual outcome
                │       ├─ SourceWriter + IndexWrite / cache invalidation
                │       └─ HistoryWrite + independent BeforeImageSource
                └─ typed Result + diagnostics + provenance
                              ↓
             view / fields / pagination → envelope → renderer → transport
```

Стрелки — упрощённый поток данных, а не доказанная диаграмма импортов или
утверждение, что эти классы уже существуют. `facade`, `QuerySession` и подобные
названия обозначают роли: общая фасадная точка не должна превращаться в один
бог-объект/сервис-локатор. Порты — небольшие внутренние интерфейсы по реальным
потребностям, не обязательная иерархия классов. Направления зависимостей,
владение поведением и проверка подстановки конкретизированы в §§18–20. Где
достаточно существующего сервиса или чистой функции, не создавать посредник
ради названия.

### 4.1. Обязанности и границы

1. **Transport:** Click разбирает аргументы, вызывает общий dispatcher,
   сопоставляет результат с exit code и выводит готовые байты. Он не владеет
   JSON-path индекса, алгоритмами history, парсингом Markdown или SQL. Парсинговые
   ошибки Click тоже попадают в согласованный transport-контракт; отдельные
   CliRunner и subprocess тесты проверяют оба пути. `--help` и shell UX не
   ломаются молча. Будущий MCP вызывает application напрямую, а не парсит stdout.
2. **Composition root:** один явный состав зависимостей на вызов и датасет;
   рабочие built-in JSON/JSONL адаптеры, конкретный источник образов, scope,
   конфигурация и часы передаются сервисам явно. Разные roots не делят глобальные
   переменные и mutable состояние. Реальный CLI по умолчанию работает без выбора
   драйверов пользователем; тест может передать независимые fake-компоненты.
3. **Application:** use cases владеют правилами операций, ошибками и эффектами.
   Результат не содержит Click objects и не зависит от выбранного рендера.
   Доступ к физическому файлу-источнику допустим через контролируемую границу
   filesystem, в том числе на чтении: запрет обхода относится к **деталям
   хранилища кэша/истории**, а не ко всем файловым операциям.
4. **Domain/query:** типизированные идентичность, область, связи, типы, время,
   диагностики, порядок, completeness и provenance; унифицировать общие
   механизмы, не заставляя документ, запись, скил и историю иметь одинаковые
   искусственные поля. История, физическое дерево и граф — разные модели.
5. **Output:** одна точка формирования envelope и таблица error → exit;
   renderer только преобразует данные в JSON/table/Markdown и не ходит в ФС,
   сеть или драйверы. `next_actions` — данные, не исполняемый код. View и формат
   независимы, но выбор view допускается только у поддерживающих его команд.
6. **Adapters:** JSON/JSONL, filesystem, Git, formats; правила допустимой области
   принадлежат application/policy, а безопасное выполнение и containment для
   конкретной файловой операции проверяются filesystem-адаптером. Эти проверки
   не вырезаются при переносе и не доказывают устранение всех TOCTOU-гонок.
   Возможность SQLite и внешних адаптеров — отдельный этап, не требование сейчас
   сделать публичный плагинный API.

**Правило зависимости:** transport → application → domain/ports;
implementations adapters подключаются в composition root. Проверять не только
импорты, но и runtime-тестами с fake: локальный файловый доступ к источникам
может быть оправдан, скрытый обход `journal`, `objects` или JSON-shards — нет.

### 4.2. Возможная файловая карта — не зафиксированное API

```text
src/todoc/
  cli.py                    # совместимый entry point main
  cli_commands/             # Click-группы и аргументы по семействам
  application/              # существующие и выделяемые use cases / coordinator
  domain/                   # смысловые модели, инварианты и ошибки
  ports/                    # небольшие интерфейсы по реальным операциям
  adapters/filesystem/      # источник данных и защита границ
  adapters/index/           # существующий JSON + parse-cache; SQLite позже
  adapters/history/         # JSONL/objects; git/embedded как before-image source
  output/                   # capability, envelope, views, renderers
  composition.py            # встроенные фабрики, per-dataset зависимости
```

`cli_commands` и остальные имена эскизные; Python одновременно не допускает
одинаковые имена модуля и пакета с неоднозначным разрешением. Выбрать структуру
после инвентаризации, сохранить `todoc.cli:main`, `python -m todoc`, packaging и
тесты импорта. Не перемещать 60+ команд разом до фиксации контрактов.

## 5. «Все запросы через кэш»: что именно унифицировать

### 5.1. Рекомендуемая семантика

**Все выборки — через общие application/query-сервисы и общий scope, а не
обязательно через постоянный индекс.** Сервис выбирает способ получения данных
по контракту и честно сообщает ограничения. Нет неявного обновления/создания
индекса или истории при read/preview.

| Операция | Основные данные и допустимая оптимизация | Что нельзя скрыть |
|---|---|---|
| Списки, дерево, граф, search/suggest, фильтры и подсчёты | Проверенный ReadModel: опубликованный индекс при доказанной актуальности либо свежий in-memory scan/parse; поиск и ранжирование — отдельные стадии. | Устаревший/неполный корпус, чужой dataset, изменённые folder config/types/ignore, ошибки доступа; фильтр до лимита и честная полнота. |
| `docs read`, секция и исходный текст | Контролируемое чтение исходных байтов, идентичности и hash; индекс помогает разрешению пути/метаданных, но не подменяет источник. | Изменение между выборкой и чтением, symlink/escape, несовпадение ID и hash, недоступный источник. |
| `validate`, `check`, сканирование и `doctor` | Исходные файлы и конфигурации; корректный parse-cache возможен как ускоритель, диагностика индекса может читать его без доверия к нему. | Ошибки источника, неполный обход, битый индекс, отсутствие прав. Проверка должна работать и когда индекс отсутствует/повреждён. |
| `log`, `show`, `blame`, timeline, tags/change, revert, GC/export | История через собственный `HistoryStore`; для образов — независимая политика embedded/git. Не реконструировать историю из индекса. | Повреждение, пропуски, неоднозначный rev, отсутствие образа, различие текущего файла и исторического содержимого. |
| `state`, конфигурация типов, discovery | Их собственные источники и сервисы; metadata-кэш — только если явно корректен. | Dataset scope, неверную конфигурацию или различия XDG state и истории. |
| Preview/apply и `index rebuild` | Preview читает входы и готовит план без записи; apply повторно проверяет предусловия и явно публикует/пишет. | Изменение после preview, отказ отдельной стадии, частичное применение, права и безопасность пути. |

**Пример пути поиска:** request → проверка root/scope и config → получить
проверенный индекс *или* построить in-memory представление → semantic filter →
ranking → стабильная сортировка и tie-break → лимит/cursor → поля/view →
envelope. Новый backend может выполнять части pipeline у себя, но обязан доказать
эквивалентность по принятому контракту; нельзя молча заменить ранжирование или
применить limit до фильтра. Нельзя требовать, чтобы каждый драйвер загружал всё
в память: допускаются итерация и pushdown с теми же порядком и полнотой.

### 5.2. Свежесть и ошибки

- Результат чтения индекса должен различать как минимум `missing`, `valid`,
  `stale`, `corrupt`, `inaccessible`; `valid` относится к **проверенным** входам
  и версии. Наличие `CURRENT.json` не доказывает актуальность.
- Fingerprint учитывает идентичность dataset, входные байты, пути и структуру,
  типы, конфиги и фактически действующие правила отбора/алгоритма. Что именно
  входит в каждый результат — часть контракта; mtime + size сами по себе не
  доказывают неизменность. Нельзя выдавать ошибку чтения файлов за cache miss.
- Parse-cache ключуется путём/областью, content hash и версиями разбора; при
  изменении зависимостей он не должен отдавать устаревшие результаты. Для cold
  read используется память; сохранение/инвалидация — явные действия записи.
- Файлы могут изменяться во время scan. Определить проверку снимка/повторный
  fingerprint, ограниченный retry или ошибку. Эти меры не доказывают полную
  атомарность файловой системы и защиту от ABA/TOCTOU.
- Повреждённый кэш допустимо обходить или чинить только по определённой
  политике: read не пишет, `doctor` показывает проблему, явный rebuild не
  должен зависеть от успешного чтения повреждённого опубликованного индекса.
  Историю rebuild никогда не удаляет.

## 6. Границы драйверов: что нужно сейчас и что позже

### 6.1. Внутренние контракты

| Роль | Сейчас: обязательный минимум | Позже, по отдельному решению |
|---|---|---|
| Index read/write | Логические snapshot/query, состояния и диагностики, публикация с предусловиями, статистика и parse cache; существующий JSON адаптер + независимый тестовый in-memory fake. | SQLite-индекс, миграции схемы и измеренный incremental update, возможность отдельных запросов/индексов, FTS5. |
| History read/write | События в устойчивом порядке, полные поля, refs/head/tags, проверка blob digest, append, план и применение GC, export/diagnostics; JSONL/refs/objects адаптер + fake. | SQLite history, проверенная миграция и backup, совместимый экспорт, восстановление, конкуренция и crash tests. |
| Before-image source | Сохранить текущий `HistoryBackend` для git/embedded и его деградацию/gap-filling. Embedded должен работать без Git. | Совместимость каждого источника с каждым реальным history store; выбор политики и fallback по явной конфигурации. |
| Source/filesystem | Идентичность root, containment, проверка symlink, чтение и запись исходников, создание/replace с известными гарантиями. | Более сильная защита гонок и recovery, если отдельно реализована и проверена. |

Индекс и история выбираются **независимо**; выбор before-image source не должен
переключать формат журнала. Будущий интеграционный тест — четыре комбинации
JSON/SQLite индекс × JSONL/SQLite history, каждая с применимой политикой
embedded/git; наличие fake сейчас не доказывает совместимость SQLite.

### 6.2. История и хранение

- Не переименовывать существующий `HistoryBackend` в полный `HistoryDriver`:
  он покрывает другую ответственность. Не использовать для истории интерфейс
  «можно удалить и пересобрать из файлов», пригодный для derived index.
- JSONL writer вычисляет `rev` как первые 12 hex SHA-256 от канонической строки
  события без `rev`; reader добавляет rev из исходной обрезанной строки при
  отсутствии поля. Дубликаты и коллизии возможны. Миграция не должна молча
  пересериализовать старые строки, терять unknown fields или менять порядок,
  refs и оригинальные образы. Отдельно решить ambiguous revisions.
- Для обычного чтения и операций, обещающих полноту или меняющих историю,
  явно определить политику повреждений: битый UTF-8/JSON, оборванная запись,
  отсутствующий или hash-invalid объект, недоступный Git, некорректный refs.
  Терпимое чтение не может выдавать частичный журнал за полный.
- GC планирует события и точные объекты до apply, сверяет предусловия и сообщает
  о потере возможности восстановления. В текущей реализации `keep_objects`
  может удалять и объекты, на которые остались ссылки; считать это существующим
  риском, а не автоматически одобренной новой политикой. Размер JSONL и размер
  SQLite не взаимозаменяемы. Экспорт — логический контракт плюс отдельный
  формат, не просто копирование каталога для всех будущих драйверов.
- Перенос истории в SQLite — отдельный проект: backup + проверка восстановления,
  предварительное сравнение последовательности, rev, refs, blob bytes и Git
  anchors в обе стороны; preview, защита от конкуренции, отказ при corrupt,
  crash/recovery и проверенный rollback. До успеха и согласования источник не
  удалять и конфигурацию не переключать.

### 6.3. Конкуренция и транзакции

`plan_hash`/сравнение hash — обнаружение некоторых изменений, не глобальная
блокировка. SQLite-транзакция отдельной БД не делает атомарным изменение файла,
журнала, refs и индекса. Для каждой операции определить стадии, порядок,
предусловия и наблюдаемые исходы: не выполнено; выполнено полностью; частично
(например, файл заменён, история не записана). Проверить отказ на каждой стадии,
конкурентное изменение и доступный recovery; не обещать автоматический откат
или crash-atomicity до реализации и тестов. Read-only SQLite позже требует
отдельно проверить `mode=ro`, WAL/SHM и влияние открытия БД на файловую систему.

## 7. Единые точки входа и выхода

### 7.1. Единый каталог возможностей

Единственный декларативный реестр должен описывать **реально** доступные
команды и их варианты, аргументы, условные требования, допустимые views/fields,
форматы, область действия, default и эффекты. Он поддерживает discovery,
валидацию и генерацию справки/схем; тест сравнивает его с Click, включая типы,
алиасы и условные комбинации, а не только число leaf. Новые возможности идеи
не появляются в реестре до реализации. Проверять неполный вызов, явный invalid
input, help и ошибку Click отдельно.

### 7.2. Query и output

Версионируемая `QuerySpec`/эквивалент: dataset/root, scope, типы, фильтры,
временные параметры, порядок/ranking, pagination/budget и необходимые поля.
Общий `QueryResult`: элементы, диагностики, provenance, полнота/усечение,
версии релевантной выборки и курсор. Типы/значения и семантика по семейству
остаются явными: `doc tag`, `folder tags`, `record labels` и `history tag` — не
одна сущность; физическая глубина дерева и глубина обхода графа тоже различны.

Курсор связан с dataset, содержимым/версией снимка, фильтрами, порядком,
релевантным конфигом, временем и версией алгоритма; при несовпадении — явная
ошибка или согласованный restart. Renderer не меняет смысл курсора. Не называть
его криптографически защищённым, пока этого нет. `total` — только когда реально
известен; частичные результаты имеют маркировку, не ложный успех.

`ResultEnvelope` — один целевой контракт результата, ошибок, диагностик,
подсказок и next actions; JSON, table и Markdown рендерят один смысл. Сначала
зафиксировать схему/golden и совместимость клиентов: единый выход не значит,
что текстовые форматы обязаны изображать каждый JSON как таблицу. Ошибки и
exit codes проверяются в `main` и настоящем процессе. Бюджет текста,
размер всего ответа и расход токенов — разные метрики.

### 7.3. Изменения

Общий контур `Request → validation → Plan → explicit apply → Outcome` должен
поддерживать несколько файлов, источник/назначение, hashes, последствия,
диагностики и неподдерживаемые последствия; это модель, не обещание реализации
многофайловой атомарности. `preview` ничего не записывает, `apply` проверяет
scope, права, план и повторно прочитанные предусловия. Для create-only нельзя
перезаписывать цель. Изменение output не должно превращать ошибку в discovery
или смягчать безопасность.

## 9. Пошаговая миграция и gates

Этот порядок — предложение для следующего решения, не разрешение приступать.
Полный подробный исполнительный план и пересмотр существующего плана потребуют
отдельного согласования. Общая стратегия: ветка остаётся текущей; не создавать
другую ветку, не выполнять merge без отдельного разрешения и не затирать
незакоммиченный снимок.

1. **Решение и сохранность.** Пользователь выбрал чистый master и только четыре
   документа без старых тестов и кода; проверить их наличие и текущую базу.
   Старое дерево не удалять, реальные данные сохранять; backup с проверкой
   восстановления обязателен перед опасными изменениями существующих данных.
   Согласовать временные правила, включая значение «багфиксы», не меняя их
   задним числом. Недостающие тесты создавать по описанным инвариантам.
2. **Базовая матрица.** Снять команды, аргументы, клиентов, side effects,
   семантику и ошибки объединённого/выбранного дерева; инвентаризировать все
   прямые storage-потребители и сохранившиеся пользовательские данные. Снять
   точные baseline tests, skips, схемы, измерения и известные отклонения. Тесты
   целевого будущего контракта на чистом master могут изначально падать; записать
   причину, не выдавать их за существующее поведение.
3. **Границы хранения — З0-S.** Реальные JSON/JSONL адаптеры и independent fake,
   инъекция, чтение без записи, safety, history/blob-source и негативные тесты;
   все затронутые use cases переходят на порты. Результат — не SQLite и не
   публичный plugin framework. Этапные проверки по §0.10 рабочего плана.
4. **Application + единый контракт.** Вынести общие request/result, query,
   plan/apply и output в существующие подходящие модули. Для каждого семейства:
   golden/characterization → use case → тонкий CLI → потребители → тесты и
   удаление старого пути. В первую очередь покрыть опасные обходы и общие
   инфраструктурные ошибки, затем чтение, history, запись, администрирование,
   state/skills и interop. Не навязывать одно представление всем источникам.
   На каждом срезе применять границы/контрактные правила §§18–20, не ждать
   окончания миграции для проверки смешанных обязанностей.
5. **Закрытие миграции.** Сверка всех Click leaf и вариантов с каталогом,
   проверка, что legacy paths не обходят новые границы; обновление документов и
   клиентов после согласования изменений поведения, удаление временных
   переходников, проверка сохранности. Старые тесты не удаляются ради зелёного
   результата. Оставшиеся несовместимости и TOCTOU фиксируются явно.
6. **Будущие драйверы и расширения — только отдельными этапами.** SQLite index,
   history и миграция данных проходят собственные contract/crash/performance
   gates. Открытые плагины, FTS/BM25 и будущие transports — не побочный эффект
   унификации CLI.

Относящиеся тесты — после каждой правки, полный набор и 100% branch coverage —
на завершении этапов согласно согласованным правилам. На clean master
известные красные тесты ещё не реализованного поведения не означают успешного
полного гейта; они классифицируются и закрываются в соответствующем этапе.

пользовательского согласования неоднозначных изменений.

## 11. Практические ограничения и риски

- **Зависимость от кэша для корректности.** Если каждый read требует `sync`,
  offline/read-only окружение и preview сломаются. Решение: read model с
  проверенным кэшем или in-memory построением, source-native fallback.
- **Ложная абстракция.** Обёртка с методами `get_json_path()` или код CLI,
  ожидающий SQLite-таблицу, не делает систему сменяемой. Проверять реальные
  потребительские операции на двух независимых реализациях.
- **Цена полного scan.** Надёжная проверка источников может быть дорогой;
  измерить и оптимизировать без ослабления корректности. Кэш не обязан
  показывать ускорение при холодном запуске; incremental и FTS — отдельные цели.
- **Дублирующиеся модели и временные мосты.** Один ответственный use case и
  единая таблица поведения для каждой команды; мост должен иметь критерий
  удаления. Нельзя смешивать старый v1 и новый v2 по случайному коду пути.
- **Данные и доверие.** Пользовательские документы/плагины — не инструкции
  ядру; никакого `eval` и автоисполнения next actions. Новые сетевые или
  исполняемые плагины требуют модели доверия, allowlist/consent и изоляции.
- **Расширяемость и стабильность API.** Внутренние Protocol ещё не публичный
  совместимый плагинный контракт. Версии данных, индексной схемы, history,
  запросов и envelope независимы; обещания расширяемости — после реального
  второго драйвера, матрицы и политики версионирования.
- **Доступность и повреждение.** Источник может быть недоступен, индекс бит,
  история неполная, Git отсутствует; эти состояния не взаимозаменяемы. Не
  исправлять ценные данные скрыто, показывать диагностику и блокировать опасный
  apply при неопределённой целостности.

## 12. Решения, которые нужно принять до переработки плана

1. Утверждаем вариант B — полный целевой охват CLI с поэтапной миграцией ядра,
   а не big-bang? Какой бюджет и приоритет относительно текущего плана unified?
2. Начинаем с сохранённого рабочего снимка и разрешённой интеграции master или
   с отдельного clean-master маршрута с передачей тестов? Пока разрешения на merge нет.
3. Какой публичный контракт совместимости: целевой v2 с обновлением клиентов,
   допустимые алиасы и сроки удаления переходников? Какие изменения требуют
   дополнительного подтверждения до реализации?
4. `read/preview` без любых побочных записей, включая XDG — подтверждаем ли это
   как приоритет над идеей action logging? Как явные команды observe/rebuild
   фиксируют внешние изменения и сообщают о пропущенных промежутках?
5. При битом индексе: read с диагностикой и in-memory fallback или жёсткая
   ошибка по операциям? Какой диагностический и восстановительный контракт?
6. История: допустима ли потеря referenced snapshots при `keep_objects`, какое
   подтверждение GC и какой export format? Как трактовать повреждённые события
   и неоднозначные rev? Должны ли некоторые read иметь tolerant режим с пометкой?
7. Когда и в каком объёме отдельно делать SQLite index/history, конфигурацию,
   migration и open plugin API? Должны ли внешние драйверы вообще исполняться в
   процессе CLI? До ответов остаются только внутренние порты.
8. Сохранять текущую временную семантику с честной маркировкой или отдельно
   реализовать оба clock? Как версионировать старые вызовы и данные?
9. Подтверждаем ли сохранение текущего поиска до отдельного quality gate для
   BM25/FTS и проверяемые бюджеты без несанкционированного изменения K1–K30?
10. Кто и как согласует временные правила для разработки, тестовых баг-репортов
    и прямой работы с файлами, не отменяя обязанности для реальной эксплуатации?

**Рекомендуемый следующий шаг:** обсудить эти решения, затем отдельно составить
единый согласованный исполнительный план, связав его с существующими З0-S и
З1–З9 без дублирования. До этого документ — архитектурная гипотеза, не команда
менять код или данные.

## 13. Старт новой сессии: чистый master и четыре документа

Пользователь выбрал опубликовать только документы, не перенося прежний код,
тесты, баг-репорты и историю. Проверить по фактическому Git, что четыре файла
есть в актуальном master:

1. `docs/plan/todoc-master-refactoring-plan.md` — порядок и гейты;
2. `docs/research/cli-architecture-refactoring.md` — архитектура и SOLID;
3. `demo/plan/unified-cli-output-implementation.md` — инварианты и задачи;
4. `demo/ideas/unified-cli-output.md` — цели единого CLI.

Если документов нет, новая сессия не должна считать публикацию состоявшейся:
остановиться и спросить, как их получить. База/ветка и разрешённые операции
определяются актуальными правилами среды, а не названием старой ветки в аудите.
Сохранить прежнее пользовательское дерево и реальную историю: не делать reset,
clean или иные разрушительные операции. Для независимого чистого checkout не
требуется переносить прежний снимок; backup и проверка восстановления нужны
перед риском для существующих пользовательских данных.

§0.6 плана unified содержит 28 исторических инвариантов и selectors, но наши
старые тесты и репорты в публикацию не входят. Новые тесты создаются в новой
сессии по сценариям и фактическому коду master, на временных datasets; если
сценарий неполон — `не проверено` и вопрос пользователю, а не ложный PASS или
вымышленное совпадение со старым тестом. Прежние результаты и 13 конфликтов/39
падений диагностического слияния не являются baseline чистого master. Номера
BUG-011–016 совпадают с другими репортами master: не смешивать их и не
перезаписывать данные. Новый агент проверяет master, baseline и решения согласно
мастер-плану; для реализации и Git-действий нужны отдельные разрешения.

## 14. Рекомендуемая очередь: какие планы готовить и когда выполнять

Это **историческая рекомендация**, не автоматическое согласие реализовать
каждую идею. При отличии порядка использовать мастер-план
`docs/plan/todoc-master-refactoring-plan.md` (в частности, move/folderize до
SQLite при принятом пользователем порядке). Сначала учесть все идеи при проектировании основы; затем делать
планы и фичи в приоритетном порядке с отдельными решениями. Слова «до/после» в
таблице — рекомендуемый порядок, а не доказанная неизбежная техническая
зависимость. Можно менять порядок отдельных параллельных ветвей по нужде, если
их контракты совместимы и основания записаны. Не замораживать API ради
гипотетических будущих фич и не писать все отложенные фичи прежде, чем заработает
основной CLI.

## 15. Как превратить конкретную идею в исполнимый план

Для каждой выбранной пользователем идеи новая сессия выполняет один и тот же
цикл. Если идея уже имеет актуальный AFTER/implementation-план, сначала
**обновить или дополнить его по отдельному поручению**, а не создавать конкурента.
При подготовке ещё не утверждённого плана можно зафиксировать предложения и
открытые вопросы; код и данные менять только в пределах полученного разрешения.

1. **Задать рамки:** проблема, пользовательские сценарии, ожидаемый эффект и
   метрики, явный scope/non-goals, существующая версия и что уже работает.
   Сверить само предложение с кодом, тестами, правилами, потребителями и
   мастер-планом; классифицировать каждую возможность `есть / частично /
   отсутствует / неизвестно`, с проверяемым источником и датой снимка.
2. **Найти зависимости и конфликты:** конкретные порты/use cases/команды и
   прочие планы, прежние поля и выходы, семантика времени/identity/scope,
   no-write, совместимость, безопасность, история и восстановление. Отличать
   реальную блокирующую зависимость от рекомендуемого порядка. Ключевые
   решения/изменение публичного поведения — к пользователю; не подменять их
   предположением агента.
3. **Спроектировать минимальный вертикальный срез:** вход/выход, модели и
   версии, owned операции каждого слоя, явные эффекты, возможные исключения,
   как обеспечить старые сценарии и возможность корректной диагностики.
   Привести конкретные пути/модули как предложения, а не гарантировать, что
   они существуют в чистом master.
4. **Миграция и сохранность:** какие данные трогаются, backup/restore,
   preview/apply и предусловия, конфликт/гонка, частичный результат, rollback
   или честный recovery; если это неприменимо — написать почему. Для истории
   запрещены подразумеваемая потеря данных и молчаливое переключение драйвера.
5. **Составить задачи с зависимостями:** для каждой входные условия, конкретные
   файлы и интерфейсы после сверки, тест сначала, реализация, результаты и
   команда проверки, ограничения на права/данные, критерий приёмки и владелец
   решения. Добавить узкие точки останова и порядок перехода между задачами.
6. **Тесты и метрики:** позитивные/негативные/пограничные случаи, несколько
   datasets, отсутствие и повреждение кэша/истории, no-write, fault injection,
   CLI subprocess и интеграция с прочими идеями по необходимости. Отдельно
   unit/contract/E2E, среда, skipped, прошлые падения и измерение производительности.
   Никаких выдуманных команд тестов или уже зелёных результатов.
7. **Review и выпуск:** матрица старые/новые клиенты и docs, тесты после правок,
   полный набор и branch coverage по завершении этапа, миграционный документ,
   остающиеся риски, пользовательское согласование и явный DoD. Не закрывать
   этап с известными неподтверждёнными требованиями. Только после утверждения
   плана и разрешения переходить к выполнению.

Шаблон готового плана: `контекст и снимок → доказательства и статус → решения
и зависимости → контракт → scope/non-goals → сохранность/миграция → задачи с
файлами и проверками → матрица регрессий/клиентов → гейты/DoD → риски и журнал`.
Не создавать новый баг-репорт из тестирования до согласования временных правил;
при реальном использовании продукта действуют существующие правила. Слово
«багфиксы» нужно уточнить, а не считать запретом исправлять код.

## 16. Контрольный алгоритм для агента и stop/go

### 16.1. Первый проход — только инвентаризация и планирование

1. Прочитать актуальные системные ограничения и `AGENTS.md`, проверить текущую
   ветку, HEAD и `git status --short`, при разрешённой сети — удалённый master.
   Не делать checkout/reset/clean/merge/commit/push как диагностику.
2. Проверить наличие четырёх документов из §13 и соответствие выбранной чистой
   базы master. Если чего-то нет, сообщить пользователю и не создавать заглушки.
   Прежние тесты и исходники не переносятся; старое дерево не удалять.
3. Сверить 15 идей, 6 AFTER и другие актуальные планы с кодом, проверить
   статус и среду. Отдельно отметить исторические результаты и расхождения.
4. Снять baseline тестов master в изолированных fixtures; по мере реализации

5. Показать отчёт с отсутствующими решениями и предложить первый срез уже

### 16.2. Дальше — только после отдельного разрешения

Для каждого утверждённого этапа: сверить входной снимок и условия → выбрать
существующие регрессии и добавить недостающие на временных данных → выполнить
точечные тесты → менять ограниченный срез → повторить точечные тесты → проверить
клиентов и отсутствие побочных эффектов → прогнать полный этапный набор и
branch coverage согласно правилам → записать результат, skips и известные
ограничения → запросить решение для следующего этапа, если оно нужно.
Проверки `validate`/linkcheck делать без изменения реального датасета и с
анализом `broken`, а не только exit code. Для benchmark §0.8 плана CLI:
скрипт пишет фиксированные результаты и `/tmp/todoc-bench-*`; сначала изолировать
их в проверенной копии, не считать `RESULTS=…` рабочей изоляцией. K1–K30,
кроме K3, не менять без согласования пользователя.

**STOP:** нет нужных документов, недостаточно данных о регрессии или нет backup перед рискованным действием; внезапные пользовательские
изменения; конфликт данных/одинаковых имён без решения; отсутствуют права или
доступы; непонятна семантика/time/scope/history; опасная запись вне тестовой
области; повреждение истории; не воспроизводится важная регрессия; требуется
несогласованное изменение критериев или операция Git вне разрешений. Отчёт
должен назвать блокер, что уже сделано и безопасные варианты продолжения.
**GO:** источник и полномочия проверены, конкретный этап согласован, нет
неразрешённых блокеров, связанные тесты и контроль сохранности проходят; полный
гейт закрывается только при его фактическом выполнении, без переименования FAIL
в skipped. Если выбран вариант B и тесты не реализованного функционала ещё
красные, их отдельно классифицировать; это не полный зелёный DoD и не право
игнорировать новые ошибки или падения затронутой области.

## 18. Ревизия архитектуры по SOLID и принципам ООП

**Статус:** проверка применительно к этому проекту, а не требование переписать
его на классах. Идеальной для всех будущих изменений архитектуры не существует;
результат оценивается по конкретным изменениям, надёжности и стоимости поддержки.
Python поддерживает чистые функции, структуры данных, композицию и структурные
`Protocol`: использовать простейший механизм, выражающий реальный контракт.
Схема §§4–7 уточняется этим разделом; имена ниже — предлагаемые роли, а не
обязательные новые классы и не утверждение о существующей реализации.

### 18.1. Что обнаружено при ревизии рабочего снимка

| Принцип | Конкретный признак в существующем коде или предыдущем предложении | Улучшение и проверка |
|---|---|---|
| **S — Single Responsibility**: одна причина изменения на уровне роли, а не «один метод на класс». | `DatasetContext` создаёт конкретный `RegistryStore`, загружает конфигурацию, сканирует, валидирует и строит данные; `RegistryStore` совмещает JSON-layout, snapshot, stats и config digest; `application/history.py` содержит и обработку истории, и физический обход/GC. Фасад из §4 сам мог бы повторить эту проблему. | Разделить обязанности по границе изменения: конфигурация/scanning, вычисление snapshot, чтение/публикация кэша, история и presentation. Оставить coordinator только для orchestration, без бизнес-правил внутри и доступа к layout. При изменении JSON-layout — адаптер и его тесты, не каждый use case; при изменении правила выборки — use case и его тесты, не рендерер/драйвер. |
| **O — Open/Closed**: расширяемость в выбранной точке, не запрет изменять код вообще. | В будущей схеме возможна новая реализация индекса или рендера; если вся логика ветвится по `driver == ...` внутри команд, каждый backend потребует изменения CLI. Реестр capabilities уже содержит статические множества, но не покрывает весь объединённый CLI. | Для реально ожидаемых вариантов — подстановка через composition и узкие контракты; для нового предметного правила допустимо менять application/domain. Новая команда обязана зарегистрировать свой контракт и адаптер; поддержка не должна появляться магически через reflection. Не замораживать публичный plugin API преждевременно. |
| **L — Liskov Substitution**: одинаковые обещания поведения, а не только одинаковые имена методов. | `HistoryBackend.read_at` может вернуть `None`, а `EmbeddedBackend` сейчас напрямую вызывает файловый `objects.read_snapshot`; fake и будущий SQLite могут формально совпасть по типу, но расходиться в порядке, ошибках, эффектах и диагностике. | Определить предусловия, исходы, ошибки и эффекты каждого порта; выполнить один набор проверок на реальном адаптере и независимом fake. Embedded должен обращаться к нужному порту образов, а не к JSONL objects в обход нового store. Git gap-filling и его деградация сохраняют отдельную политику, не притворяются одинаковой физической реализацией. |
| **I — Interface Segregation**: потребитель видит лишь нужные возможности. | Таблицы §6 описывают много операций истории и индекса; буквально реализованные как единый огромный `HistoryDriver`/`IndexDriver`, они могут превратиться в god interface. Читающая команда не должна получать полномочия GC и write из удобства. | Проектировать потребительские read/write и административные порты независимо по use cases (§19). Один встроенный адаптер может реализовывать несколько таких портов; это **не** требует отдельного класса на каждый метод. Доступ записи не передавать read/preview. |
| **D — Dependency Inversion**: стабильные политики не зависят от конкретных механизмов. | `service.py` создаёт `RegistryStore`; `write.py` импортирует инвалидацию кэша, `cli.py` использует layout индекса и strict helpers. Одного перемещения файлов в `adapters/` недостаточно. | Направить зависимости к принадлежащим потребителям портам; связать конкретные компоненты в composition root. Перевести все потоки поэтапно, проверить граф импортов **и** runtime с заменой адаптеров; сохранить файловые защиты. |
| **ООП: инкапсуляция и композиция** | Методы `RegistryStore` и его поля с путями доступны вызывающим; `HistoryRecorder` допускает `None` как режим без истории. Такой тестовый shortcut не должен случайно определять продуктовую политику. | Спрятать физические детали за контрактами. История на write — явная конфигурация/политика и результат, а не неявный `None` в production; совместимость и разрешённые режимы сначала подтвердить тестами. Использовать композицию, не строить дерево наследования абстрактных базовых драйверов. |
| **Разделение вычисления и эффектов** | В рабочем `output/envelope.py:emit` не только рендерит, но и пишет в stdout либо файл; в `cli.py` есть несколько `_emit_*` и globals группы. Предыдущий тезис «renderer чистый» — цель, а не факт. | Отделить чистое преобразование результата в текст/байты от transport-вывода и **явной** записи в файл. Если текущий `--out` доступен, описать его существующие эффекты и миграцию/разрешение до изменения UX; не записывать файл из функции форматирования. Проверить CLI и повторные вызовы в одном процессе на независимость настроек. |

Проверка проводилась на незакоммиченном рабочем снимке, не на объединённой
ветке. Это признаки риска и направления проектирования, а не формальное
доказательство, что каждый существующий класс нарушает SOLID при любом сценарии.
Прежде чем менять код, подтвердить текущее поведение и зависимости на выбранной
базе.

### 18.2. Инварианты проектирования

1. **Высокая связность, слабая сцепленность.** Модуль владеет понятной
   предметной ответственностью и может быть проверен без чужого layout;
   соседние модули не делят внутреннее mutable состояние и секретные договорённости.
2. **Композиция вместо наследования.** Не вводить `BaseCommand → BaseRead →
   BasePaged → …`: условия reuse выражать функциями, небольшими объектами и
   контрактами. Исключения допустимы, если есть проверяемое отношение «является»
   и соблюдается подстановка, а не только общий код.
3. **Одно место принятия решения.** Scope/фильтрация и правила операций принадлежат
   application/domain; адаптер воплощает физическое поведение, renderer — вид.
   Оптимизация может выполнять эквивалентную часть запроса на стороне драйвера,
   но не вводить вторую несовместимую семантику.
4. **Явные данные и эффекты.** Различать чистый расчёт, I/O и оркестрацию;
   операции отражают возможность ошибки и частичности. У логического ответа
   есть пользователь, смысл и владелец; случайный `dict[str, Any]` между всеми
   слоями не заменяет контракт. При этом неизвестные поля данных истории и
   расширения не теряются из-за чрезмерно узких DTO.
5. **Минимум абстракций.** Новый порт оправдан существующей границей, второй
   независимой реализацией для проверки или конкретным вторым адаптером с
   согласованным планом. Не вводить контейнер DI, event bus, отдельный репозиторий
   на таблицу или плагинный фреймворк без реальной потребности. Частая точка
   изменения не обязательно нуждается в классе.
6. **Тестируемые, а не названные свойства.** `atomic`, `safe`, `read-only`,
   `current` и `transaction` — только если определены наблюдаемые гарантии и
   тесты; иначе использовать более узкое название/оговорку. Нельзя вывести
   транзакционность исходника и истории из интерфейса или SQLite-транзакции.

## 19. Контрактные границы без god-объектов

### 19.1. Разделение ролей и зависимостей

Таблица уточняет крупные роли §6: строки — **интерфейсы потребителей**, не
обязательные классы. Допустимо, чтобы один объект JSON реализовал несколько
ролей, если у них отдельные контракты и его клиенты не получают лишних методов.

| Потребитель | Минимально нужная роль/ответственность | Чего не получает |
|---|---|---|
| `docs search`, lists, graph | ReadModel/QueryReader с заданной областью, полями, порядком, честной полнотой и диагностиками; источник при cache miss выбирает coordinator. | `publish`, GC, refs-write, физические пути к shard/SQL. |
| `docs read`, validator | SourceReader и нужные типы/правила; parse-cache read как опциональная оптимизация. | Запись cache/history; право объявлять источник неизменным только по кэшу. |
| `index status` / `doctor` | IndexStatusReader: состояния и доказательства проверки; проверка доступа не приводит к публикации. | Автоматический rebuild или состояние `valid` только из наличия файла. |
| `index rebuild --apply` | IndexPublisher + необходимые read/scan, explicit cache/stats update; проверка предусловий и фактический outcome. | Право удалять или пересоздавать history при пересборке cache. |
| `log`, `show`, `blame`, temporal | HistoryEventReader, RefsReader и при необходимости SnapshotReader / BeforeImageSource. Strict и tolerant режимы — явно определённые контракты/политики, не скрытая вариация адаптера. | Append, GC и молчаливый выбор старого снимка при пропаже последнего. |
| `write`, `tag`, `adopt`, `revert` | SourceWriter и только необходимые HistoryAppender/RefsWriter/SnapshotWriter, cache invalidation и выбранный источник образов; application владеет порядком стадий. | Неявное отсутствие истории, фиктивный all-or-nothing и обход валидации через другой CLI. |
| `history gc`/`export` | Отдельные административные роли планирования/apply и логического экспорта, плюс read и права конкретной операции. | Использование вычисленного по JSONL размера как универсальной метрики SQLite, скрытое удаление живых объектов или несогласованная миграция. |
| JSON/table/Markdown | Типизированный результат и presentation-параметры; преобразование без I/O. | Открытие source/cache/history и принятие решений о бизнес-смысле. |
| Click/будущий transport | Таблица возможностей, dispatcher/use cases, mapping ответов/ошибок и явно контролируемый output sink. | Доступ к деталям кэша, алгоритмам history и праву выполнить `next_actions` как код. |

**DIP на практике:** зависимости Python-кода направлены от policy/use case к
моделям и потребительским `Protocol`; адаптер импортирует эти контракты или
структурно им соответствует; composition root знает конкретные реализации и
создаёт общий граф. Допустимо совместное владение типами в `domain/` или `ports/`,
но зависимости `domain → CLI/adapter`, `renderer → storage`, `application →
JSON/SQL layout` не допускаются. Для неизбежных временных обходов: явный список,
владелец, тест и критерий удаления до закрытия миграции. Отдельно исследовать
существующий `formats` parser: не считать перевод чистого парсера за адаптер
обязательным нарушением, но не давать application жёстко зависеть от физического
хранилища.

### 19.2. Жизненный цикл и внедрение зависимостей

- **Composition root — функция сборки**, не глобальный service locator и не
  универсальный объект, который бизнес-код опрашивает по строковому ключу.
  Каждый use case получает нужные роли явно; способ внедрения — аргументы
  конструктора или функции, без обязательной сторонней библиотеки DI.
- На один вызов зафиксировать неизменяемые identity/scope/настройки и
  соответствующие зависимости каждого dataset; multi-root сохраняет независимые
  root и результаты и не выбирает первый молча. Dataset ID недостаточно как
  единственный маркер физического scope при копиях датасета; различать ID,
  проверенный root и версию снимка по согласованной модели.
- Передача capability только на чтение **снижает риск**, но Python Protocol не
  является sandbox/контролем полномочий. No-write дополнительно проверяется
  перехватом реальных эффектов/файловой средой; парсить недоверенный документ
  как данные, не как разрешение на вызов writer.
- Срок жизни и владелец ресурсов явны: открытый snapshot/iterator/соединение
  закрывается при успехе, ошибке и раннем выходе; read/preview не создаёт
  каталоги, служебные файлы или write connections. Не кэшировать stateful
  объекты между roots/вызовами без доказанной изоляции; не скрывать ошибки close.
  Для потокового результата определить срок действия снимка и правила при
  изменении источника. Для SQLite позже специально проверить `mode=ro` и WAL/SHM.
- Часы, случайность и Git-привязка, **когда они влияют на результат**, задаются
  явно или из документированного контекста; тесты управляют ими. Не вводить
  общий `Clock`/фабрику на каждый детерминированный вызов ради формальности.
- Конфигурация и публичная семантика не вытекают из `None`/отсутствия mock:
  валидировать выбранную политику на границе, логически отделить «история
  отключена намеренно» от «история недоступна» и согласовать, какие режимы
  вообще допустимы. Ошибки адаптера отображать в стабильный application outcome,
  не глотать причину и не выдавать повреждение за отсутствие.

### 19.3. Поведенческий контракт вместо интерфейса «с нужными именами»

До реализации для каждой роли задать таблицу: вход и область; предусловия;
тип и смысл результата; порядок и полнота; версия/identity; обнаруживаемые
ошибки; права и эффекты; гарантии при сбое/конкуренции; жизненный цикл;
совместимость и минимальные примеры. Особенно важно:

- `IndexRead` не обещает всегда свежий индекс: результат различает `missing`,
  `stale`, `corrupt`, `inaccessible` и `valid` **после соответствующей проверки**.
  Политика fallback/ошибки для каждого вызова должна быть отдельно согласована.
  Read не создаёт/не ремонтирует кэш; fake обязан уметь моделировать ошибки,
  а реальный адаптер проверяется и на настоящей файловой системе.
- Строгий history-read не пропускает некорректные данные под видом полноты;
  если согласован tolerant read, он возвращает признак неполноты и диагностики.
  Оба режима не должны случайно использоваться взаимозаменяемо там, где
  выполняется destructive operation. Сравнивать порядок, duplicate rev, bytes
  и неизвестные поля; нельзя навязывать алгоритм `rev`, идентичный SQLite-row ID.
- Контракт содержит **минимальные гарантии**: одинаковые исходы ошибок и
  наблюдаемые данные при эквивалентных входах, но не идентичную внутреннюю
  сериализацию или физические ошибки ОС. `missing`, `inaccessible`, `corrupt`
  и `conflict` должны оставаться различимыми; нормализация low-level exceptions
  не должна терять необходимые diagnostics и причину.
- Изменение семантики, ranking, output schema, identity или версии cursor —
  отдельное согласованное изменение контракта и тестов, не «оптимизация».
  При полной замене backend клиент не обязан знать его физический формат;
  операция, которую backend не поддерживает, не выдаёт фиктивный успех и не
  допускается в активной capability без проверенного fallback.
- История — ценные данные, а не объект кэша. `IndexPublisher` не распоряжается
  файлами истории. Как передать SnapshotReader существующему embedded backend,
  не перепутать Git revision и digest и сохранить degradation/gap-filling —
  отдельные пункты migration/test plan, а не простая замена import.

### 19.4. Где должны жить данные, схема и ошибки

- **Value objects / DTO:** применять для реально значимых границ (`DatasetScope`,
  проверенный относительный путь, ревизия/digest, параметры запроса, результат
  операции). Создавать значения через валидирующие фабрики/функции там, где
  важно обеспечить инвариант; при передаче между слоями не полагаться на
  изменяемый глобальный dict. `frozen`/типы помогают, но не являются runtime
  проверкой, не гарантируют глубокую immutability и не заменяют validation.
- **Различать идентификаторы:** root, dataset ID, path, doc ID, record ID,
  revision и content hash имеют разный смысл. Существующие форматы и неполные
  поля прочитать без потерь; относительный путь не считать безопасным до
  проверки границы и symlink при выполнении. Не смешивать иерархию директорий,
  graph edges и display-проекцию в один обязательный класс сущности.
- **Версии независимы:** схемы исходных данных, индекса/parse-cache, истории,
  query/cursor, CLI envelope и будущего публичного API меняются отдельно.
  Backward compatibility определяется per boundary: неизвестные поля истории
  сохраняются; несовместимый индекс может быть пересобран явным действием;
  непрочитанную историю нельзя молча пересоздать. Новая версия cursor должна
  определять принятие старой или понятный отказ с restart, не silent wrong page.
- **Ошибки на границе:** ожидаемые domain/application ошибки типизированы или
  кодированы предсказуемо, несут безопасную диагностику/фактический outcome;
  transport единообразно сопоставляет их с output/exit. Unexpected ошибки не
  превращаются в «пусто»; полные детали внутренних исключений не выливаются в
  публичный ответ или секреты. Политика логирования и сохранения ошибок —
  отдельно от history и от read-only требований.

## 20. Проверяемая архитектура: примеры, гейты и ограничения

### 20.1. Пример одного вертикального среза

**`docs search`** — иллюстрация целевого потока, не существующая реализация
и не разрешение изменить выдачу:

1. Click валидирует синтаксис и вызывает use case с явно заданными root и
   параметрами; не конструирует `RegistryStore`, не открывает индексные shards.
2. Use case проверяет scope/config, просит ReadModel и передаёт явную политику
   для `missing/stale/corrupt/inaccessible`. При согласованном fallback builder
   читает источники и строит memory snapshot без публикации; при ошибке чтения
   источника не использует старый cache, выдавая его за полный.
3. Одна семантическая реализация определяет filter → ranking → стабильный
   tie-break → страницу и completeness. Драйвер может сделать pushdown, только
   если contract-тест доказывает тот же результат. Поля и дерево/граф не должны
   удалять данные, необходимые для сортировки и связи курсора; правила страниц
   для каждого вида явно определены. Текст/cursor зависят от фактических входов.
4. Чистый formatter создаёт текст/байты из результата; transport управляет stdout,
   stderr и exit. Файловый output, если поддержан, обрабатывается как отдельный
   осознанный эффект, не скрыто внутри formatter. Тесты проверяют JSON/table/MD,
   второй root и отсутствие попытки записи при обычном read.

Для `history gc` аналогичный срез **не** должен подменять историю индексом:
strict read/проверка объектов → план с последствиями → явный apply и повторные
предусловия → честный полный/частичный outcome; ошибки и проверка отказа в
каждой стадии обязательны.

### 20.2. Архитектурные acceptance-тесты на каждом этапе

| Гейт / наблюдение | Как проверять и что не считать доказательством |
|---|---|
| A1. Направление зависимостей | Тест анализа импортов с конкретными допустимыми исключениями composition/tests; дополнительно заменить JSON/JSONL адаптеры в рантайме, запретив их вызовы. Один поиск текста, одно расположение файла или один mock недостаточны. |
| A2. Поведенческая подстановка | Один набор contract fixtures и сценариев на JSON/JSONL и независимый in-memory fake: идентичность, порядок, разные roots, сохранение полей, ошибки и side effects. Реальные filesystem/symlink/locking тесты остаются отдельными. Fake не доказывает работоспособность SQLite. |
| A3. Чтение и ошибка | Cold/warm/stale/corrupt/inaccessible; сравнить при согласованном fallback source-based и cache-based результаты, scope, order, diagnostics и truncation. При недоступном источнике не вернуть фиктивный полный успех. Перехватить попытки записи и сравнить filesystem до/после. |
| A4. Один источник semantics | Фикстуры с фильтрами за границей limit, равным rank, Unicode, config/temporal changes; сопоставить обычный путь и pushdown, все страницы, `total/truncated`, edges/provenance. Изменение ranking — только отдельное решение. |
| A5. Реальные права и жизненный цикл | Повторные и параллельные вызовы, два root с одинаковым dataset ID, закрытие итераторов/файлов при exception и early exit; `read/preview` в изолированных root и XDG с запретом любых записей. |
| A6. Эффекты и recovery | Инъекции отказа до/после каждой стадии записи файла, history, cache/index и админских операций; stale plan, symlink, отсутствие/битый образ, GC на ссылочных объектах. Сверить фактическое состояние и предлагаемый recovery, не ждать атомарности без механизма. |
| A7. Выход и границы API | CliRunner + subprocess: ошибки парсинга, ожидаемые и неожиданные ошибки, стабильные codes/exit, `--help`, discovery, JSON/table/Markdown и согласованный `--out`; renderer не совершает I/O, `next_actions` не исполняются. Реестр и Click сверяются по опциям и условным сценариям. |
| A8. Эволюция | Golden fixtures и consumer tests для старой/новой schemas, неизвестных полей истории и старых cursor; тесты version mismatch, миграции/отказа, повторной публикации и cleanup временных мостов. Нельзя считать сохранность данных доказанной одинаковым числом файлов. |
| A9. Стоимость поддержки | Для каждого нового интерфейса назвать потребителей, реальные вариации и тест подстановки; для каждого изменения — файлы по слоям и причину. Если интерфейс не изолирует известную причину изменения, упростить или зафиксировать обоснование. Нет произвольной нормы классов/строк. |

Эти гейты дополняют, а не подменяют §10 и полный DoD существующего плана;
выполнение подлежит отдельному разрешению. Для будущих SQLite и plugin API
добавить реальных вторых адаптеров, матрицу, fault/concurrency/recovery и
определённые совместимость/безопасность. Структурный `Protocol` и fake не
являются доказательством готовности произвольного внешнего драйвера.

### 20.3. Баланс качеств и открытые решения

Поддерживаемость конкурирует с задержкой, объёмом памяти, строгостью проверки,
обратной совместимостью и сложностью миграции. Перед заморозкой интерфейсов:

- Для базовых рабочих сценариев измерить cold/warm latency, память и стоимость
  проверки актуальности на фиксированных корпусах, а также пользовательский
  размер/полноту ответа. Указать окружение и источник baseline; конкретные
  пороги сначала согласовать. Не обещать одинаковую производительность fake,
  JSON и SQLite и не менять benchmark-критерии без разрешения.
- Для каждого пересекающего границу поля определить владельца, смысл,
  чувствительность, совместимость и необходимость в ответе. **Все поля выбранной
  поддерживаемой формы по умолчанию** и ограничения unified CLI сохраняются;
  не путать это с обязательством показывать внутренние объекты/секреты.
- Зафиксировать в компактных ADR или секции решений мастер-плана: выбранные
  порты и срок их поддержки, договор pushdown, модель snapshot, политику
  повреждения, единый capability source, переходники/удаление и соответствующих
  проверяющих. Не создавать отдельный ADR на каждую функцию автоматически.
- Capability/catalog не должен стать вторым Click с ручным дублированием или
  исполняемым source данных: определить один authoritative источник метаданных
  и проверяемое отображение в Click/schema. Если отдельные сведения невозможно
  вывести автоматически, синхронизацию обеспечивают contract-тесты и явный owner.
- Результат архитектурного ревью — не объявление «идеально», а список оставшихся
  допущений, стоимости и доказанных проверок. Пользователь решает спорные
  компромиссы; будущие запросы могут потребовать пересмотра контрактов.
