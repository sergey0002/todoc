## 1. Проблема, измеренная

Текущий механизм публикует **полный снимок состояния на каждый запуск**, независимо от того,
менялось ли что-нибудь. Замер на копии `demo/` (2026-11-25):

| Измерение | Значение | Команда |
|---|---|---|
| Поколений после 5 команд `docs search` | **5** | `ls .todoc/index/generations \| wc -l` |
| Уникальных содержимых среди них | **1** | SHA-256 по 5 файлам каждого поколения |
| Размер одного поколения | 285 КБ | `du -sh` |
| `.todoc/index` в демо | **27 МБ** (94 поколения) | `du -sh demo/.todoc/index` |
| Сами документы (истина) | **2.4 МБ** | `du -sh --exclude=.todoc demo` |
| Метка времени в `meta.json` | **отсутствует** | ключи: `schema_version`, `dataset_id`, `generation_id`, `config_digest` |

Повторная проверка того же демо 2026-11-25: после единственного `index rebuild` число
поколений выросло с 93 до 94 — рост воспроизводится на глазах, и он линейный по числу
команд, а не по объёму изменений.

Выводы:

1. **Снимок на запуск — это не история.** Пять идентичных снимков несут ноль информации.
   Правильная единица истории — **событие записи**, а не факт запуска команды.
2. **Производное в 11 раз больше истины** и растёт неограниченно (P1-2: сборки мусора нет).
3. **Историю нельзя даже отсортировать по времени.** `generation_id = uuid.uuid4().hex[:12]`
   (`registry.py:70`) — случайный, не упорядоченный; `created_at` в метаданных нет.
   Единственное использование `datetime` во всём `src/todoc` — `_utc_date()` в `cli.py:312`,
   и оно нужно для плейсхолдера `{date}` в шаблонах, не для истории.
4. Пересборка вызывается из **15 мест** в `cli.py` (`rebuild_index()`), при том что
   `load_index()` используется в 10. Это же — причина P1-1.

**Тезис редизайна:** индекс — это кэш, он один и инвалидируется по содержимому.
История — это журнал событий, дописываемый за O(1). Эти две роли сейчас смешаны в одном
механизме, и отсюда обе проблемы.

## 2. Три хронологии, которые нельзя смешивать

Задача распадается на три независимых вопроса. Каждый существующий инструмент решает ровно один:

| Вопрос | Механизм | Кто решает |
|---|---|---|
| **A. Как файл выглядел раньше?** (откат) | контентно-адресуемые снимки | git; OpenSpec — нет; Zep — нет |
| **B. Зачем и в рамках какой задачи?** (намерение) | дельты, proposal, жизненный цикл | OpenSpec; git — частично |
| **C. Что было правдой на дату X?** (факты) | би-темпоральные интервалы | Zep/Graphiti; git — нет |

Смешивание даёт систему, плохо делающую всё три. Поэтому — слои, каждый проверяем отдельно.

## 3. Ограничения, которые план не нарушает

| Принцип | Как соблюдается |
|---|---|
| **P1** Файлы — истина | Журнал и снимки не заменяют файлы; источник истины не меняется |
| **P2** Портабельность | Только relative paths; `dataset_id` переживает move; `history/` переносится вместе с папкой |
| **P3** Декларативность | Дельты и `derived_from` — JSON/Markdown-данные, никакого кода в DATA_ROOT |
| **P4** Разделение измерений | План использует все четыре оси по назначению: `doc_type: delta` — семантика документа, `dir_type` для `changes/` — роль папки, `entity_type: change` — запись, `relation_type: blocked_by` — связь. Ничто не выводится из расширения или имени папки |
| **P5** Детерминированное ядро | Никакого LLM в поиске противоречий; инвалидация факта только явная |
| **P6** Review-first | `revert`, `change apply` — preview по умолчанию, `--apply` + `expected_hash` |
| **P7** Bounded context | `log`/`diff`/`stale` отдают `truncated`, `cursor`, `--limit` |
| **P8** Точные locations | Каждая запись журнала несёт path + изменённые диапазоны строк |
| **P9** Явные связи | `blocked_by`, `derived_from` — данные в источнике, граф производный |
| **P10** Только установленный код | Дельты не исполняются; применяется только разрешённый набор операций |
| **P11** CLI — контракт, MCP — адаптер | Вся логика истории живёт в application-слое и доступна через CLI. MCP, если появится, будет тонким адаптером (§16). Именно этот принцип делает решение «MCP позже» не отступлением, а следованием конституции |
| **P12** Offline-first | Бэкенд `git` вызывает локальный бинарник, не сеть и не модель. Автоопределение не создаёт сетевых обращений; при отсутствии git — деградация в `embedded` |
| **P13** Объяснимость | Каждая новая команда возвращает `next_actions` argv-массивом; `history.backend_unavailable` и `staleness.dependency_changed` называют причину, а не факт |
| **P14** Совместимость без зависимости | `changes/` — обычный Markdown с YAML front matter, открывается в Obsidian как остальной DATA_ROOT; ни git, ни Obsidian не становятся runtime-зависимостью |

**Поправка в конституцию нужна только для бэкенда `embedded`.** Таблица в
[`09-storage-and-index.md`](../state/09-storage-and-index.md) делит всё на «истина» и
«производное, удаляемое». В бэкенде `embedded` появляется третья категория —
**необратимое производное**: `.todoc/history/` нельзя пересобрать из файлов, значит
каталог должен явно бэкапиться. В бэкенде `git` третьей категории нет: история
восстанавливается из репозитория (§18). Решение принято 2026-11-25; в
`09-storage-and-index.md` оно ещё не зафиксировано — это отдельная задача до Фазы 1.

## 5. Схемы

### 5.1 Событие журнала

```json
{"schema_version":1,"rev":"a1b2c3d4e5f6","at":"2026-11-25T10:42:29Z",
 "kind":"doc.edit","actor":"cli","change_id":"change:fix-p1-10",
 "paths":[{"path":"docs/state/09-storage-and-index.md",
           "before":"sha256:aa…","after":"sha256:bb…","ranges":[[31,58]]}],
 "basis":"docs edit --patch-file patch.json","git_head":"ac96060…"}
```

- `rev` = SHA-256 строки журнала (12 hex) — стабилен, не требует счётчика.
- Порядок — порядок строк в файле; `at` — вторичная сортировка.
- `kind`: `doc.create` | `doc.edit` | `doc.fix` | `record.create` | `record.edit`
  | `change.open` | `change.apply` | `change.archive` | `change.revert`
  | `external.change` | `snapshot` | `gc`.
- `ranges` — изменённые диапазоны строк; без них невозможна лента по разделу.
- `git_head` — HEAD на момент записи, то есть состояние **до** изменения. Нужен бэкенду
  `git` (§18): по нему восстанавливается содержимое «до» и решается, нужен ли свой
  снимок. В бэкенде `embedded` поле отсутствует, а не пусто.

Поля `generation_id` в схеме нет намеренно. Оно было бы унаследовано от текущего
механизма, но Фаза 0 (§6) убирает серию поколений: остаётся один `.todoc/index/current/`.
Ссылаться на несуществующее после Фазы 0 понятие журнал не должен.

Формат JSONL выбран потому, что дописка атомарна одним `write`+`fsync` без
read-modify-write, файл грепается и диффится в git, и не нужна БД.

### 5.2 Снимок

`.todoc/history/objects/<2hex>/<rest>` — zlib-сжатые байты, имя = SHA-256 несжатого
содержимого (тот же формат `sha256:`, что уже возвращает `file_hash`).

**Храним только образ «до».** Образ «после» уже лежит на диске. Содержимое файла на
ревизии R восстанавливается как образ «до» первого изменения после R, либо текущий файл,
если изменений не было. Это вдвое уменьшает объём без потери возможности.

### 5.3 Запись изменения

`change` предлагается сделать **обычным `entity_type`**, а не отдельной сущностью:

```json
{"schema_version":1,"record_id":"change:add-history","entity_type":"change",
 "title":"Журнал изменений и откат","status":"proposed",
 "created_at":"2026-11-25T10:00:00Z","applied_at":null,
 "artifacts":["docs/state/09-storage-and-index.md"],
 "relations":[{"type_id":"blocked_by","target":{"kind":"record","id":"change:index-redesign"}}]}
```

Тогда бесплатно достаются: валидация схемы, `records query --where status=proposed`,
типизированные отношения с cardinality и обход графа зависимостей через существующий
`relations graph`. Это прямое использование P9 вместо нового механизма.

`status`: `proposed` → `in_progress` → `blocked` → `applied` → `archived` | `reverted`.

### 5.4 Дельта

```markdown
---
target: docs/state/09-storage-and-index.md
base_hash: sha256:aa…        # опционально, для строгой проверки
---

## MODIFIED: ## Поколение индекса
…новое тело раздела…

## ADDED: ## Журнал событий
…

## REMOVED: ## Устаревшее
```

Якорь — путь заголовков; markdown уже разбирается на секции (`docs read --section`,
`SECTION_MAX_LINES=40` в `cli.py:50`), поэтому парсер секций переиспользуется.

**Здесь todoc сильнее OpenSpec.** `openspec validate` проверяет *формат* дельты.
`todoc change validate` проверяет *применимость к живому состоянию*: целевой файл
существует, якорь найден, `base_hash` совпадает, а пробное применение не добавляет
диагностик в `validate --all`. У OpenSpec валидатора состояния нет.

### 5.5 Би-темпоральные поля

На отношении (опционально, обратно совместимо):

```json
{"type_id":"employs","target":{"kind":"record","id":"person:sergei"},
 "valid_from":"2024-01-01","valid_to":"2026-06-30",
 "observed_at":"2026-11-25T10:00:00Z","superseded_at":null}
```

- `valid_from`/`valid_to` — когда было правдой в мире (у Graphiti это `valid_at`/`invalid_at`).
- `observed_at`/`superseded_at` — когда todoc узнал / когда заменил (`created_at`/`expired_at`).
- **Инвалидация, а не удаление**: противоречащий факт закрывает старый `superseded_at`.
  Именно Mem0 критикуют за разрушающий `DELETE`, теряющий историю.
- Точка во времени: `valid_from <= T AND (valid_to IS NULL OR T < valid_to)`.

Оговорка: у Zep противоречие ищет LLM, у todoc ядро детерминированное (P5), поэтому
инвалидация **явная** — через `change` или правку записи. Система не догадывается.

### 5.6 Зависимости артефактов

```json
{"record_id":"metric:bench-2026-11-25","entity_type":"metric",
 "derived_from":[{"path":"bench/results/benchmark.json","hash":"sha256:cc…"}]}
```

`todoc stale` сравнивает записанный хеш с текущим. Механизм уже есть в кодовой базе как
прецедент: `config_digest` (`registry.py:16-27`) — SHA-256 по конфигурации, чтобы понять,
менялась ли она между поколениями. Тот же приём, применённый к произвольным зависимостям.

## 6. Фаза 0 — редизайн индекса (предпосылка)

Без неё журнал будет дублировать накопление поколений.

1. **Один снимок вместо серии.** `.todoc/index/current/` публикуется через тот же
   tmp+rename, что и сейчас (`registry.py:70-95`), но перезаписывается на месте.
   История поколений удаляется — её роль переходит журналу.
2. **Инвалидация по `corpus_digest`.** SHA-256 по отсортированным парам
   `(rel_path, content_hash)` плюс `config_digest`. Совпал — снимок не переиздаётся,
   диагностики берутся из существующего. Это закрывает и P1-1.
3. **`stats.json`** (path → hash, mtime, size) позволяет считать дайджест через `stat()`
   без перечитывания содержимого неизменённых файлов.
4. **`created_at` в `CURRENT.json`** — сейчас времени нет нигде.

Закрывает: P1-1, P1-2. Убирает 27 МБ производного в демо (замер 2026-11-25).

## 7. CLI-контракт

Все команды — в существующем конверте (`ok`, `data`, `diagnostics`, `next_actions`),
с `truncated`, `cursor` и бюджетом по P7.

```
todoc index rebuild [--force]

todoc log [--path P] [--section H] [--change ID] [--tag T] [--kind K]
          [--since ISO] [--until ISO] [--limit N] [--cursor C]
todoc show <rev> [--path P] [--section H]
todoc diff [<rev-a>] [<rev-b>] [--path P] [--section H] [--context N]
todoc blame --path P [--section H]
todoc revert <rev> [--path P] [--apply] [--expected-hash H]
todoc tag <name> [--rev R] [--message M]

todoc change list [--status S]
todoc change open --title T [--blocked-by ID] [--artifact P]
todoc change show <id>
todoc change validate <id>          # применимость дельт к живому состоянию
todoc change verify <id>            # completeness/correctness/coherence, детерминированно
todoc change apply <id> [--apply]   # bundle-транзакция
todoc change archive <id> [--tag T]
todoc change revert <id> [--apply]

todoc context --change <id> [--budget N] [--with-diff]   # один вызов — весь контекст задачи
todoc context --tag <name>  [--budget N] [--with-diff]

todoc stale [--path P] [--severity S]
todoc stale --ack <path> --reason R  # признание устаревания нерелевантным
todoc timeline [--as-of D] [--path P]
todoc records query --as-of D

todoc history adopt                  # миграция: снимок текущего состояния, rev=baseline
todoc history export [--to DIR]      # бэкап для бэкенда embedded
todoc history gc [--keep-objects N] [--purge-before ISO] [--dry-run]
```

Соответствие ментальной модели git:

| git | todoc |
|---|---|
| `git log` / `log --follow` | `todoc log` / `log --path` |
| — | `todoc log --section "## Решение"` (git так не умеет) |
| `git show <rev>:<path>` | `todoc show <rev> --path` |
| `git diff a b` | `todoc diff a b` |
| `git blame` | `todoc blame` |
| `git revert` | `todoc revert --apply` |
| `git tag` | `todoc tag` / `change archive --tag` |
| ветка | `change` — «ветка намерения», не содержимого |
| `git bisect` | `todoc stale` + `todoc timeline` |

**Лента по разделу** — то, чего git не даёт: фильтрация записей журнала по пересечению
`ranges` с границами секции. Парсер секций уже есть.

**Перехват записи.** Все три точки записи — `apply_write_plan` (`write.py:107`),
`apply_fix` (`write.py:126`), `apply_edit_ops` (`write.py:142`) — уже идут через
`atomic_write` и принимают `expected_hash`. Журнал пишется в одной транзакции с ними.

## 8. Коды диагностик

| Код | Смысл |
|---|---|
| `history.journal_unreadable` | строка не разбирается как JSON |
| `history.journal_truncated_line` | последняя строка оборвана (допустимо, игнорируется) |
| `history.object_missing` | снимок отсутствует в `objects/` |
| `history.revision_unknown` | неизвестный `rev` |
| `history.range_conflict` | файл изменён после снимаемой ревизии |
| `change.not_found` / `change.id_invalid` | — |
| `change.delta_target_missing` | целевой файл дельты не существует |
| `change.delta_target_outside_root` | цель дельты выходит за DATA_ROOT (включая `..`, абсолютный путь и симлинк наружу) |
| `change.delta_anchor_missing` | заголовок-якорь не найден |
| `change.base_hash_mismatch` | файл ушёл из-под дельты |
| `change.blocked_by_unresolved` | зависимость не в `archived` |
| `change.already_applied` | повторное применение |
| `change.post_apply_invalid` | пробное применение добавляет диагностики |
| `temporal.invalid_interval` | `valid_to <= valid_from` |
| `staleness.dependency_changed` | хеш зависимости разошёлся |
| `staleness.dependency_missing` | файл зависимости удалён |
| `history.backend_unavailable` | бэкенд `git` выбран, но git недоступен; деградация в `embedded` (severity `warning`) |
| `change.apply_order_ambiguous` | порядок применения артефактов неоднозначен, нужен явный `order` |

Полнота таблицы проверена скриптом: все коды, упомянутые где-либо в плане, перечислены
здесь. Конфликтов с 81 существующим кодом в `src/todoc` нет — префиксы `history.`,
`change.`, `temporal.`, `staleness.` в текущем коде не используются.

Лимиты в `dataset.json` (по образцу `DEFAULT_LIMITS` в `config.py`):

## 9. Фазы и критерии приёмки

Номера фаз — как в обсуждении. Порядок исполнения предложен с учётом зависимостей.

**Решение принято 2026-11-25: Фаза 0 и Фаза 4 делаются одним заходом.** Это снимает
противоречие в прежней формулировке, где Фаза 0 была «предпосылкой для всех», а Фаза 4 —
«рекомендованным стартом». Фаза 0 идёт первой внутри набора, потому что журнал поверх
текущего индекса писал бы ещё больше мусора.

### Фаза 0. Редизайн индекса — **РЕАЛИЗОВАНА 2026-11-25**

- **K31**: повторная команда чтения на неизменном корпусе не переиздаёт снимок (0 новых записей).
  Проверено: `generation_id` не меняется на 5 чтениях и меняется после правки файла.
- **K32**: в `.todoc/index` ровно один снимок; размер не растёт от числа запусков.
  Проверено: 337 КБ после 5 чтений и после 5 пересборок (было 27 МБ и 94 поколения).
- Приёмка: 5 команд чтения на демо → 1 снимок, а не 5. Выполнено.

Фактическое расхождение с планом: K32 сформулирован через `history gc`, которого до Фазы 1
не существует. Критерий проверен напрямую — числом снимков в `.todoc/index`.

### Фаза 4. Зависимости и устаревание — **РЕАЛИЗОВАНА 2026-11-25**

Не зависит от журнала: нужны только хеши, которые уже считаются. Бьёт в боль, которую уже
наблюдали: числа `420 passed`, `2491 инструкция`, `868 веток` разошлись по семи файлам, и
искали их грепом.

- `derived_from` в записях и front matter; `todoc stale`. Сделано, включая `--ack --reason`
  из §17.2 и якоря на фрагмент из §17.1 (JSON Pointer и `section:`).
- **K33**: recall обнаружения устаревания = 1.0 на засеянном дрейфе (10 засеянных расхождений).
  Проверено: 10 из 10 обнаружены.
- **K34**: 0 ложных срабатываний на неизменённых зависимостях. Проверено.
- **K44**: 0 ложных срабатываний при изменении несвязанной части зависимости. Проверено на
  `/probes/S1` и `/meta/score` при якоре на `/meta/date`.
- **K45**: `stale --ack` снимает диагностику, смена хеша возвращает её. Проверено.

### Фаза 1. Журнал и откат — **РЕАЛИЗОВАНА 2026-11-25**

- `ports/history.py`, `adapters/history/{journal,objects,backends}.py`, `application/history.py`.
  Единственный `subprocess` в `src/todoc` — в `adapters/history/backends.py`, ядро от git не
  зависит.
- `log`, `show`, `diff`, `blame`, `revert`, `tag`, `history gc`, `history adopt`,
  `history export`. CLI вырос с 27 до 36 листовых команд.
- Режим по умолчанию `observed` (решение принято): при сканировании расхождение хеша без
  объясняющей записи журнала фиксируется как `external.change`. Сделано, включая правило
  базовой линии: без `history adopt` неизвестный путь внешним не объявляется, иначе первый
  скан после первой записи пометил бы весь корпус.
- **K35**: `revert` восстанавливает содержимое байт-в-байт на 20 засеянных правках.
  Проверено: 20 из 20. Базовая линия (`snapshot`) в счёт не идёт — у неё нет состояния «до».
- **K36**: объём `history/` после `gc` ≤ 2× от объёма документов. Проверено: 30 813 байт
  истории на 47 190 байт документов = 0,65×.
- **K37**: лента по разделу отдаёт только события, пересекающие границы секции. Проверено:
  правка строки 9 отдаётся только для `## Решение`, строки 13 — только для `## Итоги`.

Фактическое расхождение с планом, найденное при проверке: `revert` был построен на
`content_at()`, которая возвращает состояние **после** события, поэтому откат последнего
изменения молча возвращал текущий файл (`applied: true`, содержимое то же). Семантика
разделена по образцу git: `show REV` — состояние на ревизии, `revert REV` — образ «до»
события (`before_content()`). Создание файла и базовая линия дают `no_before`, а не
`revision_unknown` в тексте ошибки.

Попутно закрыт дефект, существовавший до Фазы 1: отсутствующий `--patch-file` давал голый
трейсбек `FileNotFoundError` вместо конверта (нарушение P11). Теперь `usage.error`, exit 2.

### Фаза 2. Записи изменений и дельты — **РЕАЛИЗОВАНА 2026-11-25** (в core — решение принято)

Это те самые bundle-транзакции, которые конституция (G3) и
[`memory-llm-wiki.after.md`](memory-llm-wiki.after.md) (Шаг 5) называют гейтом перед
широкими записями агента. Не новая идея — закрытие уже заявленного пробела.

- `entity_type: change`, `relation_type: blocked_by`, `changes/` в DATA_ROOT.
- `application/changes.py`, `application/context.py`; `doc_type: delta` с `any_of_sections`
  (ADDED/MODIFIED/REMOVED) и первым в кодовой базе `schema` для front matter документа.
- `change list/open/show/validate/verify/apply/archive/revert` + `context` — 9 новых команд,
  CLI вырос с 36 до 45 листовых команд.
- События журнала `change.open` / `change.apply` / `change.revert` / `change.archive`
  с привязкой `change_id`.
- **K38**: `change validate` ловит дрейф якоря и `base_hash` до применения. Проверено
  именованными тестами на пять засеянных дрейфов (`test_validate_detects_missing_anchor`,
  `_base_hash_mismatch`, `_missing_target`, `_delta_without_target`, `_ambiguous_order`),
  ложных срабатываний нет (`test_validate_on_correct_delta_has_no_errors`).
- **K39**: `change apply` атомарен: при ошибке ни один файл не изменён. Проверено:
  `test_apply_is_atomic_on_write_failure` (оба файла байт-в-байт прежние, статус `proposed`)
  и `test_apply_reports_when_rollback_also_fails`.
- **K42**, **K43**, **K46**: проверены именованными тестами (один вызов `context` на задаче
  из 5 документов; объём ≤ бюджета без тел диффов; два запуска `verify` идентичны).

Расхождения с планом, найденные при проверке:

1. `change apply` писал событие `kind: doc.edit` с `change_id: None`, поэтому
   `log --change <id>` своей же истории не видел. Исправлено: все четыре команды передают
   идентификатор изменения в регистратор журнала.
2. §17.4 `history.require_change_for_multi_file` не реализован: пути многофайловой записи
   в ядре нет (`apply_write_plan`, `apply_fix`, `apply_edit_ops` пишут один файл), поэтому
   флагу нечего проверять. Зафиксировано в [известных проблемах](../state/11-known-issues.md)
   как P1-12.
3. `change archive` переносит папку в `changes/archive/<YYYY-MM-DD>-<slug>/`, поэтому
   `change_dir` ищет запись в обоих местах, а `list_changes` читает `record_id` из
   `change.json`, а не из имени папки.
4. Шаблон `tasks.md` не содержит ни одного пункта: `change verify` считает незакрытые
   чекбоксы, и пункт в шаблоне делал бы каждое свежее изменение неполным.

### Фаза 3. Би-темпоральность — **РЕАЛИЗОВАНА 2026-11-25**

- Поля из §5.5 у записей **и** отношений, `--as-of`, инвалидация вместо удаления.
- `application/temporal.py`: нормализация моментов к UTC (лексикографический порядок
  совпадает с хронологическим), полуоткрытый интервал, выборки по обоим часам, лента.

- **K40**: point-in-time запрос корректен на засеянных интервалах (точно, без допусков).
  Проверено: `test_k40_point_in_time_is_exact_on_seeded_intervals` сверяет выборку на 11 днях
  четырёх засеянных интервалов (включая открытые с обеих сторон), плюс
  `test_k40_interval_end_is_exclusive_not_inclusive` фиксирует полуоткрытость.
- **K41**: противоречащий факт закрывает старый, старый остаётся читаемым. Проверено:
  `test_k41_contradicting_fact_closes_the_old_one` (закрытый факт остаётся в данных и в ленте,
  виден только до `superseded_at`) и `test_k41_closed_fact_still_readable_through_records`.

Расхождения с планом, найденные при проверке:

1. В таблицу §8 добавлен код `temporal.invalid_instant` — неразбираемое значение даты или

2. Темпоральные поля поддержаны не только на отношении (как в §5.5), но и на самой записи —

## 10. Миграция

1. Существующие `generations/` не конвертируются — они не содержат ни времени, ни порядка,
   ни намерения, то есть восстанавливать из них нечего. Команда `todoc history adopt`
   снимает текущее состояние как базовую ревизию `rev=baseline` и удаляет `generations/`.
2. `dataset.json` получает секцию `history` с дефолтами; отсутствие секции = `mode: "observed"`.
3. Старые записи без темпоральных полей ведут себя точно как сейчас — поля опциональны.
4. Обратная совместимость CLI не нарушается: все новые команды добавляются, существующие
   сигнатуры не меняются.

## 11. Риски

| Риск | Мера |
|---|---|
| Рост объёма `history/` | zlib + дедупликация по хешу + `history gc --keep-objects` |
| **Приватность**: история хранит удалённое | `history gc --purge-before`; без него «удалил» ≠ «удалил» |
| Повреждение журнала | append-only + оборванная последняя строка игнорируется, не валит команду |
| История не пересобирается | режим `git`: восстанавливается из репозитория, третья категория не нужна (§18). Режим `embedded`: явная третья категория хранения и требование бэкапа в конституции |
| Незакоммиченные промежуточные состояния в режиме `git` | правило `gap-filling`: свой снимок пишется, когда прошлое состояние недостижимо из git (§18) |
| `changes/` попадает под сканер | `HARD_EXCLUDE_DIRS` (`scanner.py:10`) его не исключает — нужно правило `dir_type`; валидация дельт решена в §19 |
| `change.json` без `record_id` не станет записью | `service.py:87` пропускает JSON без `record_id` — намеренно, чтобы не смешивать |
| Конкурентная запись | не решается: single-writer, C33 (multi-user) — WON'T |

## 12. Чего сознательно нет

- **Веток, слияний, 3-way merge, packing с дельта-сжатием, remote.** Это git; переделывать
  его хуже бессмысленно. История todoc линейна.
- **LLM-извлечения фактов** (Mem0 phase 1). Нарушает P5; остаётся за пределами ядра.
- **Graph DB.** Убивает переносимость; в [`competitive-analysis.md`](competitive-analysis.md)
  Zep отмечен именно за это («портабельность: низкая, graph DB — истина»).
- **Автообнаружения противоречий.** Только явная инвалидация.
- **Разделения на «истину» и «копию» документов.** Файлы остаются единственной истиной (P1).

Что взято у каждого источника:

| Источник | Взято | Не взято |
|---|---|---|
| OpenSpec | `changes/` как единица работы; ADDED/MODIFIED/REMOVED; архив с датой; `blocked_by` | их CLI-обвязка, переписывание спеки целиком |
| Zep/Graphiti | би-темпоральность; инвалидация вместо удаления; point-in-time | graph DB, LLM-поиск противоречий |
| Mem0 | аудит-лог каждой мутации `old → new + event + actor`; словарь операций | LLM-extract, разрушающий `DELETE` |
| git | контентная адресация blob/commit; oplog как JSONL | ветки, merge, packing, remote |

## 13. Открытые вопросы

1. Валидируются ли файлы в `changes/` как обычные документы? Если да — нужен `doc_type`
   для дельт и правило в `rules/document-rules.json`.
   **Решено** (§19): валидируются, `doc_type: delta`, правило по glob
   `**/changes/*/deltas/*.md`.
2. Снимать ли снапшот на каждом скане в режиме `observed`? Это даёт «до» для внешних
   правок, но удваивает объём. Альтернатива — снимать только при обнаружении расхождения.
   **Решено** (§18): правило `gap-filling` — снимок пишется только когда предыдущее
   состояние недостижимо из бэкенда истории.
3. Нужен ли `todoc log` в MCP-контракте сразу, или после стабилизации CLI.
   **Решено** (2026-11-25): MCP — надстройка над CLI и только потом. Сейчас всё делается
   через CLI; MCP может вообще не понадобиться. В контракт истории это ничего не вносит:
   `todoc log` проектируется как обычная команда CLI, а вопрос о её отражении в MCP
   откладывается до момента, когда MCP вообще появится. Следствие для §16: строка
   «интеграции с агентами» остаётся слабым местом по нашей собственной воле, а не долгом.
4. Хранить `history/` в git по умолчанию или оставить на усмотрение пользователя
   (тогда нужна явная команда `todoc history export`).
   **Решено** (§18): два бэкенда, автоопределение — `git` внутри репозитория, `embedded`
   вне его; `todoc history export` остаётся для режима `embedded`.
5. Добавлять ли `schema` в `KIND_FIELDS["doc_type"]` (вариант (a) в §19) —
   это изменение контракта описателей, затрагивающее все `doc_type`, а не только дельты.
   **Решено** (2026-11-25): **вариант (a)**, обобщить. Схема объявляется для любого
   `doc_type`, проверка front matter документов становится общей с записями.

Все пять вопросов закрыты. Открытых решений перед реализацией нет.

## 14. Ответ на ключевой сценарий: «документы задачи и релиза + их история»

Запрошенный сценарий: найти документы, связанные с задачей или релизом, и просмотреть всю
их историю из CLI способом, удобным агенту. Он складывается из уже заложенного, но в плане
не хватало связующей команды. Добавляется:

```
todoc context --change <id> [--budget N] [--with-diff] [--output json]
todoc context --tag <name>  [--budget N] [--with-diff] [--output json]
```

Ответ — **один bounded-пакет**, а не серия запросов:

```json
{"ok":true,"data":{
  "change_id":"change:add-history","status":"applied","applied_at":"2026-11-25T11:40:00Z",
  "revisions":["a1b2c3d4e5f6","f6e5d4c3b2a1"],
  "artifacts":[
    {"path":"docs/state/09-storage-and-index.md",
     "doc_type":"state","title":"Хранилище: индекс, поколения, кэш",
     "commits":2,"first":"2026-11-20T09:00:00Z","last":"2026-11-25T11:40:00Z",
     "stale":false}],
  "counts":{"artifacts":3,"revisions":2,"changed_lines":41},
  "truncated":false}}
```

Почему это удобно агенту (по [`../research/mcp-cli-agents.md`](../research/mcp-cli-agents.md), §8.2–8.4):

- **Прогрессивное раскрытие.** По умолчанию — только счётчики, пути, заголовки и ревизии.
  Тела диффов — только с `--with-diff` или адресно через `todoc show <rev> --path`.
- **Подсчёт вне контекста модели.** Число правок, изменённых строк и затронутых документов
  считается в CLI (§8.3), а не пересчитывается моделью по сырому журналу.
- **Один вызов вместо пяти.** Агент не должен сначала читать `change.json`, потом журнал,
  потом по каждому пути искать историю.
- **Обязательные маркеры интерпретации** (§8.4): `truncated`, `counts`, единицы времени в UTC.

Связка данных: `artifacts` в `change.json` (§5.3) → записи журнала с `change_id` (§5.1) →
`ranges` для лент по разделу → `refs.json` для релизов. Всё уже заложено; не хватало только
команды, которая собирает это за один вызов.

**Обратное направление** — от документа к задачам — даёт существующая `todoc log --path`
с фильтром по `change_id`. Обе стороны закрыты.

## 15. Требования к CLI истории из нашего исследования

[`../research/mcp-cli-agents.md`](../research/mcp-cli-agents.md) (§7, §8, §12, §13) даёт
конкретные анти-паттерны. Они переносятся в критерии приёмки новых команд — иначе план
повторит ошибки, которые сам же задокументировал.

| Анти-паттерн из §12 | Требование к новым командам |
|---|---|
| «Обрезать список молча или возвращать топ-N без признака ограничения» | `log`, `stale`, `context` всегда несут `truncated` + `cursor` + путь получить остаток |
| «Возвращать успешный статус при выполнении только части операции» | `change apply` — всё или ничего; частичное применение = ошибка, файлы не тронуты |
| «Автоматически повторять после таймаута необратимое действие, не проверив идемпотентность» | `revert` и `change apply` принимают `expected_hash`; повтор безопасен |
| «Требовать TTY prompt в сценарии автоматизации» | `--no-input` у каждой новой команды (уже есть у 28 существующих опций в `cli.py`) |
| «Делать машинный режим неотличимым от меняющейся human-таблицы» | `--output json` — строгий конверт; `table`/`markdown` не обещают стабильности |
| «Возвращать все строки/поля на всякий случай» | `context` без `--with-diff` не отдаёт тела; `--fields` для проекции |

Дополнительно из §7.4 («команда меняет состояние — сообщать, что именно изменилось»):
каждая пишущая команда истории обязана разделять «подготовлено» и «применено» и возвращать
идентификатор результата — `rev` или `change_id`.

Из §7.1–7.2 это уже выполняется в кодовой базе и должно сохраниться: коды выхода 0–6
документированы в `errors.py:1-11`, а `_emit_error()` кладёт в stdout ровно один конверт
`ok: false` плюс человекочитаемую строку в stderr — то есть ошибка тоже машина-читаема.
Новые команды обязаны идти через тот же путь, а не заводить свои.

### Чем мы будем сильнее

1. **Единственный инструмент, связывающий намерение с проверяемым состоянием.** OpenSpec
   проверяет формат дельты, SpecKit — согласованность артефактов между собой. Ни один не
   спрашивает «а существует ли в живом файле раздел, который ты правишь?». У нас это
   `change.delta_anchor_missing` и `change.base_hash_mismatch`.
2. **Хронология без внешнего VCS и на уровне раздела.** git даёт историю файла; ни один
   конкурент не даёт историю раздела документа.
3. **Темпоральность фактов.** Это уровень Zep/Graphiti, но в обычных файлах, без graph DB.
4. **Устаревание по якорям, а не по файлу** — см. §17.1.
5. **Всё вышеперечисленное — офлайн и в переносимой папке.**

### Чего у нас не будет (осознанно)

- **Охвата агентов.** У SpecKit 30–41 интеграция и ~140 тыс. звёзд, у OpenSpec 20+. У нас
  один CLI. **Решение 2026-11-25:** MCP — надстройка над CLI и только потом; сейчас всё
  делается через CLI, и MCP может вообще не понадобиться. Это осознанный выбор, а не долг:
  CLI уже обслуживает любого агента, который умеет запускать команды, а дублировать тот же
  контракт вторым протоколом — это две поверхности, которые надо держать согласованными.
  Разрыв в дистрибуции остаётся, в качестве — нет.
- **LLM-этапов.** `clarify`, `analyze`, `converge` у SpecKit — это работа модели. Мы их не
  повторяем по P5; наш аналог `converge` — детерминированный `change verify` (§17.3).
- **Скаффолдинга и экосистемы.** Мы не генерируем проект и не имеем пресетов.
- **Публикации и веба.** Docusaurus/Mintlify остаются лучше для публичных доков.

**Вывод:** мы не заменяем OpenSpec/SpecKit в их сценарии (зелёный проект, много агентов).
Мы сильнее там, где документация и спецификации уже существуют и должны **оставаться
проверяемо верными** — brownfield, аудит, работа агента над существующей базой. Это ровно
тот пробел, который в их собственных сравнениях описан как «documentation drift is the
default».

## 17. Дополнения к плану

### 17.1 Якоря в `derived_from` — иначе `stale` утонет в ложных срабатываниях

В §5.6 зависимость — это `{path, hash}` всего файла. Значит любое изменение
`benchmark.json` пометит устаревшим каждый документ, который на него ссылается, даже если
изменилось несвязанное поле. Критерий K34 (0 ложных срабатываний) при такой схеме
невыполним. Уточнение схемы:

```json
"derived_from":[
  {"path":"bench/results/benchmark.json","pointer":"/meta/date","hash":"sha256:…"},
  {"path":"docs/state/10-testing-and-quality.md","section":"## Текущие цифры","hash":"sha256:…"}
]
```

Хеш считается от **фрагмента**: JSON Pointer для JSON, путь заголовков для Markdown
(парсер секций уже есть), диапазон строк как частный случай. Оба механизма уже реализованы
в кодовой базе — `jsonfmt.py` умеет JSON Pointer, `markdown.py` умеет секции.

Это прямой урок Swimm: их сильная сторона — связь на уровне токена/сниппета через SHA и
ссылки AST, а не на уровне файла. Их же слабая сторона — предупреждение: «auto-sync flags
documentation that needs updating but cannot write those updates... teams that do not
establish clear ownership will find flagged items accumulating without resolution».
Отсюда второе дополнение.

### 17.2 Подтверждение устаревания, иначе `stale` станет шумом

`stale`, который нельзя закрыть, игнорируют. Добавляется явное подтверждение:

```
todoc stale --ack <path> --reason "числа обновлены вручную, зависимость не релевантна"
```

Поля `stale_acknowledged_at` и `stale_ack_reason` в записи/front matter; подтверждение
сбрасывается, когда хеш зависимости меняется снова. Диагностика `staleness.dependency_changed`
не выдаётся для подтверждённых и не менявшихся зависимостей. Без этого K34 недостижим на
реальном датасете.

### 17.3 `change verify` — детерминированный аналог `converge`

У SpecKit `/speckit.converge` ищет расхождения кода и спецификации моделью. У OpenSpec
`/opsx:verify` даёт трёхмерный отчёт (completeness / correctness / coherence) с оценками
CRITICAL / WARNING / SUGGESTION. Наш аналог — без модели:

```
todoc change verify <id>
```

- **completeness**: все `tasks.md` отмечены, все `artifacts` изменены;
- **correctness**: текущее состояние файлов соответствует дельтам (по хешам секций);
- **coherence**: `validate --all` не даёт новых диагностик относительно `base`.

Оценки отображаются на уже существующие `severity: error | warning`. Детерминированность — это
преимущество: результат воспроизводим и может быть гейтом в CI, чего нельзя сказать о
проверке моделью.

### 17.4 Церемония должна быть необязательной

Слабое место OpenSpec по их собственным обзорам: «one-artifact-at-a-time constraint...
makes the workflow feel slow when a change is small and obvious». Поэтому:

- `docs edit` и `fix` работают **без** открытого `change` — как сейчас;
- `change` требуется только для многофайловых правок (`--apply` более чем одного файла)
  и только если в `dataset.json` включён `history.require_change_for_multi_file`;
- по умолчанию флаг выключен.

Иначе инструмент начнут обходить, и журнал окажется неполным — что обесценит всю хронологию.

**Решение от 2026-11-25 (Фаза 2).** Флаг пока не реализован, и это содержательное решение,
а не пропуск: пути многофайловой записи в ядре не существует. `apply_write_plan`, `apply_fix`
и `apply_edit_ops` пишут ровно один файл, а `change apply` — единственная операция на
несколько файлов — уже идёт через изменение. Флаг проверял бы несуществующий код, поэтому
он появится вместе с многофайловой записью вне изменений. Пробел зафиксирован в
[известных проблемах](../state/11-known-issues.md) как P1-12.

### 17.5 Приоритеты артефактов внутри `change`

SpecKit помечает независимые задачи `[P]` для параллельного исполнения агентами. Нам это
не нужно на уровне задач (это уже task manager, C26 WON'T), но нужно на уровне артефактов:
порядок применения дельт должен быть детерминированным. Добавляется `order` в `change.json`
и диагностика `change.apply_order_ambiguous`, если порядок неоднозначен. Это требование
K39 (атомарность) — без детерминированного порядка атомарность непроверяема.

### 17.6 Новые критерии

| Критерий | Что измеряет |
|---|---|
| **K42** | `context --change` возвращает все связанные артефакты за один вызов; полнота 1.0 на засеянной задаче из 5 документов |
| **K43** | `context` без `--with-diff` не содержит тел диффов; объём ответа ≤ бюджета |
| **K44** | `stale` с якорями: 0 ложных срабатываний при изменении несвязанной части зависимости |
| **K45** | `stale --ack` снимает диагностику; смена хеша зависимости возвращает её |
| **K46** | `change verify` воспроизводим: два запуска на неизменном состоянии дают идентичный результат |
| **K47** | Ни одна новая команда не требует TTY при `--no-input` |
| **K48** | Каждая новая команда при ошибке возвращает конверт `ok: false` в stdout и ненулевой exit code |

K47 и K48 — прямая проверка анти-паттернов из §12 исследования; их легко измерить
subprocess-тестом с закрытым stdin.

## 18. Два режима хранения: `embedded` и `git`

Решение принято 2026-11-25: история отслеживается git'ом, но это закрывает **долговечность,
а не семантику**. Поэтому режимов два, и переключаются они одной настройкой.

### Что git закрывает, а что нет

Проверено: `subprocess` в `src/todoc` — 0 вхождений, git-интеграции в кодовой базе нет.
`.todoc/history` в `.gitignore` отсутствует, то есть каталог по умолчанию отслеживается
(в отличие от `**/.todoc/index/`, `**/.todoc/cache/`, `**/.todoc/generated/`).

| Проблема | Git закрывает? |
|---|---|
| Долговечность истории (бэкап) | **Да** — снимает требование отдельного бэкапа |
| Хранение содержимого «до» | **Да** — git уже контент-адресен, свой `objects/` дублирует его |
| Привязка правки к задаче (`change_id`) | **Нет** — в git это текст коммита, не структурированное поле |
| Изменённые диапазоны строк (`ranges`) | **Нет** — дифф их вычисляет, но не хранит как индекс |
| Лента по разделу | **Нет** — производная от `ranges` |
| Би-темпоральные факты | **Нет** — это данные в файлах, git к ним не относится |
| Устаревание по `derived_from` | **Нет** — git не сравнивает хеши зависимостей |
| Bounded-выдача агенту | **Нет** — у `git log` нет `truncated`/`cursor`/бюджета |

Вывод: **журнал нужен в обоих режимах.** Git заменяет снапшот-стор, а не журнал.

### Режимы

```json
"history": {
  "backend": "git",          // "embedded" | "git"
  "mode": "observed",
  "snapshots": "gap-filling" // см. ниже
}
```

**`embedded`** — снимки пишутся в `.todoc/history/objects/` всегда. История самодостаточна,
переносится копированием папки, git не требуется. Бэкап — забота пользователя
(`todoc history export`).

**`git`** — снимки по умолчанию не пишутся: содержимое «до» берётся из git
(`git show <git_head>:<path>`). Журнал пишется всегда. Бэкап обеспечивается git'ом.

### Проблема промежуточных состояний и правило `gap-filling`

У режима `git` есть изъян, который надо назвать явно. Событие журнала создаётся в момент
записи, а коммит делает пользователь — позже или никогда. Поэтому:

- в журнал пишется `git_head` на момент записи (состояние **до** изменения);
- если пользователь сделал три записи подряд без коммита, у всех трёх событий один
  `git_head`, и два промежуточных состояния из git не восстановить.

Отсюда правило **`gap-filling`**: свой снимок пишется только тогда, когда предыдущее
состояние файла недостижимо из git, то есть когда у прошлого события по этому пути тот же
`git_head`. Иначе — не пишется.

Результат: git покрывает закоммиченные состояния, свой стор — только незакоммиченные
промежутки. Объём близок к нулю при дисциплине коммитов и остаётся полным без неё.

### Деградация при отсутствии git

Режим `git` не должен ломать датасет на машине без git (P2 — переносимость). Поэтому:

- git вызывается через `subprocess` только в режиме `git`; ядро от него не зависит;
- при отсутствии git или вне репозитория — диагностика `history.backend_unavailable`
  (severity `warning`) и автоматический переход на `embedded` для этой записи;
- `todoc doctor` сообщает фактический бэкенд и причину деградации.

### Что это меняет в прежних разделах

- §3: поправка в конституцию нужна только для режима `embedded`. В режиме `git` третья
  категория хранения исчезает — история становится производным, которое восстанавливается из git.
- §11 (риски): риск «история не пересобирается» снимается в режиме `git`.
- §13, вопрос 4: закрыт — `history/` в git по умолчанию, `.gitignore` не меняется.

**Решение принято 2026-11-25: автоопределение.** Внутри git-репозитория — `git`, вне его —
`embedded`. Определяется один раз при `init` и пишется в `dataset.json`; явный флаг
переопределяет. Если git исчез после `init`, датасет не ломается: переход на `embedded`
с диагностикой `history.backend_unavailable` (severity `warning`).

Проверка при `init` — одна команда `git rev-parse --is-inside-work-tree`, её результат
фиксируется, а не вычисляется на каждую запись: датасет не должен менять поведение от того,
в какую папку его переложили.

## 19. `doc_type` для дельт: что уже есть в коде

Решение принято 2026-11-25: дельты валидируются существующим механизмом `doc_type`,
новый код — минимальный. Ниже — ровно то, что проверено в кодовой базе.

### Уже работает без нового кода

| Механизм | Где | Что даёт дельтам |
|---|---|---|
| `required_sections` | `validator.py:197` | диагностика `markdown.section.missing` + фикс `add_heading` |
| `section_rules` (`child_level`, `min_children`, `severity`) | `validator.py:210-236` | `markdown.section.empty` — раздел дельты без содержимого |
| **Префиксное совпадение заголовков** | `_heading_matches`: `if wanted.endswith(":"): return actual.startswith(wanted)` | **ключевое**: селектор `## MODIFIED:` совпадает с `## MODIFIED: ## Поколение индекса`. Проверено прогоном |
| `heading_path_for` | `markdown.py:344`, используется в `search.py:72` и `cli.py:455` | разрешение якоря дельты в реальный раздел |
| `parse_heading_selector` | `descriptors.py:269` | разбор селектора `## Заголовок` → `(2, "Заголовок")` |
| `template`, `prompts` | `KIND_FIELDS["doc_type"]` | стартовый шаблон дельты и CRUD-промпты |
| Маршрутизация по glob | `default_document_rules()` в `config.py` | правило `**/changes/*/deltas/*.md` → `doc_type: delta` |

Префиксное совпадение — главная находка: формат дельты `## MODIFIED: <цель>` из §5.4
валидируется **существующим** кодом, ничего писать не нужно.

Описатель типа — целиком данные:

```json
{"schema_version":1,"type_id":"delta","kind":"doc_type","format":"markdown",
 "description":"Дельта изменения: ADDED / MODIFIED / REMOVED относительно цели",
 "template":"template.md",
 "section_rules":[
   {"heading":"## ADDED:","child_level":3,"min_children":1},
   {"heading":"## MODIFIED:","child_level":3,"min_children":1},
   {"heading":"## REMOVED:","child_level":3,"min_children":1}]}
```

### Чего не хватает — два пункта, оба маленькие

**1. «Хотя бы один из» отсутствует.** `required_sections` требует присутствия **всех**
перечисленных селекторов: цикл в `_check_structure` выдаёт диагностику на каждый
ненайденный. Дельте же достаточно любого одного из ADDED / MODIFIED / REMOVED.
Нужно поле `any_of_sections` в `KIND_FIELDS["doc_type"]` и одна ветка в `_check_structure`.
Использовать для этого `required_sections` нельзя — оно запретило бы дельту только
с добавлением.

**2. Front matter дельты не проверяется схемой.** Проверено: `schema` есть в
`KIND_FIELDS["entity_type"]`, но **отсутствует** в `KIND_FIELDS["doc_type"]`. Поэтому
`target` и `base_hash` из §5.4 существующим механизмом не валидируются.

Рассматривались два варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| (a) добавить `schema` в `KIND_FIELDS["doc_type"]` | единый механизм для документов и записей; front matter любых документов становится проверяемым | меняет поверхность описателей; затронет все `doc_type` |
| (b) проверять в `changes.py` | не трогает описатели | дублирует логику валидации схемы |

**Решение принято 2026-11-25: вариант (a), обобщить.** `schema` добавляется в
`KIND_FIELDS["doc_type"]`, проверка front matter документов становится общей с записями.
Обоснование: front matter документов сейчас не проверяется вообще, и это полезно далеко за
пределами дельт; соответствует P3 «декларативность типов».

Следствие, которое надо учесть в реализации: поле остаётся **необязательным**. Существующие
`doc_type` без `schema` ведут себя как раньше — ни одна текущая проверка не должна
сломаться. Дельты — первый тип, который его объявляет.

### Итог по объёму нового кода

Не нужно писать: парсер заголовков, проверку разделов, фиксы, маршрутизацию, разрешение
якоря. Нужно: `any_of_sections` (одна ветка), решение по `schema` для `doc_type`,
применение дельты (`change apply`) и проверка применимости (`change validate`).

## 21. Источники

- OpenSpec — структура `specs/` + `changes/`, формат дельт, семантика архива:
  [concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md),
  [getting-started](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md).
- Zep/Graphiti — би-темпоральная модель `valid_at/invalid_at` + `created_at/expired_at`,
  инвалидация вместо удаления, оговорка «invalidation only happens when a contradicting
  episode arrives»: [temporal model](https://mintlify.wiki/getzep/graphiti/concepts/temporal-model),
  [facts](https://help.getzep.com/v4/facts).
- Mem0 — двухфазный extract→update, ADD/UPDATE/DELETE/NOOP, аудит-лог `old_memory → new_memory`,
  критика разрушающего DELETE:
  [обзор](https://www.hubbleflow.ai/resources/magazine/mem0-memory-layer),
  [сравнение](https://www.digitalapplied.com/blog/open-source-agent-memory-mem0-letta-zep-compared).
- Контентно-адресуемое хранилище — модель blob/tree/commit, шардирование `objects/<2hex>/`,
  oplog как JSONL, `{mtime, size}` для пропуска перечитывания:
  [Git data model](https://missing.csail.mit.edu/2026/version-control/),
  [построение VCS в TypeScript](https://medium.com/@jaykarvashu/building-drift-a-content-addressed-vcs-in-typescript-29cda4890c31).
- GitHub Spec Kit — пайплайн `constitution → specify → clarify → plan → tasks → analyze →
  implement → converge`, раскладка `.specify/` и `specs/NNN-feature/`, маркеры `[P]` для
  параллельных задач, 30–41 интеграция с агентами:
  [CLI tool reference](https://deepwiki.com/github/spec-kit/4-cli-tool-reference),
  [репозиторий](https://github.com/github/spec-kit).
- Сравнение OpenSpec и Spec Kit — «living specs vs feature specs», отсутствие архива и
  verification gate у Spec Kit, медлительность OpenSpec из-за ограничения
  «один артефакт за раз»:
  [OpenSpec vs GitHub Spec Kit](https://www.specnative.dev/blog/openspec-vs-speckit),
  [OpenSpec vs Spec-Kit](https://ovidiueftimie.substack.com/p/openspec-vs-spec-kit).
- Swimm — связь документа с кодом на уровне токена/сниппета через SHA и ссылки AST,
  auto-sync как флаг в CI, и предупреждение о накоплении необработанных флагов без
  назначенного владельца: [обзор](https://www.switchtools.io/tool/swimm),
  [сравнение с Mintlify](https://inferensys.com/differences/ai-software-factory-platforms/ai-software-factory-end-to-end-platforms/swimm-vs-mintlify).
- docs-as-code и дрейф — «version control tracks doc changes but can't identify which docs
  need updating when code ships»; у Docusaurus `onBrokenLinks` ловит только битые ссылки:
  [docs as code](https://falconer.com/guides/docs-as-code/),
  [синхронизация Docusaurus](https://dev.to/alisa_hester_1/how-to-keep-docusaurus-docs-in-sync-with-your-source-code-4f03).
- Собственное исследование интерфейсов агента —
